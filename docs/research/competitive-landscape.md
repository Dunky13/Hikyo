# Wenv — Competitive Landscape Survey

**Date: 2026-07-29.** Research performed against live official docs, GitHub repos (README/LICENSE/ee directories), and pricing pages on this date. Primary sources only; every claim carries its source inline.

Scope: Infisical, Phase (phase.dev), HashiCorp Vault, OpenBao, SOPS + age, External Secrets Operator (ESO), Doppler (closed SaaS, UX reference). Synthesis (comparison table, gap analysis, license precedents) at the end.

---

## Infisical

### 1. Environment model

- Secrets are organized into **projects**, each split into **environments** — "split secrets into environments (e.g., development, staging, production)"; environments are customizable in project settings ([docs: projects](https://infisical.com/docs/documentation/platform/secrets-mgmt/project)). Environment count is tier-gated: Free = 3, Pro = 6/project, Advanced = 12/project, Enterprise = unlimited ([pricing](https://infisical.com/pricing)).
- **Folders** give "path-based secret storage," "infinitely nested," names restricted to alphanumerics and dashes; a "Replicate Secrets" feature copies secrets/folders between paths and environments ([docs: folders](https://infisical.com/docs/documentation/platform/folder)).
- **Secret referencing / interpolation**: `${KEY1}` (same env/folder), `${dev.KEY2}` (other env), `${prod.frontend.KEY2}` (env + folder), cross-project via `${@backend-api.prod.KEY1}` — cross-project refs are "not recursively expanded"; the fetching client must have permission on all base and dependent secrets ([docs: secret referencing](https://infisical.com/docs/documentation/platform/secret-reference)).
- **Secret imports** pull whole folders into the current path; "the order of secret imports matters… the secret value from the bottom-most secret import is taken" (last-import-wins override) ([docs: secret referencing & importing](https://infisical.com/docs/documentation/platform/secret-reference)).
- **Personal overrides**: shared vs personal values — "a shared value is to a `main` branch as a personal value is to a custom branch"; an override affects only the overriding user; secret reminders don't work with personal overrides ([docs: projects](https://infisical.com/docs/documentation/platform/secrets-mgmt/project)).
- **Side-by-side multi-env editing: confirmed.** The **Secrets Overview** page "captures a bird's-eye view of secrets and folders across environments" and is "useful for comparing secrets, identifying if anything is missing, and making quick changes" ([docs: projects](https://infisical.com/docs/documentation/platform/secrets-mgmt/project)); clicking a folder shows its contents "across different environments" to spot discrepancies ([docs: folders](https://infisical.com/docs/documentation/platform/folder)).

### 2. Schema/validation

- No typed values and no required-keys schema. What exists is **Secret Validation Rules**: write-time constraints on keys/values — rule types for Static Secrets, Dynamic Secrets, Secret Rotations; constraints = min/max length, regex, required prefix, required suffix, prevent value reuse; scoped by environment and folder-path glob (`/**`, `/services/*`); static-secret validation applies at write time only and "existing secrets… are not retroactively validated" ([docs: secret validation rules](https://infisical.com/docs/documentation/platform/secret-validation-rules)).
- No tier restriction is stated on that doc page, and the implementation lives in the MIT tree at `backend/src/services/secret-validation-rule` (not `/ee`) ([repo services dir](https://github.com/Infisical/infisical/tree/main/backend/src/services)).
- There is no validate-before-delivery step: rules gate writes/generation, not reads/exports ([docs: secret validation rules](https://infisical.com/docs/documentation/platform/secret-validation-rules)).

### 3. Versioning & audit

- **Secret versioning**: every change creates a version; history viewable in sidebar or via API `version` param; "rollback" today = copy-paste an old value into a new version, "automatic rollback… coming soon" ([docs: secret versioning](https://infisical.com/docs/documentation/platform/secret-versioning)). Per pricing, versioning is **not in Free**; starts at **Pro** ([pricing](https://infisical.com/pricing)).
- **Point-in-Time Recovery**: commit-based ("a snapshot of changes… at a specific point in time," scoped to environment+folder), with "Revert changes" (undo one commit) and "Roll back to this commit" (full state restore) ([docs: PIT recovery](https://infisical.com/docs/documentation/platform/pit-recovery)). The docs page says "available under the **Pro Tier**" while the current pricing page places Point-in-time Recovery in **Advanced** ($40/identity/mo) — the docs lag the pricing page ([docs](https://infisical.com/docs/documentation/platform/pit-recovery) vs [pricing](https://infisical.com/pricing)). Self-hosted PIT requires an enterprise license ([docs: PIT recovery](https://infisical.com/docs/documentation/platform/pit-recovery)).
- **Audit logs**: "40+ different events," filterable by event/actor/source/date; **paid-only** — Cloud Pro+ with tiered retention, self-hosted requires an enterprise license; ClickHouse recommended as an alternate audit backend at scale ([docs: audit logs](https://infisical.com/docs/documentation/platform/audit-logs)). Retention per pricing: Free = none, Pro = 30 days, Advanced = 90 days, Enterprise = custom ([pricing](https://infisical.com/pricing)). Audit log streaming to external providers exists ([README](https://github.com/Infisical/infisical/blob/main/README.md), [docs: audit log streams](https://infisical.com/docs/documentation/platform/audit-log-streams/audit-log-streams)); its implementation is in `/ee` (`audit-log-stream`) ([ee services](https://github.com/Infisical/infisical/tree/main/backend/src/ee/services)).

### 4. RBAC & reveal controls

- **Org roles**: Admin, Member, No Access; **project roles**: Admin, Member, Viewer, No Access; multiple roles per user with additive permissions ([docs: RBAC](https://infisical.com/docs/documentation/platform/access-controls/role-based-access-controls)).
- **Custom roles require Enterprise per the docs page** (pricing page lists "Custom Roles" from the Advanced tier) and enable "restricting access to specific secrets, folders, and environments" — i.e., per-environment/per-path permission is a paid custom-role feature ([docs: RBAC](https://infisical.com/docs/documentation/platform/access-controls/role-based-access-controls), [pricing](https://infisical.com/pricing)).
- Also available: ABAC, **additional privileges** on top of roles, and **temporary (timed) access** ([docs: access controls overview](https://infisical.com/docs/documentation/platform/access-controls/overview)).
- **Hide-values-show-names exists**: the permission model separates `DescribeSecret` (metadata only) from `ReadValue`, added explicitly "to make secret value access more granular… purely describe a secret, or reveal its value entirely" ([docs: permissions](https://infisical.com/docs/internals/permissions), [PR #3128](https://github.com/Infisical/infisical/pull/3128)).
- **Approval workflows (change requests)**: policies target an environment (e.g. `prod`); edits auto-create a change request routed to approvers; Self Approvals toggle, break-glass "Bypass Approvals," minimum approval threshold, Approve/Merge/Reject. "Available under the **Enterprise Tier** on Infisical Cloud"; self-hosted needs an enterprise license ([docs: approval workflows](https://infisical.com/docs/documentation/platform/pr-workflows)). Access requests are likewise Enterprise ("Approval Workflows & Access Requests") ([pricing](https://infisical.com/pricing)).

### 5. Delivery

- **CLI**: `infisical run [options] -- <cmd>` injects secrets as env vars; flags `--env` (default `dev`), `--path` (repeatable, first duplicate wins), `--projectId`, `--watch` (auto-restart on change, "intended for development purposes"), `--token` ([docs: infisical run](https://infisical.com/docs/cli/commands/run)); `infisical export` and `infisical secrets` for export/CRUD ([docs: CLI overview](https://infisical.com/docs/cli/overview)).
- **Docker/Compose guidance**: wrap the entrypoint — `CMD ["infisical", "run", "--projectId", "<id>", "--", "npm", "run", "start"]`, pass `INFISICAL_TOKEN` obtained via machine-identity login into the container; service tokens deprecated in favor of machine identities ([docs: Docker](https://infisical.com/docs/integrations/platforms/docker)).
- **Agent**: daemon that "automatically authenticates with Infisical and deposits renewed access tokens at specified path" and renders secrets to files via Go `text/template`; YAML config with `auth` (universal-auth, kubernetes, azure, gcp, aws-iam), `sinks`, `templates` (`destination-path`, `polling-interval` default 5 min), optional persistent cache ([docs: agent](https://infisical.com/docs/integrations/platforms/infisical-agent)).
- **Kubernetes operator**: CRDs — legacy v1alpha1 `InfisicalSecret` (now deprecated), `InfisicalPushSecret`, `InfisicalDynamicSecret`; new v1beta1 `InfisicalConnection`, `InfisicalAuth`, `InfisicalStaticSecret` ("Replaces `InfisicalSecret`"); syncs to native K8s Secrets and "can also automatically reload dependent Deployment resources" ([docs: K8s operator](https://infisical.com/docs/integrations/platforms/kubernetes/overview)).
- **ESO provider**: official Infisical provider in External Secrets Operator, incl. PushSecret ([external-secrets.io Infisical provider](https://external-secrets.io/latest/provider/infisical/)); note Infisical's own post on ESO's maintenance pause steering users to its native operator ([Infisical blog](https://infisical.com/blog/external-secrets-operator-paused)).
- **CSI**: Infisical provider for the Secrets Store CSI driver mounts secrets as pod volumes, avoiding K8s Secret objects; requires a machine identity with Kubernetes auth + a `SecretProviderClass` ([docs: Kubernetes CSI](https://infisical.com/docs/integrations/platforms/kubernetes-csi), [repo](https://github.com/Infisical/infisical-csi-provider)).
- **K8s native auth**: Infisical forwards the pod's service-account JWT "to the Kubernetes API Server at the TokenReview API for verification," checks Allowed Service Account Names / Allowed Namespaces, returns a short-lived access token ([docs: Kubernetes auth](https://infisical.com/docs/documentation/platform/identities/kubernetes-auth)).

### 6. CLI ergonomics

- Main verbs: `login`, `init`, `run`, `export`, `secrets`, `agent` ([docs: CLI overview](https://infisical.com/docs/cli/overview)).
- Human flow: `infisical login` then `infisical init` to bind a directory to a project ([docs: CLI overview](https://infisical.com/docs/cli/overview), [docs: project config](https://infisical.com/docs/cli/project-config)).
- Machine flow (CI): `export INFISICAL_TOKEN=$(infisical login --method=universal-auth --client-id=<id> --client-secret=<secret> --silent --plain)`; `--projectId` is required when authenticated via machine identity ([docs: infisical run](https://infisical.com/docs/cli/commands/run)). Machine-identity auth methods platform-wide: Universal Auth (default), Kubernetes, GCP, Azure, AWS, OIDC — plus JWT, LDAP, OCI, SPIFFE, TLS-cert, token auth per the backend service list ([README](https://github.com/Infisical/infisical/blob/main/README.md), [backend/src/services](https://github.com/Infisical/infisical/tree/main/backend/src/services)).

### 7. License precision (dual license, /ee boundary)

- **Root LICENSE**: MIT Expat for everything except "All content that resides under any 'ee/' directory of this repository… licensed under the license defined in 'ee/LICENSE'" ([LICENSE](https://github.com/Infisical/infisical/blob/main/LICENSE)).
- **ee license** (`backend/src/ee/LICENSE.md`, "Infisical Enterprise License"): production use only with a valid Enterprise subscription "for the correct number of user seats"; you may modify and publish patches, but Infisical retains title to modifications; **"you may copy and modify the Software for development and testing purposes, without requiring a subscription"**; otherwise copying/distributing/selling is forbidden ([ee LICENSE.md](https://github.com/Infisical/infisical/blob/main/backend/src/ee/LICENSE.md)).
- **What's inside `/ee` today** (`backend/src/ee/services`): `secret-approval-policy`/`secret-approval-request`, `access-approval-policy`/`access-approval-request`, `audit-log`, `audit-log-stream`, `pit` (point-in-time), `permission` (custom-role engine), `group`, `saml-config`, `scim`, `oidc`, `ldap-config`, `dynamic-secret`(+lease), `secret-rotation-v2`, `secret-replication`, `secret-scanning(-v2)`, `external-kms`, `hsm`, `kmip`, `gateway`/`gateway-v2`/`relay`, `trusted-ip` (IP allowlisting), `project-template`, `sub-org`, `github-org-sync`, `honey-token`, all `pam-*` services, `license`/`license-v2`, `rate-limit` ([ee services dir](https://github.com/Infisical/infisical/tree/main/backend/src/ee/services)).
- **Self-hosted free vs paid**: the self-hosted free version is the MIT core (projects/envs/folders, referencing/imports, overrides, CLI/agent/operator/SDK delivery, machine identities, built-in roles, validation rules); audit logs, PIT, approval workflows, custom roles, SAML/SCIM/LDAP, dynamic secrets, rotation etc. each state self-hosted use "requires an enterprise license (contact sales@infisical.com)" ([audit logs docs](https://infisical.com/docs/documentation/platform/audit-logs), [PIT docs](https://infisical.com/docs/documentation/platform/pit-recovery), [approval workflow docs](https://infisical.com/docs/documentation/platform/pr-workflows)). Self-hosted paid pricing is a separate (higher) rate card: Pro $25/id/mo, Advanced $50/id/mo, Enterprise ~$90–100/id/mo ([pricing](https://infisical.com/pricing)).
- **Tier drift over time (vendor-published evidence)**: Infisical's own pricing blog describes a former **Pro at $18/identity/mo including secret versioning, point-in-time recovery, RBAC, secret rotation, temporary access, SAML SSO and 90-day audit retention** ([Infisical blog: secrets manager pricing](https://infisical.com/blog/secrets-manager-pricing)); the current pricing page has a 4-tier Free/Pro($20)/Advanced($40)/Enterprise structure where **PIT and rotation moved up to Advanced, Pro's audit retention dropped to 30 days, and dynamic secrets + approval workflows sit at Enterprise** ([pricing](https://infisical.com/pricing)). The PIT docs still saying "Pro Tier" corroborates the recent upward move ([PIT docs](https://infisical.com/docs/documentation/platform/pit-recovery)). The README badge still advertises "license-MIT-blue" despite the dual license ([README](https://github.com/Infisical/infisical/blob/main/README.md)).

### 8. Architecture

- Monorepo monolith: `backend` (TypeScript — 37.5M bytes TS vs ~1M Go in the repo), `frontend`, `docs`, `helm-charts`, plus a newer `backend-go` directory; shipped as a single standalone Docker image (`Dockerfile.standalone-infisical`, incl. a FIPS variant) with `docker-compose.prod.yml` for local/self-host ([repo root](https://github.com/Infisical/infisical), [languages API](https://api.github.com/repos/Infisical/infisical/languages)).
- Storage: "Infisical's storage backend is PostgreSQL"; "Infisical uses Redis to enable more complex workflows including a queuing system," cron jobs and cache; components = REST API, Web UI, CLI, SDKs (Node, Python, Java, Go, Ruby, .NET), Kubernetes Operator, Agent ([docs: components](https://infisical.com/docs/internals/architecture/components)).
- Encryption: sensitive data encrypted server-side with AES-256-GCM (96-bit nonces) before hitting Postgres; the **root encryption key** is "a 256-bit AES key provided by the operator as an environment variable" that "never leaves the server's memory," optionally sourced from an HSM (Thales Luna, AWS CloudHSM); an auto-generated Internal KMS Root Key sits between the root key and **per-organization and per-project data keys** ("cryptographic isolation between tenants"); external cloud KMS integration uses envelope encryption of project keys ([docs: security](https://infisical.com/docs/internals/security), [docs: HSM](https://infisical.com/docs/documentation/platform/kms/hsm-integration), [docs: KMS](https://infisical.com/docs/documentation/platform/kms/overview)).
- Satellite components are Go: CLI ([Infisical/cli](https://github.com/Infisical/cli), language: Go), K8s operator ([Infisical/kubernetes-operator](https://github.com/Infisical/kubernetes-operator), Go), CSI provider ([Infisical/infisical-csi-provider](https://github.com/Infisical/infisical-csi-provider), Go). ClickHouse is an optional audit-log backend at scale ([docs: audit logs](https://infisical.com/docs/documentation/platform/audit-logs)).

### 9. Weaknesses vs a fully-OSS env-config manager (deterministic inheritance + schema + matrix UI + no paywall)

- **Production-table-stakes features are paywalled, and on self-host they're license-gated, not just cloud-gated**: audit logs (any retention) ([docs](https://infisical.com/docs/documentation/platform/audit-logs)), secret versioning (not in Free per pricing) ([pricing](https://infisical.com/pricing)), point-in-time rollback ([docs](https://infisical.com/docs/documentation/platform/pit-recovery)), approval workflows/change requests (Enterprise) ([docs](https://infisical.com/docs/documentation/platform/pr-workflows)), custom roles / per-env-per-path permissions ([docs](https://infisical.com/docs/documentation/platform/access-controls/role-based-access-controls)), SAML/SCIM/LDAP, dynamic secrets, rotation — all in `/ee` under a production-use-forbidden license ([ee services](https://github.com/Infisical/infisical/tree/main/backend/src/ee/services), [ee LICENSE](https://github.com/Infisical/infisical/blob/main/backend/src/ee/LICENSE.md)).
- **Environment count itself is metered** (3 on Free, 6 on Pro, 12 on Advanced) — a fully-OSS tool has no such cap ([pricing](https://infisical.com/pricing)).
- **No deterministic inheritance model**: there is no base-environment → child-environment cascade. Composition is done via secret imports with positional "bottom-most import wins" ordering ([docs](https://infisical.com/docs/documentation/platform/secret-reference)) — order-dependent per-folder wiring rather than a declared, project-wide inheritance graph; cross-project references aren't recursively expanded ([docs](https://infisical.com/docs/documentation/platform/secret-reference)), and keeping envs aligned is a manual visual diff in the Secrets Overview plus manual "Replicate Secrets" copying ([docs: folders](https://infisical.com/docs/documentation/platform/folder)).
- **No schema layer**: validation rules are per-secret write-time constraints (regex/length/prefix) ([docs](https://infisical.com/docs/documentation/platform/secret-validation-rules)); there is no notion of required keys per environment, typed values, or validation-before-delivery — a missing `prod` key surfaces only in the overview UI or at app runtime.
- **Rollback ergonomics**: single-secret rollback is literally copy-paste today ("automatic rollback… coming soon") ([docs](https://infisical.com/docs/documentation/platform/secret-versioning)), and real commit-based rollback is paid ([docs](https://infisical.com/docs/documentation/platform/pit-recovery)).
- **Tier instability risk**: features have demonstrably migrated upward (PIT and rotation from a $18 Pro to a $40 Advanced tier; Pro audit retention 90d → 30d) ([old vendor blog](https://infisical.com/blog/secrets-manager-pricing) vs [current pricing](https://infisical.com/pricing)), so building on a paid feature carries repricing risk; the "MIT" README badge understates the dual-license reality ([README](https://github.com/Infisical/infisical/blob/main/README.md)).
- Counterweight to be fair: the MIT core's delivery surface (CLI/agent/operator/CSI, machine identities incl. K8s TokenReview auth) and the free matrix-style Secrets Overview are strong and genuinely open ([components](https://infisical.com/docs/internals/architecture/components), [K8s auth](https://infisical.com/docs/documentation/platform/identities/kubernetes-auth)), and Secret Validation Rules living in the MIT tree is a notable recent exception to the paywall pattern ([backend/src/services](https://github.com/Infisical/infisical/tree/main/backend/src/services)).

## Phase

Primary-source survey of Phase (phase.dev / phasehq), captured 2026-07-29. Company: Phi Security Inc.

### 1. Environment model

- **Apps → Environments → Folders**: "A Phase App is used to manage Secrets for a single project, repository, or application," and "An App can contain multiple Environments" ([docs.phase.dev/console/apps](https://docs.phase.dev/console/apps)). Every app gets three default environments — "Development, Staging, Production" ([docs.phase.dev/console/environments](https://docs.phase.dev/console/environments)).
- **Custom environments are paywalled**: "The ability to create and manage custom environments is available for organizations with a `Phase Pro` or `Enterprise` tier subscription" ([docs.phase.dev/console/environments](https://docs.phase.dev/console/environments)). Free = 3 fixed envs; Pro = 10 custom; Enterprise = unlimited ([phase.dev/pricing](https://phase.dev/pricing)).
- **Secret referencing** (interpolation, not inheritance): `${KEY}` same-env root path; `${staging.DEBUG}` cross-environment; `${production./frontend/SECRET_KEY}` path-scoped; `${backend_api::production.SECRET_KEY}` cross-app. Unresolvable references (insufficient token access) are returned verbatim, unresolved ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)).
- **Personal overrides**: per-user secret value overrides — "the overridden value of the Secret will only be visible to you. When developing locally with the Phase CLI, the override value will be used by default," toggleable active/inactive ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)).
- **Folders/paths**: secrets can live under folder paths within an environment (evidenced by path-scoped reference syntax and the operator's `phaseAppEnvPath` field) ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets), [docs.phase.dev/integrations/platforms/kubernetes](https://docs.phase.dev/integrations/platforms/kubernetes)).
- **No side-by-side multi-environment editing**: the environments docs describe per-environment "cards" opened one at a time from a Secrets overview screen; no matrix/table view where secrets are compared or edited across environments in one grid is documented ([docs.phase.dev/console/environments](https://docs.phase.dev/console/environments)).

### 2. Schema / validation

- Secrets are opaque encrypted key/value strings with optional **comments and tags** (both saved only on "Deploy") ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)).
- A March 2026 release added "Secret Types with write-only secrets" ([phase.dev/changelog](https://phase.dev/changelog)) — a sensitivity/visibility classification, not a value-type system.
- **No typed values, no required-key declarations, no schema validation before delivery** appear anywhere in the console or CLI docs ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets), [docs.phase.dev/cli/commands](https://docs.phase.dev/cli/commands)). Validation is limited to reference resolution (which silently passes through unresolved references over the API).

### 3. Versioning & audit

- **Per-secret history**: "You can view the entire history of a Secret by hovering on the Secret row and clicking the 'History' button" — timeline with timestamps and authors; restoring sets the old value pending the next Deploy ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)). Secret versioning is on **all tiers**, including Free ([phase.dev/pricing](https://phase.dev/pricing)).
- **Point-in-time recovery (whole-environment rollback) is Pro+** — absent from Free ([phase.dev/pricing](https://phase.dev/pricing)).
- **Audit logs**: Free retains **24 hours**, Pro **90 days**, Enterprise **custom** retention ([phase.dev/pricing](https://phase.dev/pricing)). Org-wide audit log shipped June 2026 ([phase.dev/changelog](https://phase.dev/changelog)).

### 4. RBAC & reveal controls

- **Five managed roles**: Owner (org creator, all access), Admin (all but core org settings), Manager (broad but needs explicit App/Environment authorization), Developer (most restricted; explicit App+Environment assignment), Service (default for service accounts) ([docs.phase.dev/access-control/roles](https://docs.phase.dev/access-control/roles)).
- **Custom roles require "Pro or Enterprise tier subscription"**, with No/Read/Full/Custom access levels and per-CRUD-operation toggles ([docs.phase.dev/access-control/roles](https://docs.phase.dev/access-control/roles)). Pricing page words it as RBAC on Pro, "Custom Roles" on Enterprise ([phase.dev/pricing](https://phase.dev/pricing)).
- **Per-environment permissions**: access is granted per App and per Environment for Managers/Developers ([docs.phase.dev/access-control/roles](https://docs.phase.dev/access-control/roles)).
- **No hide-values ("reveal control") capability documented** — access control is grant/deny at environment level, not "can list but not read values" (closest is March 2026 write-only secret types, [phase.dev/changelog](https://phase.dev/changelog)). **No approval workflows**: none in the roles docs or pricing page; Phase's own AWS-comparison page listed change-approval as "planned… early Q1 2025" ([phase.dev/vs-aws-secrets-manager](https://phase.dev/vs-aws-secrets-manager/)), and as of 2026-07 it still does not appear in the access-control docs — apparently slipped/unshipped.
- Network access policies (IP restrictions) shipped May 2025 ([phase.dev/changelog](https://phase.dev/changelog)).

### 5. Delivery

- **CLI**: `phase run <cmd>` injects secrets as env vars; `phase shell` gives an ephemeral injected shell; `phase secrets export` emits dotenv/JSON/YAML; offline mode serves encrypted cached secrets with `PHASE_OFFLINE=1` ([docs.phase.dev/cli/commands](https://docs.phase.dev/cli/commands)).
- **Docker**: a native Docker integration is listed in docs navigation (CLI-in-image pattern) ([docs.phase.dev](https://docs.phase.dev/)).
- **Kubernetes**: own operator ([phasehq/kubernetes-secrets-operator](https://github.com/phasehq/kubernetes-secrets-operator), GPL-3.0), Helm-installed, `PhaseSecret` CRD (`phaseAppId`, `phaseAppEnv`, `phaseAppEnvPath`, `pollingInterval`, `managedSecretReferences`), authenticates via a `PHASE_SERVICE_TOKEN` k8s Secret, 60s default poll, auto-redeploy via `secrets.phase.dev/redeploy: 'true'` annotation ([docs.phase.dev/integrations/platforms/kubernetes](https://docs.phase.dev/integrations/platforms/kubernetes)). **No External Secrets Operator provider** — ESO is not mentioned anywhere in the Kubernetes docs ([docs.phase.dev/integrations/platforms/kubernetes](https://docs.phase.dev/integrations/platforms/kubernetes)).
- **Sync integrations**: GitHub Actions, GitHub Dependabot, GitHub Environments, Vercel, Railway ([docs.phase.dev/integrations/platforms/railway](https://docs.phase.dev/integrations/platforms/railway)), Render ([docs.phase.dev/integrations/platforms/render](https://docs.phase.dev/integrations/platforms/render)), Cloudflare Pages ([docs.phase.dev/integrations/platforms/cloudflare-pages](https://docs.phase.dev/integrations/platforms/cloudflare-pages)), Cloudflare Workers, AWS Secrets Manager, AWS ECS, Azure Key Vault ([docs.phase.dev/integrations/platforms/azure-key-vault](https://docs.phase.dev/integrations/platforms/azure-key-vault)), HashiCorp Vault ([docs.phase.dev/integrations/platforms/hashicorp-vault](https://docs.phase.dev/integrations/platforms/hashicorp-vault)), HashiCorp Nomad ([docs.phase.dev/integrations/platforms/hashicorp-nomad](https://docs.phase.dev/integrations/platforms/hashicorp-nomad)), Tailscale (July 2026) ([phase.dev/changelog](https://phase.dev/changelog)). Also Terraform provider, REST API, SDKs for Go/Node.js/Python ([github.com/phasehq/console README](https://github.com/phasehq/console)).
- **Key constraint**: syncs require opting the environment out of E2EE — see §7/§8.

### 6. CLI ergonomics

- Verbs: `phase auth` (webauth browser flow by default — encrypted X25519 keypair exchange, "no plaintext tokens transmitted" — plus token, AWS IAM, and Azure identity modes), `phase init` (writes `.phase.json` linking dir → app), `phase run`, `phase shell`, `phase secrets list/get/create/update/delete/import/export`, `phase dynamic-secrets list / lease generate|get|renew|revoke`, `phase apps list`, `phase users whoami/switch/logout/keyring`, `phase ai enable/disable/skill`, `phase console`, `phase docs`, `phase completion` ([docs.phase.dev/cli/commands](https://docs.phase.dev/cli/commands)).
- Headless auth: `PHASE_SERVICE_TOKEN` env var; service tokens follow the pattern `pss_service:v2:...` ([docs.phase.dev/cli/commands](https://docs.phase.dev/cli/commands)). Other env vars: `PHASE_HOST`, `PHASE_OFFLINE`, `PHASE_DEBUG`, `PHASE_VERIFY_SSL` ([docs.phase.dev/cli/commands](https://docs.phase.dev/cli/commands)).
- CLI was **rewritten from Python to Go in March 2026** ([phase.dev/changelog](https://phase.dev/changelog)).

### 7. License precision (verified from actual LICENSE files)

README states it verbatim: "available under the MIT expat license, with the exception of the `ee` directory which will contain Pro or Enterprise features requiring a Phase license" ([github.com/phasehq/console](https://github.com/phasehq/console)).

So the console is **open-core, not fully MIT**.

Also: "For references to resolve over the Public API or native integrations, all referenced apps must have SSE enabled… SSE is not required for references to resolve when using E2E enabled clients such as the CLI or SDKs" ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)). Net: the headline E2EE claim and the sync/REST-API feature set are mutually exclusive per environment.

### 8. Architecture

- **Components**: frontend React/Next.js/TypeScript; backend Python/Django; Docker/Kubernetes deployment with Helm chart ([github.com/phasehq/console README](https://github.com/phasehq/console)). Runtime dependencies from self-hosted config: **PostgreSQL** (`DATABASE_*` vars) and **Redis/Valkey** (`REDIS_*` vars), with distinct backend and worker containers sharing `SECRET_KEY`/`SERVER_SECRET` (32-byte hex each) ([docs.phase.dev/self-hosting/configuration/envars](https://docs.phase.dev/self-hosting/configuration/envars)).
- **Cryptography** (all libsodium primitives): not literal sealed boxes but the same construction — per-operation ephemeral Curve25519 keypair, X25519 exchange with recipient public key, XChaCha20-Poly1305 payload, output `Keph || Ciphertext || IV` ([docs.phase.dev/security/architecture](https://docs.phase.dev/security/architecture)).
- **Key hierarchy**: user mnemonic (BIP39, 24 words) → Account Seed via Argon2ID (1 GB mem, 4 iter, org-UUID salt) → Ed25519 signing + derived X25519 keypair, locally wrapped by a Device Key (Argon2ID of sudo password, 64 MB, 2 iter). Each **environment** has its own X25519 keypair from a random 32-byte seed plus a 32-byte salt for client-side key hashing. Access provisioning = "wrapped seeds": environment seed/salt encrypted to each member's public key, stored server-side as EnvironmentKey objects, decrypted client-side ([docs.phase.dev/security/architecture](https://docs.phase.dev/security/architecture)).
- Secret key/value/comment fields encrypted asymmetrically to the environment public key; decryption is client-side with the environment private key (except SSE environments, where the server holds capability to decrypt for syncs) ([docs.phase.dev/security/architecture](https://docs.phase.dev/security/architecture), [docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)).
- **Tokens**: PATs and service tokens use a split-key design — half embedded in the token string, half wrapped server-side; Lockbox sharing derives a keypair from a Box Seed carried only in the URL fragment ([docs.phase.dev/security/architecture](https://docs.phase.dev/security/architecture)).
- **No agent/sidecar daemon**; delivery is CLI-injection (Go), the k8s operator (poll-based), or server-side syncs. Languages: TypeScript (frontend), Python (backend), Go (CLI since 2026-03) ([github.com/phasehq/console](https://github.com/phasehq/console), [phase.dev/changelog](https://phase.dev/changelog)).

### 9. Weaknesses vs a fully-OSS env-config manager (deterministic inheritance + schema validation + matrix UI + no paywall)

- **Paywalled essentials**: custom environments (beyond dev/staging/prod) are Pro+ ([docs.phase.dev/console/environments](https://docs.phase.dev/console/environments)); PITR/rollback Pro+; audit retention beyond 24h Pro+; custom roles Pro+; >5 users / >3 apps Pro+ ([phase.dev/pricing](https://phase.dev/pricing)). These gates apply to self-hosted too via license activation ([docs.phase.dev/self-hosting/configuration/envars](https://docs.phase.dev/self-hosting/configuration/envars)). "Open source" here is open-core: MIT shell + commercial `ee/` ([raw ee/LICENSE](https://raw.githubusercontent.com/phasehq/console/main/backend/ee/LICENSE)).
- **No inheritance model**: environments are siblings; there is no base→env deterministic inheritance/override chain — only manual `${env.KEY}` string references, which fail *silently* (returned unresolved) when the token lacks access or SSE is off ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)). Personal overrides are the only layering primitive.
- **No schema layer**: no types, no required keys, no pre-delivery validation ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)) — a missing key is discovered at runtime.
- **No matrix UI**: per-environment cards only; no side-by-side cross-environment grid ([docs.phase.dev/console/environments](https://docs.phase.dev/console/environments)).
- **E2EE/feature tension**: any environment that needs syncs or the public API must drop to SSE, so the security headline and the automation feature set can't be held simultaneously ([docs.phase.dev/console/secrets](https://docs.phase.dev/console/secrets)).
- **Self-hosting friction**: Django backend + Next.js frontend + worker + Postgres + Redis + SMTP + TLS, with the operator polling rather than event-driven, and no ESO provider to slot into existing external-secrets setups ([docs.phase.dev/self-hosting/configuration/envars](https://docs.phase.dev/self-hosting/configuration/envars), [docs.phase.dev/integrations/platforms/kubernetes](https://docs.phase.dev/integrations/platforms/kubernetes)).
- **Governance maturity**: approval workflows were publicly "planned… early Q1 2025" and still aren't in the docs as of 2026-07 ([phase.dev/vs-aws-secrets-manager](https://phase.dev/vs-aws-secrets-manager/), [docs.phase.dev/access-control/roles](https://docs.phase.dev/access-control/roles)); the CLI was fully rewritten (Python→Go) in March 2026, signaling churn ([phase.dev/changelog](https://phase.dev/changelog)). Counterweights to note honestly: SOC 2 Type II (Feb 2026), external pentest (Nov 2025), dynamic secrets, rotation (Jul 2026) — the crypto design is the strongest part of the product ([phase.dev/changelog](https://phase.dev/changelog), [docs.phase.dev/security/architecture](https://docs.phase.dev/security/architecture)).

One correction to the task premise: phasehq/console is indeed MIT — but only outside `ee/`; the CLI and k8s operator are GPL-3.0, not MIT.

## HashiCorp Vault

### 1. Environment model
- Secrets live in **KV secret engines** (v1 unversioned, v2 versioned) mounted at arbitrary paths; secrets are "arbitrary static secrets" organized purely by path ([KV v2 docs](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2)). There is **no first-class "environment" concept** — environments are a path-naming convention (`secret/dev/...`, `secret/prod/...`); the docs describe only path organization, no environment semantics ([KV docs](https://developer.hashicorp.com/vault/docs/secrets/kv)).
- **Namespaces** ("mini-Vault instances" for tenant isolation, each with its own secret engines, auth methods, policies) require "Appropriate Vault Enterprise license or HCP Vault Dedicated cluster"; children can inherit policy/identity elements from parent namespaces — but this is tenant isolation, not env-config inheritance ([Namespaces docs](https://developer.hashicorp.com/vault/docs/enterprise/namespaces)).
- No mechanism for value inheritance/overrides between paths, and no side-by-side multi-environment editing in the UI — the UI edits one secret path at a time ([UI KV tutorial](https://developer.hashicorp.com/vault/tutorials/secrets-management/versioned-kv)).

### 2. Schema/validation
- KV is **schemaless**: values are arbitrary JSON key-value pairs; no typed values, required keys, or schema enforcement appear anywhere in the KV v2 docs or API ([KV v2 docs](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2), [KV v2 API](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2)). The closest validation primitives are policy-level `allowed_parameters`/`required_parameters` on writes ([Policies docs](https://developer.hashicorp.com/vault/docs/concepts/policies)).

### 3. Versioning & audit
- KV v2 keeps versions per key; "When 0 is used or the value is unset, Vault will keep 10 versions" (configurable via `max_versions`, oldest permanently deleted beyond the limit), with optional check-and-set (`cas`) writes ([KV v2 API](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2)).
- Rollback: `vault kv rollback` "restores a given previous version to the current version… if the current version is 5 and the rollback version is 2, the data from version 2 will become version 6" ([kv rollback](https://developer.hashicorp.com/vault/docs/commands/kv/rollback)). Soft delete / undelete / destroy are distinct operations ([KV v2 docs](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2)).
- **Audit devices** — `file`, `syslog`, `socket` — log every API request/response and are in the free/community edition ([Audit docs](https://developer.hashicorp.com/vault/docs/audit)); only advanced audit items sit behind Enterprise ([Enterprise docs](https://developer.hashicorp.com/vault/docs/enterprise)).

### 4. RBAC & reveal controls
- **Deny-by-default, path-based ACL policies** in HCL/JSON with capabilities `create/read/update/patch/delete/list/sudo/deny`, glob (`*`) and segment (`+`) wildcards, parameter constraints, and identity-templated paths ([Policies docs](https://developer.hashicorp.com/vault/docs/concepts/policies)).
- **Sentinel policies** (RGPs tied to tokens/entities/groups; EGPs tied to endpoints, incl. unauthenticated paths; advisory/soft/hard enforcement) are **Enterprise-only** ([Sentinel docs](https://developer.hashicorp.com/vault/docs/enterprise/sentinel)).
- **Control groups** (M-of-N approver authorization via response-wrapping tokens before a request is satisfied) are **Enterprise-only** ([Control groups docs](https://developer.hashicorp.com/vault/docs/enterprise/control-groups)).
- UI masks secret values by default; "click the sensitive information toggle" to reveal ([Versioned KV tutorial](https://developer.hashicorp.com/vault/tutorials/secrets-management/versioned-kv)).

### 5. Delivery
- **Vault Agent**: auto-auth + token renewal, Consul-Template rendering of secret-bearing config files "without requiring changes to your application", client-side caching, and process-supervisor mode injecting secrets as env vars into a child process ([Agent docs](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent)).
- **Kubernetes**: three official paths — Agent Injector sidecar, Vault Secrets Store CSI provider (mount as volumes), and the **Vault Secrets Operator** (syncs Vault secrets to k8s Secrets) ([Vault on Kubernetes](https://developer.hashicorp.com/vault/docs/platform/k8s)).
- **Docker Compose**: no first-class story — you compose it yourself from the CLI/Agent templating + env vars (agent process-supervisor mode is the documented mechanism, [Agent docs](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent)).

### 6. CLI ergonomics
- `vault kv get/put`, `vault login`, `vault server`, `vault operator …`; pluggable auth methods (token, OIDC, userpass, k8s, AppRole, …) behind `vault login` ([CLI commands docs](https://developer.hashicorp.com/vault/docs/commands)). Mature but verb-heavy; every read is an authenticated API call against a running server.

### 7. LICENSE PRECISION
- **BUSL 1.1** since the announcement of **August 10, 2023**: "all future releases" of HashiCorp products moved to BSL 1.1; use is free "except where providing a competitive offering to HashiCorp"; APIs/SDKs stayed MPL 2.0 ([HashiCorp announcement](https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license)).
- Current LICENSE file: "Business Source License 1.1", licensor **International Business Machines Corporation** (post-acquisition), Change Date "Four years from the date the Licensed Work is published", Change License **MPL 2.0**, production use allowed unless "offering the Licensed Work to third parties on a hosted or embedded basis in order to compete with IBM Corp's paid version(s)" ([LICENSE](https://github.com/hashicorp/vault/blob/main/LICENSE)).
- **Enterprise-gated features** (from the Enterprise docs index): namespaces, replication (perf + DR), performance standbys, HSM support/PKCS#11, FIPS, seal wrap, entropy augmentation, Sentinel/policy-as-code, control groups, multi-factor authN (identity/step-up), lease count quotas, redundancy zones, automated upgrades, Secrets Sync, Secrets Import, SCIM ([Enterprise docs](https://developer.hashicorp.com/vault/docs/enterprise)). Commercial plans: PAYG / Flex / Enterprise Self-Managed via sales ([pricing page](https://www.hashicorp.com/en/products/vault/pricing)).

### 8. Architecture
- Single Go binary (`vault server`); data passes a **security barrier** that encrypts everything before it reaches the storage backend, so "if a malicious attacker attempts to gain access to the storage backend, the data cannot be compromised" ([Architecture docs](https://developer.hashicorp.com/vault/docs/internals/architecture)).
- Starts **sealed**; default unseal is **Shamir key shares** with a threshold reconstructing the root key; **auto-unseal** via cloud KMS/HSM is available in community, while **Seal HA** is Enterprise ([Seal docs](https://developer.hashicorp.com/vault/docs/concepts/seal)).
- Integrated **Raft** storage is the recommended backend; HA is active-node + standbys; leases auto-revoke expired credentials ([Architecture docs](https://developer.hashicorp.com/vault/docs/internals/architecture), [Vault on k8s HA](https://developer.hashicorp.com/vault/docs/platform/k8s)).

### 9. Weaknesses vs a fully-OSS env-config manager
- Heavy operational footprint: run/seal/unseal/upgrade a stateful HA server before storing the first value ([Seal docs](https://developer.hashicorp.com/vault/docs/concepts/seal)).
- Zero environment semantics: no inheritance, no diffing dev/staging/prod, no schema, no matrix UI — environments are naming discipline ([KV v2 docs](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2)).
- The multi-tenant/isolation answer (namespaces), fine-grained approvals, and rule-based policies are paywalled ([Enterprise docs](https://developer.hashicorp.com/vault/docs/enterprise)).
- BUSL 1.1 forbids competitive hosted/embedded offerings and makes downstream redistribution legally fraught ([LICENSE](https://github.com/hashicorp/vault/blob/main/LICENSE)).

## OpenBao

### 1. Environment model
- Same path-based KV v1/v2 model as Vault (API-compatible fork), same absence of a first-class environment concept ([What is OpenBao](https://openbao.org/docs/what-is-openbao/), [migration guide](https://openbao.org/docs/guides/migration/)).
- **Namespaces are free and open source**: announced May 30, 2025 (beta v2.3.0-beta20250528) and shipped in the 2.3.x line — "logical partitions within a single OpenBao instance", "application API compatible with upstream's [Vault Enterprise] implementation", with hierarchical CRUD, per-namespace engines/auth/policies/tokens, routing via path or `X-Vault-Namespace` header, and `bao namespace` CLI ([namespaces announcement](https://openbao.org/blog/namespaces-announcement/), [2.3.x release notes](https://openbao.org/community/release-notes/2-3-0/)). 2.6.0 added **namespace sealing** (per-tenant key material, tenant-revocable) ([2.6.0 release notes](https://openbao.org/community/release-notes/2-6-0/)).
- Still no inheritance mechanism between paths/namespaces for config values and no multi-env matrix editing; the Web UI itself was only reintroduced in 2.2.x ([2.2.0 release notes](https://openbao.org/community/release-notes/2-2-0/)).

### 2. Schema/validation
- KV remains schemaless key-value, as in Vault ([What is OpenBao](https://openbao.org/docs/what-is-openbao/)). OpenBao's validation investments target certificates/auth, not KV: **CEL (Common Expression Language)** policies for PKI and JWT auth landed in 2.3.x ([2.3.x release notes](https://openbao.org/community/release-notes/2-3-0/)).

### 3. Versioning & audit
- KV v2 versioning/rollback identical to upstream (API-compatible fork of the MPL-licensed 1.14.x branch) ([migration guide](https://openbao.org/docs/guides/migration/)). Audit devices are free; 2.3.2 hardened audit-device creation controls among CVE fixes ([2.3.x release notes](https://openbao.org/community/release-notes/2-3-0/)).

### 4. RBAC & reveal controls
- Same HCL path/capability ACL model and `bao`-side policy commands; 2.6.0 added PATCH support for policy modification ([2.6.0 release notes](https://openbao.org/community/release-notes/2-6-0/)). No Sentinel (proprietary); CEL is the emerging expression-policy substitute in PKI/JWT ([2.3.x release notes](https://openbao.org/community/release-notes/2-3-0/)). No control-group equivalent documented. UI (2.2.x+) inherits Vault's masked-value viewing pattern ([2.2.0 release notes](https://openbao.org/community/release-notes/2-2-0/)).

### 5. Delivery
- **OpenBao Agent** exists with full parity: auto-auth + renewal, template rendering, response caching, and process-supervisor mode injecting "OpenBao secrets injected as environment variables" ([Agent docs](https://openbao.org/docs/agent-and-proxy/agent/)).
- **Kubernetes**: official Helm chart (dev/standalone/HA), **Agent Injector** ("more mature solution, with proven production record"), and a **CSI provider** on the vendor-neutral secrets-store CSI driver. **No official secrets operator** is documented — the operator gap vs Vault's VSO ([OpenBao on Kubernetes](https://openbao.org/docs/platform/k8s/)).
- Docker Compose story: same as Vault — CLI/Agent + env templating, nothing first-class ([Agent docs](https://openbao.org/docs/agent-and-proxy/agent/)).

### 6. CLI ergonomics
- `bao` mirrors `vault`: `bao kv get/put`, `bao login`, `bao server`, `bao operator`, `bao namespace`; env vars use `BAO_ADDR`/`BAO_TOKEN`/`BAO_NAMESPACE` and "will fall back to `VAULT_` if present" for drop-in compatibility ([CLI docs](https://openbao.org/docs/commands/)).

### 7. LICENSE PRECISION
- **MPL 2.0** — the LICENSE file is the Mozilla Public License, version 2.0 ([LICENSE](https://github.com/openbao/openbao/blob/main/LICENSE)).
- Forked from Vault's **1.14.x branch, the last MPL 2.0 stream** (last MPL point release v1.14.8; later 1.14.x releases were BUSL) ([openbao issue #282](https://github.com/openbao/openbao/issues/282), [migration guide](https://openbao.org/docs/guides/migration/)).
- Governance: Linux Foundation ("LF Projects, LLC"), currently an **OpenSSF Sandbox project** ([What is OpenBao](https://openbao.org/docs/what-is-openbao/)); it entered the LF via **LF Edge**, announced as one of four new LF Edge projects on April 30, 2024 ([Linux Foundation press release](https://www.linuxfoundation.org/press/open-edge-computing-hits-critical-mass-as-lf-edge-expands-technical-reach-with-4-new-projects-1)).
- **Removed vs Vault**: Enterprise-only stubs (cross-cluster/unified CRL), mlock, legacy transit key formats, and poorly maintained storage backends were dropped early ([2.0.0 release notes](https://openbao.org/community/release-notes/2-0-0/)); no Sentinel, no enterprise replication.
- **Added vs Vault** (release cadence roughly two majors/year): 2.0 GA Jul 16, 2024 — paginated LIST, transit XChaCha20-Poly1305/soft-delete, token IP-binding ([2.0.0](https://openbao.org/community/release-notes/2-0-0/)); 2.1 Nov 29, 2024 — **transactional storage**, PostgreSQL backend reintroduced, OIDC device flow ([2.1.0](https://openbao.org/community/release-notes/2-1-0/), [LF Edge announcement](https://lfedge.org/announcing-openbao-v2-1-0-transactional-storage-postgresql-and-more/)); 2.2 Mar 5, 2025 — **ACME client for the server's own TLS listener certs**, PKCS#11 auto-unseal, Web UI back, recursive scan ([2.2.0](https://openbao.org/community/release-notes/2-2-0/)); 2.3.x (mid-2025, latest 2.3.2 Aug 7, 2025) — **namespaces**, CEL for PKI/JWT, KMIP auto-unseal ([2.3.x](https://openbao.org/community/release-notes/2-3-0/)); 2.6.0 Jul 14, 2026 — namespace sealing, KMS seal plugins, workflows endpoints, distroless images ([2.6.0](https://openbao.org/community/release-notes/2-6-0/)).

### 8. Architecture
- Same Go single-binary, barrier-encrypted, seal/unseal architecture inherited from Vault 1.14 ([What is OpenBao](https://openbao.org/docs/what-is-openbao/)); Raft integrated storage plus a transactional PostgreSQL backend ([storage docs](https://openbao.org/docs/configuration/storage/), [2.1.0](https://openbao.org/community/release-notes/2-1-0/)); Shamir plus a broader free auto-unseal menu (PKCS#11, KMIP, cloud KMS — cloud seals moving to external plugins in 2.7) ([2.2.0](https://openbao.org/community/release-notes/2-2-0/), [2.6.0](https://openbao.org/community/release-notes/2-6-0/)); Raft non-voter nodes since 2.2 ([2.2.0](https://openbao.org/community/release-notes/2-2-0/)).

### 9. Weaknesses vs a fully-OSS env-config manager
- Inherits all of Vault's operational weight (sealed server, unseal ceremony, HA cluster) and all of its missing environment semantics — namespaces are tenant isolation, not env inheritance or schema ([namespaces announcement](https://openbao.org/blog/namespaces-announcement/)).
- Ecosystem gaps: no official secrets operator ([k8s docs](https://openbao.org/docs/platform/k8s/)), Web UI only restored in 2.2 and still trailing ([2.2.0](https://openbao.org/community/release-notes/2-2-0/)), smaller plugin/integration surface than Vault's commercial ecosystem, and a young governance track (OpenSSF Sandbox) ([What is OpenBao](https://openbao.org/docs/what-is-openbao/)).
- Upside vs Vault: everything is MPL 2.0 with no paywalled tier — namespaces, HSM auto-unseal, and audit are free ([LICENSE](https://github.com/openbao/openbao/blob/main/LICENSE), [2.3.x](https://openbao.org/community/release-notes/2-3-0/)).

## License-capture case study: BUSL → OpenBao timeline
- **2023-08-10** — HashiCorp announces all future product releases (incl. Vault) move MPL 2.0 → **BUSL 1.1**, with a "competitive offering" restriction; existing releases stay MPL ([announcement](https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license)).
- **Late 2023** — fork work begins publicly in the openbao GitHub org against Vault's last-MPL 1.14.x stream ([openbao issue #1 "Fork Hashicorp Vault"](https://github.com/openbao/openbao/issues/1), [issue #282 on fork base](https://github.com/openbao/openbao/issues/282)).
- **2024-04-30** — Linux Foundation formally announces OpenBao as one of four new **LF Edge** projects ([LF press release](https://www.linuxfoundation.org/press/open-edge-computing-hits-critical-mass-as-lf-edge-expands-technical-reach-with-4-new-projects-1)).
- **2024-07-16** — OpenBao **2.0 GA**, first stable independent release ([2.0.0 release notes](https://openbao.org/community/release-notes/2-0-0/)).
- **2025** — OpenBao ships formerly Enterprise-gated capability (namespaces, 2.3.x) for free ([namespaces announcement](https://openbao.org/blog/namespaces-announcement/)); Vault's licensor is now **IBM** per the LICENSE file, Change License MPL 2.0 after four years per released version ([Vault LICENSE](https://github.com/hashicorp/vault/blob/main/LICENSE)).
- Pattern: relicense → community fork of last-open branch → foundation governance → fork re-implements paywalled features in the open — the same BUSL-capture arc as Terraform/OpenTofu, and the standing argument against building on BUSL-licensed infrastructure.

## SOPS + age

### 1. Environment model
SOPS is "an editor of encrypted files that supports YAML, JSON, ENV, INI and BINARY formats and encrypts with AWS KMS, GCP KMS, Azure Key Vault, HuaweiCloud KMS, age, and PGP" ([getsops/sops README](https://github.com/getsops/sops)) — it operates on files, with no tool-level environment concept; environments are a file/path convention (e.g. `*.dev.yaml` vs prod paths). Per-environment key targeting is done in `.sops.yaml` `creation_rules`: "creation rules are evaluated sequentially, the first match wins"; the docs' example shows that "upon creation of a file that matches the pattern `*.dev.yaml`, KMS set A as well as PGP and age is used" while "prod files use KMS set B in the PROD IAM, PGP and age". SOPS "recursively look[s] for a `.sops.yaml` file" and "the filename of the file being created is compared with the filename regexes" ([README §Using .sops.yaml conf](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). There is no inheritance between files/rules and no UI anywhere — the entire documented surface is the CLI and config file ([getsops.io/docs](https://getsops.io/docs/)).

### 2. Schema/validation
None. SOPS encrypts leaf values in structured files; there is no type system or validation of values — the docs describe only encryption/decryption of file contents, nothing about schemas ([getsops.io/docs](https://getsops.io/docs/), [README](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).

### 3. Versioning & audit
Version history is whatever git provides — encrypted files are committed; SOPS keeps "keys … in cleartext" because that "allows for better diff and overall readability" ([README §Encryption Protocol](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). SOPS has one built-in audit feature: it can "write a log entry into a pre-configured PostgreSQL database when a file is decrypted", configured via `/etc/sops/audit.yaml`; the documentation carries no deprecation notice for it as of v3.9+ ([README §Auditing](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). No rollback mechanism beyond `git revert` exists in the tool itself.

### 4. RBAC & reveal controls
Access = key possession: any master key listed on a file (age identity, KMS grant, PGP key) can decrypt the entire file's data key, hence every value in the file ([README §Encryption Protocol](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). Finer granularity is limited to *which values get encrypted*: `--encrypted-regex` "will only encrypt values under keys that match the supplied regular expression", plus `--unencrypted-regex`, `_unencrypted`/`encrypted` suffixes ("all values underneath the key that set the `_unencrypted` suffix will be left in cleartext"), and `--encrypted-comment-regex` for YAML ([README §Encrypting only parts of a file](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). Key groups + "Shamir's Secret Sharing to split the data key such that each key group has a fragment" with a configurable threshold can require multiple parties to decrypt ([README §Key groups](https://github.com/getsops/sops/blob/v3.9.0/README.rst)) — but there is no per-key RBAC and no reveal masking.

### 5. Delivery
- **Processes/Compose**: `sops exec-env` and `sops exec-file` "place all output into the environment of a child process and into a temporary file, respectively" (FIFO by default, no plaintext on disk), and `sops -d` decrypts to stdout for piping into `docker compose` ([README §Passing secrets to other processes](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).
- **Kubernetes/Flux**: the Flux kustomize-controller decrypts in-cluster — `Kustomization` sets `spec.decryption: provider: sops` with a `secretRef` holding keys; for age, "the key name must end with `.agekey` to be detected as an age key"; encrypted manifests stay in git, decryption happens at reconcile ([fluxcd.io SOPS guide](https://fluxcd.io/flux/guides/mozilla-sops/)).
- **sops-secrets-operator** (isindir): "manages Kubernetes Secret Resources created from user defined SopsSecrets CRs", decrypting sops data into native Secrets for GitOps; supports AWS/GCP KMS, Azure KV, PGP, age; MPL-2.0 ([isindir/sops-secrets-operator](https://github.com/isindir/sops-secrets-operator)).
- **helm-secrets**: "a Helm plugin to decrypt encrypted Helm value files on the fly" during install/upgrade, via `secrets://` protocol or `helm secrets` wrapper; sops backend plus vals; Apache-2.0 ([jkroepke/helm-secrets](https://github.com/jkroepke/helm-secrets)).

### 6. CLI ergonomics
v3.9.0 added "separate subcommands for encryption, decryption, rotating, editing, and setting values" (`sops encrypt/decrypt/edit/rotate/set`), plus `filestatus` and `unset` ([v3.9.0 release notes](https://github.com/getsops/sops/releases/tag/v3.9.0)). `sops updatekeys` "uses the `.sops.yaml` configuration file to update (add or remove) the corresponding secrets in the encrypted file" after recipient changes ([README §updatekeys](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). age keys are found in `keys.txt` in the sops user config dir (Linux `$HOME/.config/sops/age/keys.txt`), or via `SOPS_AGE_KEY_FILE` / `SOPS_AGE_KEY` ([README §Encrypting using age](https://github.com/getsops/sops/blob/v3.9.0/README.rst)). Key generation: `age-keygen -o key.txt` prints the `age1...` public key; `-pq` for post-quantum ([FiloSottile/age README](https://github.com/FiloSottile/age)).

### 7. License & governance
SOPS `LICENSE` is "Mozilla Public License Version 2.0" ([getsops/sops LICENSE](https://github.com/getsops/sops/blob/main/LICENSE)). "SOPS was accepted to CNCF on May 17, 2023 at the Sandbox maturity level" — still Sandbox, not incubating ([cncf.io/projects/sops](https://www.cncf.io/projects/sops/)). It was "initially launched as a project at Mozilla in 2015" and "graciously donated to the CNCF as a Sandbox project in 2023, now under the stewardship of a new group of maintainers" in the getsops org ([getsops/sops README](https://github.com/getsops/sops)). age is BSD-3-Clause ("Neither the name of the age project…") ([age LICENSE](https://github.com/FiloSottile/age/blob/main/LICENSE)). Everything is open source; nothing paywalled.

### 8. Architecture
Stateless Go CLI, no server. Envelope encryption: "When SOPS creates a file, it generates a random 256 bit data key and asks each KMS and PGP master key to encrypt the data key" — one encrypted copy of the data key per recipient (age, AWS KMS, GCP KMS, Azure KV, PGP, Vault); each leaf value is encrypted "with AES256_GCM using the data key and a 256 bit random initialization vector"; integrity: "SOPS computes a MAC on all the values to ensure that no value has been added or removed fraudulently. The MAC is stored encrypted with AES_GCM." Key names are AEAD additional data and stay cleartext ([README §Encryption Protocol](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).

### 9. Weaknesses vs a fully-OSS env-config manager
- **Rotation/team-change toil**: adding/removing a teammate means editing `.sops.yaml` then running `sops updatekeys` on *every* affected file, re-encrypting the data key ([README §updatekeys](https://github.com/getsops/sops/blob/v3.9.0/README.rst)); a departed keyholder retains git history they could still decrypt unless values are rotated too.
- **No environment matrix/diffing**: environments are filename conventions; nothing compares dev vs prod key sets or flags drift ([README](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).
- **Merge conflicts**: encrypted values + per-file MAC make conflicting edits to the same file effectively un-mergeable without decrypt-merge-re-encrypt (MAC covers all values, so partial textual merges break the file) ([README §Encryption Protocol](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).
- **No read audit by default**: the only audit is the optional PostgreSQL decrypt log requiring server-side setup on every machine ([README §Auditing](https://github.com/getsops/sops/blob/v3.9.0/README.rst)); a copied age key file decrypts silently forever.
- **Secret sprawl**: secrets live per-repo in files; no central inventory, no per-key access, no UI, onboarding requires distributing age keys or cloud-KMS IAM out of band ([README §Encrypting using age](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).

## External Secrets Operator (ESO)

### 1. Role
ESO is delivery/sync, not storage: "External Secrets Operator is a Kubernetes operator that integrates external secret management systems like AWS Secrets Manager, HashiCorp Vault, Google Secrets Manager, Azure Key Vault and many more" and "automatically injects the values into a Kubernetes Secret" ([external-secrets README](https://github.com/external-secrets/external-secrets), [external-secrets.io](https://external-secrets.io/latest/)). CRDs: **SecretStore** (namespaced, "separate[s] concerns of authentication/access" — provider credentials/config), **ClusterSecretStore** ("a global, cluster-wide SecretStore that can be referenced from all namespaces"), **ExternalSecret** ("declares what data to fetch"; the controller uses it "as a blueprint to create secrets"), plus **ClusterExternalSecret**, **PushSecret**/**ClusterPushSecret** for cluster-scope and write-back ([overview docs](https://external-secrets.io/latest/introduction/overview/)). ESO has no environment concept of its own — environments are whatever paths/projects the backing store models — and no UI.

### 2. Schema/validation
No schema validation of secret values. Transformation only: `spec.target.template` where "each data value is interpreted as a Go template" (engineVersion v2, 200+ sprig functions, `templateFrom` ConfigMaps/Secrets, `templateAs: Values|KeysAndValues|Literal`); the only strictness is that "referencing a non-existing key in the template will raise an error" ([templating guide](https://external-secrets.io/latest/guides/templating/)). `dataFrom.extract`/`find` pull multiple properties; `decodingStrategy` (`None` default, `Base64`, `Base64URL`, `Auto`) decodes values, with the caveat that with `Auto` "some non-encoded secret values might end up being decoded, producing gibberish" ([decoding strategy guide](https://external-secrets.io/latest/guides/decoding-strategy/)).

### 3. Versioning/audit
None of its own — versioning/audit are delegated to the provider. ESO's contribution is sync: the controller "ensure[s] that the secret values stay in sync with the external API" on a per-resource `refreshInterval` ([overview docs](https://external-secrets.io/latest/introduction/overview/)).

### 4. RBAC
Standard Kubernetes RBAC over the CRDs; the SecretStore/ExternalSecret split exists so cluster admins own provider credentials while namespace users only declare what to fetch ([overview docs](https://external-secrets.io/latest/introduction/overview/)). No secret-level RBAC beyond what K8s and the provider give.

### 5. Delivery
Delivery *is* the product — external store → K8s `Secret`. 40+ providers are listed on the docs front page, including HashiCorp Vault, Doppler, **Infisical**, 1Password (Connect + SDK), Bitwarden Secrets Manager, AWS (Secrets Manager/Parameter Store), Google Cloud Secret Manager, Azure Key Vault, Akeyless, Pulumi ESC; **Phase does not appear** in the provider list ([external-secrets.io provider table](https://external-secrets.io/latest/)). No Docker Compose story — it only produces Kubernetes Secrets.

### 6. CLI
None — interaction is `kubectl` + YAML CRDs; a standalone CLI exists only as an open feature request ([issue #5530](https://github.com/external-secrets/external-secrets/issues/5530)). Maintenance/stability: only "the most-up-to date, current minor version" is supported, previous minors go EOL on each release (~3-week cadence in 2026, e.g. v2.7 for K8s 1.35 released Jun 26 2026), support is "on a best-effort basis" and maintainers "kindly ask for patience when asking for support" ([stability & support policy](https://external-secrets.io/latest/introduction/stability-support/)).

### 7. License, CNCF status, 2025 maintainer crisis
Apache-2.0 ([external-secrets repo](https://github.com/external-secrets/external-secrets)). "external-secrets was accepted to CNCF on July 26, 2022 at the Sandbox maturity level" — still Sandbox as of 2026-07, with an incubation application pending ([cncf.io/projects/external-secrets](https://www.cncf.io/projects/external-secrets/), [cncf/toc#1486 via toc#1819](https://github.com/cncf/toc/issues/1819)). The maintainer crisis is primary-sourced: "Health of External Secrets project" opened 2025-07-30 — "Our only active maintainer these days is @Skarlso … which is a bad sign"; "We've decided to stop releases until more long-term maintainers join our team" ([issue #5084](https://github.com/external-secrets/external-secrets/issues/5084)); CNCF TOC filed a formal health issue on 2025-08-13 quoting the "difficult decision to pause all official SemVer releases … until we can form a larger, sustainable maintainer team" ([cncf/toc#1819](https://github.com/cncf/toc/issues/1819)). Outcome: contribution ladder + interim maintainers were instituted, maintainers "voted continuing releases" with a first tentative date of Sept 22 2025, and the issue is closed; the 2026 release cadence on the support page confirms releases resumed ([issue #5084](https://github.com/external-secrets/external-secrets/issues/5084), [stability page](https://external-secrets.io/latest/introduction/stability-support/)). Directly relevant to any maintenance-burden analysis: a single-vendor dependency on ESO carried real bus-factor risk within the last year.

### 8. Architecture
Go controller/operator, CRD-driven, three components: the **core controller** (reconciles ExternalSecrets: finds the SecretStore, instantiates a provider API client, fetches values, writes the Secret); a **webhook** "to convert custom resources between api versions and to provide a ValidatingWebhook for the `ExternalSecret` and `SecretStore` resources"; and a **cert-controller** that generates the webhook's TLS credentials and "injects the certificate as `caBundle`" into CRDs and the ValidatingWebhookConfiguration — webhook/cert-controller are "optional but highly recommended" ([components docs](https://external-secrets.io/latest/api/components/), [overview docs](https://external-secrets.io/latest/introduction/overview/)).

### 9. Weaknesses
- **Kubernetes-only**: output is a K8s `Secret`; nothing for Compose, bare VMs, or CI outside a cluster ([overview docs](https://external-secrets.io/latest/introduction/overview/)).
- **Not a store**: you still need Vault/Infisical/a cloud secrets manager behind it — ESO adds sync, not storage, editing, versioning, or audit ([README](https://github.com/external-secrets/external-secrets)).
- **Another moving piece**: controller + webhook + cert-controller to deploy, upgrade on a fast single-supported-minor treadmill, and monitor ([components](https://external-secrets.io/latest/api/components/), [support policy](https://external-secrets.io/latest/introduction/stability-support/)).
- **No editing UX**: no UI, no CLI; all authoring is YAML against CRDs, and value editing happens in the backing store's tooling ([issue #5530](https://github.com/external-secrets/external-secrets/issues/5530)).
- **Governance risk**: Sandbox-level project that paused releases in 2025 for lack of maintainers ([cncf/toc#1819](https://github.com/cncf/toc/issues/1819)).

Sourcing notes: all claims above are from project-owned sources (getsops/sops repo + getsops.io, FiloSottile/age repo, fluxcd.io, isindir/sops-secrets-operator, jkroepke/helm-secrets, external-secrets.io + external-secrets repo, cncf.io, cncf/toc). One gap: SOPS's detailed reference now lives at getsops.io/docs but is split across subpages; I cited the identical content at the project's own v3.9.0 README ([github.com/getsops/sops/blob/v3.9.0/README.rst](https://github.com/getsops/sops/blob/v3.9.0/README.rst)), which is the last full in-repo reference. "Phase" has no ESO provider as of today's provider table — worth rechecking if the survey ships later.

## Doppler (closed SaaS — UX reference)

### 1. Environment model (the UX benchmark)

- **Hierarchy: workplace → projects → environments → configs.** "A project in Doppler is where you define the app config and secrets for a single service or application"; each project ships with three default environments — Development, Staging, Production — and custom environments can be added and drag-reordered ([docs.doppler.com/docs/create-project](https://docs.doppler.com/docs/create-project), [docs.doppler.com/docs/default-environments](https://docs.doppler.com/docs/default-environments)).
- **Root configs:** each environment has one root config (`dev`, `stg`, `prd`) holding "a master list of secrets for that environment" — "the master branch or root config for their respective environments, where all future configs branch off of" ([docs.doppler.com/docs/root-configs](https://docs.doppler.com/docs/root-configs)).
- **Branch configs (the killer feature):** "Each environment may optionally have branch configs, which allow overrides from the root config for that environment." Root updates auto-propagate to all branches; a branch's local override of a specific secret takes precedence over the inherited root value. Duplicating a config creates a new branch off the same root, carrying the source's overrides. Use cases: per-cloud deployments (AWS/GCP/Azure branch of `prd`), unreleased-feature secrets, promotion of branch values back to root ([docs.doppler.com/docs/branch-configs](https://docs.doppler.com/docs/branch-configs)).
- **Personal configs:** auto-generated private branch per developer — "every user that has write access to the environment [gets] their own branch config that only they can access" ([docs.doppler.com/docs/branch-configs](https://docs.doppler.com/docs/branch-configs)).
- **Config inheritance (separate, config-level mechanism):** a config can inherit entire other configs, including cross-project ("configs inside the project will still be able to inherit from other configs outside the project"); with multiple parents "the topmost config will always take precedence," own secrets override all inherited, order is user-reorderable. Team/Enterprise only ([docs.doppler.com/docs/config-inheritance](https://docs.doppler.com/docs/config-inheritance)).
- **Secret referencing:** inline `${SECRET_NAME}` interpolation (e.g. `${USER}.doppler.com:${PORT}`); cross-config `${config.SECRET_NAME}`; cross-project `${project.config.SECRET_NAME}` (paid plans). "Secret references are resolved at read-time"; a dangling reference is left as the literal string. Referencing can be disabled globally, per-project, or per-config ([docs.doppler.com/docs/secrets](https://docs.doppler.com/docs/secrets)).
- **Multi-environment editing — mirror, not side-by-side compare:** no dedicated side-by-side diff view in the docs. Instead, "when adding or updating a secret, you're able to mirror the change to any of the other environments inside the project," and **missing secret detection** flags (red "Action Required" indicators) secrets present in one environment but absent in others. Cascading changes apply only the modified properties (e.g. mirroring a visibility change to `prd` leaves `prd`'s value untouched) ([docs.doppler.com/docs/root-configs](https://docs.doppler.com/docs/root-configs), [docs.doppler.com/docs/secrets](https://docs.doppler.com/docs/secrets)).

### 2. Schema / validation

- **Value types with enforcement:** secrets can be typed and value-validated — structural (`json`, `json5`, `xml`, `yaml`), identifiers (`uuid`, `ulid`, `cuid2`), temporal (`date`, `datetime` ISO 8601 UTC), numeric (`integer`, `decimal`), text (`string`, `email`, `url`, `boolean`), plus `directReference` for cross-config refs ([docs.doppler.com/docs/secrets](https://docs.doppler.com/docs/secrets)).
- **Visibility as an attribute per secret:** Unmasked ("always displayed"), Masked (shows `****`, reveal on click), Restricted ("not viewable in the dashboard after it is saved," "retrievable only via non-user tokens (e.g. a service token)") ([docs.doppler.com/docs/secret-visibility](https://docs.doppler.com/docs/secret-visibility)).
- **No hard "required secrets" schema** — the closest is missing-secret detection warnings across environments, which alert rather than block ([docs.doppler.com/docs/root-configs](https://docs.doppler.com/docs/root-configs)).

### 3. Versioning & audit

- **Per-secret version history:** "Every version of a secret is retained for the lifetime of that secret"; viewable via "Secret History" per row; individual historical versions can be permanently redacted (current version cannot be); clearing history requires delete + recreate ([docs.doppler.com/docs/versioning](https://docs.doppler.com/docs/versioning)).
- **Config-level activity log with rollback:** every change (rename, token creation, secret edits) appears in a "commit style log which can be rolled back at any time" ([docs.doppler.com/docs/versioning](https://docs.doppler.com/docs/versioning), [docs.doppler.com/docs/workplace-logs](https://docs.doppler.com/docs/workplace-logs)).
- **Retention by tier:** activity logs — Developer 3 days, Team 90 days, Enterprise custom ([doppler.com/pricing](https://www.doppler.com/pricing)).

### 4. RBAC & reveal controls

- **Project roles:** Admin / Collaborator (manage secrets, trusted IPs, service tokens; can't rename or delete configs) / Viewer / None; workplace Owner/Admin always get project Admin. Grants are per-environment and **per-config** ("configure what role they'll have on the project and which configs they'll have access to"). "Role based access is available with our Team and Enterprise plans" ([docs.doppler.com/docs/project-permissions](https://docs.doppler.com/docs/project-permissions)).
- **Restricted visibility as a reveal control:** hides values but keeps names/usable via service tokens — with the caveat that anyone who can mint a service token can still read restricted values programmatically ([docs.doppler.com/docs/secret-visibility](https://docs.doppler.com/docs/secret-visibility)).
- **Change requests (Team/Enterprise; "Change Request Policies" on Enterprise):** "workflow-driven mechanism for proposing additions, modifications, or deletions"; users with only read visibility can propose; reviewers with an "Approve Change Requests" permission approve diff-formatted changes; statuses Draft → In Review → Approved → Merged; merge fires webhooks/syncs like a direct edit. Separation of duties via custom author/reviewer roles ([docs.doppler.com/docs/change-requests](https://docs.doppler.com/docs/change-requests), [doppler.com/pricing](https://www.doppler.com/pricing)).
- Custom roles: Enterprise, or a $9/seat/month Team add-on ([doppler.com/pricing](https://www.doppler.com/pricing)).

### 5. Delivery

- **`doppler run`** injects secrets as env vars into the child process: `doppler run -p PROJECT -c CONFIG -- CMD`; `--command '... $VAR'` for shell interpolation ([docs.doppler.com/docs/cli](https://docs.doppler.com/docs/cli)).
- **`doppler secrets download`** — e.g. `doppler secrets download --no-file --format=json` (also env/dotenv formats) ([docs.doppler.com/docs/cli](https://docs.doppler.com/docs/cli)).
- **Docker/Compose:** CLI in the image entrypoint (`doppler run` before app start) with `DOPPLER_TOKEN` passed as env var/build arg; secrets never baked into images ([docs.doppler.com/docs/docker](https://docs.doppler.com/docs/docker)).
- **Kubernetes operator:** `DopplerSecret` CRD maps a Doppler config → managed k8s Secret; operator (in `doppler-operator-system`) "is solely responsible for continuously syncing secret updates" and "can optionally automatically reload any deployments that reference a managed secret"; auth via service token or OIDC ([docs.doppler.com/docs/kubernetes-operator](https://docs.doppler.com/docs/kubernetes-operator)).
- **ESO provider:** official Doppler provider for External Secrets Operator; service tokens recommended (single-config scope), service-account tokens need project/config set on the (Cluster)SecretStore ([docs.doppler.com/docs/external-secrets-provider](https://docs.doppler.com/docs/external-secrets-provider), [external-secrets.io/latest/provider/doppler](https://external-secrets.io/latest/provider/doppler/)).
- **Webhooks:** fire on `config.secrets.update` with added/removed/updated diff, custom JSON payloads, SHA256 HMAC signing (`X-Doppler-Signature`), aimed at redeploy triggers (GitHub Actions, GitLab, Vercel, etc.); distinct from **integration syncs** that push secrets into AWS/Azure/Vercel/etc. (Developer 5 syncs, Team 100, Enterprise unlimited) ([docs.doppler.com/docs/webhooks](https://docs.doppler.com/docs/webhooks), [doppler.com/pricing](https://www.doppler.com/pricing)).

### 6. CLI ergonomics

- Verbs: `doppler login` (interactive auth), `doppler setup` ("assigns a specific directory (and its subdirectories) to a particular config" — directory-scoped defaults, no repeated flags), `doppler run`, `doppler secrets get NAME --plain` / `set` / `download` / `delete` ([docs.doppler.com/docs/cli](https://docs.doppler.com/docs/cli)).
- **Service tokens:** read-only, scoped to a single config ("least privilege… only has access to a single config"); format `dp.st.<config>.xxxx`; consumed via `doppler configure set token --scope`, `DOPPLER_TOKEN` env var, or `--token`; ephemeral tokens via `doppler configs tokens create NAME --max-age 1m --plain` (auto-deleted on expiry). Docs explicitly warn never to use personal/CLI tokens in live environments ([docs.doppler.com/docs/enclave-service-tokens](https://docs.doppler.com/docs/enclave-service-tokens), [docs.doppler.com/docs/cli](https://docs.doppler.com/docs/cli)).

### 7. License & pricing

- **Platform is proprietary SaaS** — but note a survey-relevant update: the "no self-hosting" premise is now stale. **Doppler On-Prem launched June 8, 2026** for "regulated industries and security-sensitive environments," letting orgs "keep secrets and backups inside their environment," Enterprise-tier ([official announcement, community.doppler.com](https://community.doppler.com/t/we-re-excited-to-announce-doppler-on-prem/1987)). No self-host for free/Team tiers; core server remains closed source.
- **CLI license: Apache 2.0** — confirmed at [github.com/DopplerHQ/cli/blob/master/LICENSE](https://github.com/DopplerHQ/cli/blob/master/LICENSE).
- **Tiers** ([doppler.com/pricing](https://www.doppler.com/pricing)): **Developer** — free for 3 users then $8/user/mo, max 25 users, 10 projects, 50 service tokens, 5 config syncs, 3-day logs, no RBAC/change requests/rotation. **Team** — $21/user/mo, max 500 users, 250 projects, 500 tokens, 100 syncs, 90-day logs, RBAC, SAML SSO, change requests, automatic rotation; custom roles/user groups/extra syncs $9/seat/mo add-ons each. **Enterprise** — custom pricing: custom roles, SCIM, dynamic secrets, proxied rotation, change request policies, custom log retention, 99.95% SLO, on-prem or cloud.

### 8. Architecture

- Closed-source multi-tenant SaaS; public claims: AES-256-GCM encryption plus tokenization so "internet-exposed infrastructure never accesses encryption keys or ciphertext"; encryption ops on isolated infrastructure; Enterprise customer-managed keys on AWS/GCP ("we encrypt your data with an additional key you control"); SOC 2 and ISO 27001 certified; "75B+ secrets read every month" ([doppler.com/security](https://www.doppler.com/security)).
- Open pieces: the CLI (Go, Apache 2.0 — [github.com/DopplerHQ/cli](https://github.com/DopplerHQ/cli)), the Kubernetes operator, and the ESO provider integration; everything else (dashboard, API server, storage) is closed.

### 9. What Doppler gets right / weaknesses (Wenv takeaways)

**Right (worth replicating in OSS):**
- The **root-config → branch-config inheritance model**: one master secret list per environment, cheap overlays for per-cloud/per-feature/per-developer variation, automatic propagation with override-wins semantics, plus auto-generated private personal configs ([docs.doppler.com/docs/branch-configs](https://docs.doppler.com/docs/branch-configs)).
- **`${...}` referencing** across configs and projects, resolved at read-time — kills copy-paste drift of shared credentials ([docs.doppler.com/docs/secrets](https://docs.doppler.com/docs/secrets)).
- **Missing-secret detection + mirror-across-environments** editing — solves environment drift in the UI without a heavyweight diff tool ([docs.doppler.com/docs/root-configs](https://docs.doppler.com/docs/root-configs)).
- **Typed/validated secret values** (json/uuid/url/datetime…) — rare even among paid competitors ([docs.doppler.com/docs/secrets](https://docs.doppler.com/docs/secrets)).
- **Ergonomic CLI**: directory-scoped `doppler setup` + one universal `doppler run` injection verb + single-config read-only service tokens ([docs.doppler.com/docs/cli](https://docs.doppler.com/docs/cli)).
- Per-secret visibility (masked/restricted), commit-style rollback log, and change-request approval flow as a coherent governance story ([docs.doppler.com/docs/secret-visibility](https://docs.doppler.com/docs/secret-visibility), [docs.doppler.com/docs/versioning](https://docs.doppler.com/docs/versioning), [docs.doppler.com/docs/change-requests](https://docs.doppler.com/docs/change-requests)).

**Weaknesses (Wenv's opening):**
- SaaS lock-in with closed server; self-hosting exists only as an Enterprise-priced on-prem product since June 2026 — nothing self-hostable at indie/homelab scale ([community.doppler.com](https://community.doppler.com/t/we-re-excited-to-announce-doppler-on-prem/1987)).
- Per-seat pricing that gates table-stakes features: RBAC, change requests, config inheritance, and rotation all start at $21/user/mo Team; custom roles and user groups are paid add-ons on top ([doppler.com/pricing](https://www.doppler.com/pricing)).
- Restricted visibility is leaky by design — service-token minting bypasses it ([docs.doppler.com/docs/secret-visibility](https://docs.doppler.com/docs/secret-visibility)).
- No true side-by-side multi-environment compare/edit grid in the dashboard (only mirroring + missing-secret warnings) — a gap Wenv could exceed, not just match ([docs.doppler.com/docs/root-configs](https://docs.doppler.com/docs/root-configs)).
- 3-day activity log retention on the free tier makes auditability effectively paid ([doppler.com/pricing](https://www.doppler.com/pricing)).

### Gap analysis — the Wenv wedge

No surveyed product offers, fully open-source and self-hostable, the combination of:

1. **Deterministic environment inheritance** (base → env → override, declared, not ad-hoc). Only Doppler has it (root/branch configs + config inheritance) — closed SaaS, and inheritance itself starts at Team $21/user/mo ([branch configs](https://docs.doppler.com/docs/branch-configs), [pricing](https://www.doppler.com/pricing)). Infisical's imports are ordered last-wins lists; Phase has only string references; Vault/OpenBao/SOPS/ESO have nothing.
2. **Schema validation** (typed values, required keys per environment, validated before delivery). Only Doppler has typed values, and even it only *warns* on missing keys ([docs](https://docs.doppler.com/docs/secrets)). Nobody blocks a deploy on an incomplete environment.
3. **Environment-matrix UI** (side-by-side view *and* edit across all environments). Only Infisical has a real cross-env grid ([Secrets Overview](https://infisical.com/docs/documentation/platform/secrets-mgmt/project)) — but pairs it with paywalled audit/rollback and tiered environment counts.
4. **No paywall on production-required features** (audit, rollback, custom roles, approvals). Only OpenBao and SOPS clear this bar — and neither has environments, schema, or a usable env UI. Both open-core apps (Infisical, Phase) fence exactly these features into `/ee` with in-production license enforcement.
5. **First-class Docker Compose** (documented run/export/agent flow for non-K8s deployment). Everyone treats Compose as an afterthought except CLI-run vendors; nobody targets "self-hosted homelab/SMB Compose stack" as the primary deployment.

The wedge is the *conjunction*: Doppler's environment model (1, 2) + Infisical's matrix UI (3) + OpenBao/SOPS's licensing posture (4) + a Compose-native delivery story (5). Every incumbent is missing at least two of the five, and the two products closest on UX (Infisical, Doppler) both monetize the exact features Wenv would ship free.

Secondary observations for positioning:
- ESO is complementary, not competitive: an Wenv ESO provider (like Infisical's and Doppler's; Phase has none) is the cheapest credible K8s story, alongside or before a native operator ([provider table](https://external-secrets.io/latest/)). Its 2025 maintainer pause ([cncf/toc#1819](https://github.com/cncf/toc/issues/1819)) argues for not making it the *only* K8s path.
- SOPS is the migration source to target: its pain points (updatekeys toil, no drift view, no read audit, merge conflicts) are Wenv's demo script ([README](https://github.com/getsops/sops/blob/v3.9.0/README.rst)).
- Phase's E2EE-vs-sync mutual exclusion ([docs](https://docs.phase.dev/console/secrets)) is a cautionary design lesson: server-side features and client-side encryption must be reconciled up front.

### License precedents

- **HashiCorp Vault: MPL 2.0 → BUSL 1.1 (2023-08-10), licensor now IBM** ([announcement](https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license), [LICENSE](https://github.com/hashicorp/vault/blob/main/LICENSE)) → community forked the last MPL branch as **OpenBao** under Linux Foundation governance (LF Edge, 2024-04-30; 2.0 GA 2024-07-16), which then shipped formerly Enterprise-only namespaces for free ([timeline above](#license-capture-case-study-busl--openbao-timeline)). The canonical capture-and-fork arc; single-vendor CLA + permissive-to-BUSL is the exact risk Wenv's license choice must preclude.
- **Infisical: MIT + `/ee` proprietary carve-out** with production-use restriction in [ee/LICENSE.md](https://github.com/Infisical/infisical/blob/main/backend/src/ee/LICENSE.md); governance/ops features (audit logs, PIT recovery, approvals, custom roles, SCIM, groups) land in `/ee` from day one ([ee/services](https://github.com/Infisical/infisical/tree/main/backend/src/ee/services)). **Features have also demonstrably migrated upward between paid tiers**: Infisical's own pricing blog describes a former $18/id/mo Pro including PIT recovery, RBAC, rotation and 90-day audit retention ([vendor blog](https://infisical.com/blog/secrets-manager-pricing)); on the current 4-tier page, PIT and rotation sit in Advanced ($40) and Pro audit retention dropped to 30 days ([pricing](https://infisical.com/pricing)) — the PIT docs still saying "Pro Tier" corroborate the recent move ([PIT docs](https://infisical.com/docs/documentation/platform/pit-recovery)). The README's "MIT" badge understates the dual license ([README](https://github.com/Infisical/infisical/blob/main/README.md)). Building on an open-core vendor's paid feature carries repricing risk even without a relicense.
- **Phase: same open-core shape** (MIT console + commercial `ee/`, GPL-3.0 CLI/operator) plus **runtime license-key gating in the self-hosted binary** (`PHASE_LICENSE`) ([envars](https://docs.phase.dev/self-hosting/configuration/envars)) — "open source" with in-app feature flags.
- **Clean precedents**: SOPS MPL 2.0 (Mozilla → CNCF sandbox, community maintainers) ([cncf.io](https://www.cncf.io/projects/sops/)), age BSD-3 ([LICENSE](https://github.com/FiloSottile/age/blob/main/LICENSE)), ESO Apache 2.0 under CNCF ([cncf.io](https://www.cncf.io/projects/external-secrets/)), OpenBao MPL 2.0 under LF.
- **Implication for Wenv**: a copyleft-leaning OSI license (MPL 2.0 as the pragmatic middle: file-level copyleft, fork-proofs the core, no BUSL path without unanimous contributor consent) plus foundation-style or DCO governance — and an explicit public commitment of "no /ee directory": audit, rollback, RBAC, approvals in the free core, since that boundary is precisely where every commercial competitor monetizes.
