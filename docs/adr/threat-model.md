# Wenv threat model (ADR, locked 2026-07-29)

> **Declared amendment (2026-08-06, [multi-instance.md](./multi-instance.md), per the [oss-mechanics.md](./oss-mechanics.md) amendment procedure):** the server's enumerated outbound destinations gain one class — **configured remote Wenv instances** (the directory tier's server-to-server fetch), under the full user-configured-outbound control set fixed there: canonical HTTPS origins only, SPKI pin verified before bytes on every connection, no redirects, rebinding defeated by the pin, private ranges explicitly permitted, response/fan-out/aggregate-rate bounds, explicit-config-only CONNECT-tunneled proxying. Zero configured remotes = zero outbound; the enumeration rule is preserved by enumeration, not weakened. Details in [multi-instance.md](./multi-instance.md).

Context: Wenv is a planned fully open-source, self-hosted secrets + environment-config manager. Go single binary; pluggable datastore (sqlite + postgres, field-level envelope encryption identical on both); v1 scale envelope 1 instance / 1-3 orgs / <=25 users / <=10k secret entries; single node, no HA in v1; delivery via CLI run-wrapper (Compose) and a minimal K8s operator syncing native Secrets; outbound "deployment modules" push secrets to VCS/CI platforms (Forgejo reference adapter in v1); org layer day one; SaaS possible later.

Granularity note: this is the wayfinding-level threat model ADR. It fixes attacker classes, trust stance, and guarantees. Mechanism-level specification is explicitly delegated: encryption mechanics (AEAD choice, AAD binding, nonce rules, key lifecycle, ciphertext versioning, replay/swap defense) -> encryption-model ticket; token/credential formats -> machine-identities ticket; K8s reconciliation semantics -> K8s-integration ticket; auth flows/MFA/session mechanics -> human-auth ticket; audit mechanics -> audit ticket; backup/restore/availability procedures -> operations spec; adapter sync integrity -> deployment-module ticket. Same-org permission ladder (who may list/read/reveal/edit/publish, adapter configuration and use, token creation) -> RBAC ticket, BOUND by: least privilege and deny-by-default WITHIN an org, not only across orgs; capabilities are separate grants, not bundles; authorization is evaluated against current policy immediately before EACH sensitive disclosure or external effect (not once per job): a long-running or queued job re-checks before every secret read and every adapter push, and revocation mid-job terminates the job's remaining sensitive operations; deprovisioning a user MUST atomically invalidate their sessions, API credentials, and cached authorization. Each delegated ticket MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

## Protected assets
Primary: secret values; root key; service-account tokens; human session tokens; adapter (deployment-module) outbound credentials; audit-log integrity.
Secondary: config metadata (org/project/environment names, key names, schemas, descriptions, audit metadata, ciphertext sizes). A stolen DB exposes this metadata even though values stay encrypted — accepted and documented; it can reveal infrastructure shape and credential targets. Selected-metadata encryption is a possible future hardening, not v1.

## Trust boundaries — including where plaintext goes after delivery
1. Browser <-> server (TLS; browser endpoint risks — extensions, DOM tooling, clipboard, screenshots — are accepted endpoint risks, documented).
2. CLI/workload <-> API: token auth over TLS — authenticated transport is REQUIRED on every non-loopback boundary: browser, CLI/workload API, remote postgres (TLS or same-host socket), K8s API (standard kubeconfig verification), adapter->provider calls (TLS with certificate verification, no insecure-skip flags in v1).
3. Server <-> datastore (root key never stored in DB; see root-key failure domain below).
4. Server <-> external providers reached by deployment modules (the boundary is server->provider, NOT server->module: modules run in-process and are trusted server code, reviewed as such; tenant-configured destinations are an SSRF/exfiltration surface — constraint on the deployment-module ticket, bound concretely: https-only schemes; default-DENY of ALL non-global and special-use destination ranges (loopback, link-local/metadata, RFC1918, IPv6 ULA, CGNAT, multicast/reserved) with exceptions grantable ONLY by the instance operator at deployment configuration level — never by tenants or org admins; DNS-rebinding-safe resolution (validate the IP actually dialed); proxy-aware clients must not bypass these controls — configured proxies either apply the same destination-range policy or are refused for secret-bearing/adapter traffic; no redirect following on secret-bearing requests; response-size caps; adapter credentials least-privilege. Malicious or compromised providers are an attacker class: adapters must treat provider responses as untrusted input and never echo secret material back in errors.)
5. Backup boundary (age-encrypted exports; see backup key semantics).
6. Post-delivery surfaces — plaintext legitimately leaves Wenv and its protection at delivery: child-process environments (/proc, core dumps, container inspect) on Compose hosts; native K8s Secrets (etcd, namespace RBAC, cluster admins, etcd backups); CI/VCS provider secret stores and their runners/logs. These are DELIVERED-TO systems: Wenv's guarantees end at the delivery boundary; the threat model documents this expansion honestly (docs must state K3s --secrets-encryption, provider-side exposure). Compromised workloads, pods, CI runners, and cluster admins are attacker classes AGAINST DELIVERED VALUES and are outside Wenv's ability to defend — scoping (next section) limits what any one of them ever received.

## Attacker classes and stance
Defend against: unauthenticated network outsiders; authenticated malicious or careless regular users (least privilege, deny-by-default); stolen low-privilege accounts; former users (immediate deprovisioning); cross-org malicious tenants; compromised workloads/CI runners (limited to their token scope, see workload credentials); database/backup/storage-admin theft of data at rest (headline guarantee).
Cross-org isolation mechanism: deny-by-default authorization with org context propagated through EVERY execution path — API handlers, background workers, exports, search, audit queries, K8s reconciliation, adapter jobs — via a single mandatory chokepoint; identifier lookups always ownership-checked; cross-org negative tests required in CI for every entry-point class. NOT cryptographic per-org keys in v1 (accepted residual risk: an authorization bug is not backstopped by crypto; revisit if SaaS).
Operator-equivalent (documented): an attacker with WRITE access to the live datastore (e.g. compromised remote postgres) can rewrite identities, authorization state, and v1 audit records — treated as operator-equivalent compromise; mitigations: postgres hardening guidance in deployment docs, AEAD associated-data binding (encryption ticket) prevents ciphertext transplant even for a DB writer, and the fail-closed audit stance limits silent tampering to actors at this level. Release-signing-key compromise: accepted residual risk with mitigations — signing key held offline/outside CI, documented revocation + re-key procedure, provenance attestation as extension path.
Trusted (documented, not defended against): the instance operator (holds root key, OS access — can read everything; all operator-visibility claims in docs are explicit about this); org admins within their own org (a stolen org-admin account = full org compromise — documented; mitigations are the human-auth ticket's session/MFA decisions); adapter code shipped in the binary (in-process, trusted; third-party adapter contributions get security review — supply-chain section).

## Compromise assumptions and guarantees
- Headline guarantee (data-at-rest theft): theft of the database (sqlite file copy, postgres dump) or of a backup, WITHOUT the root key, yields no secret values AND no directly replayable stored credentials (explicit residual: offline guessing of weak human passwords remains possible against Argon2id verifiers — slowed, not prevented; password policy is the human-auth ticket's constraint): secret values are envelope-encrypted; service-account and session tokens are high-entropy random (>=256-bit) and stored only as fast-hash verifiers (safe ONLY because entropy makes brute force infeasible — binding constraint on the machine-identities ticket); human passwords use a vetted memory-hard KDF (Argon2id); ALL machine-generated tokens including single-use ones (bootstrap, invite, reset) are high-entropy (>=128-bit random minimum), hashed AND expiring; MFA seeds and recovery codes are envelope-encrypted; adapter outbound credentials are envelope-encrypted like secret values. Backup identity keys are protected assets. CI-tested: dumps grepped for known plaintext AND stolen-dump authentication attempts must fail.
- Running-server compromise (root key in memory): this is full control-plane compromise — the attacker can read all decryptable values, alter values, mint credentials, capture future writes, drive configured adapters, rewrite the v1 audit log, extract the root key, and persist. Stated plainly in docs; no zero-knowledge claims anywhere. Mandated recovery posture (documented runbook): rebuild the instance from trusted artifacts and rotate EVERYTHING — root key, human credentials, workload tokens, adapter credentials, and ALL secret values that were decryptable at any point during the compromise window (i.e. every stored value, not only delivered ones), including values written before the trusted rebuild completed.
- Root key theft alone (no DB copy): yields nothing immediately, BUT enables decryption of any DB copy still protected by that key version — including retained old backups, which rotation cannot retroactively protect (documented residual risk). Root-key compromise therefore requires rotation + re-encryption to protect FUTURE copies, and the root key must NOT share a backup/storage domain with the database (deployment docs requirement; the encryption ticket defines rotation completion semantics and failure atomicity).
- Backup key semantics: backups contain the already-field-encrypted DB export, additionally age-encrypted to a backup identity that is DISTINCT from the root key and stored separately. Restoring requires backup key + DB; reading values additionally requires the root key. Restore is a security event, bound: restores require operator authentication, are audit-logged, and restore brings the instance up FAIL-CLOSED in a recovery mode: EVERY pre-restore authentication artifact in the restored state is invalidated — sessions, API tokens, adapter credentials, and all single-use artifacts (bootstrap/invite/reset tokens, MFA seeds, recovery codes; previously captured bearer values must not survive restore) — with fresh post-restore identity proof required, human accounts require credential reset/revalidation before first login — unconditionally, independent of identity/role reconciliation (restored password verifiers are never trusted as-is) — and the operator must additionally reconcile identities and roles, and the operator must reconcile users/roles against current intent before normal operation resumes — restoring an older DB can resurrect since-revoked tokens, removed users, and old roles, and truncate audit history; the operations spec must carry these as blocking requirements plus loss/rotation/restore-testing procedures.
- Audit-log integrity, v1 stance: protected at the application layer (no delete/update API, append-only at app level) against tenants and low-privilege users. Durability is fail-closed, with external effects handled precisely: for internal operations (auth, grants, reveals, fetches, restores) the audit record is durable before the operation completes, else the operation fails; for external effects (adapter pushes) a durable INTENT record precedes the external call and a durable terminal OUTCOME record (success/failure/unknown) follows it — an audit-write failure before the call aborts the push; an outcome-write failure surfaces as an operational error requiring reconciliation, never silence. Audit growth is retention-managed (ops spec), never silently dropped. NOT tamper-proof against the instance operator or a full server compromise in v1 — stated limitation; external sink/hash-chaining is the audit ticket's extension path.
- Availability: single node, no HA is an accepted v1 posture. Baseline, covering every attacker-triggerable expensive path (auth, fetch, search, export, adapter fan-out, K8s reconcile): per-principal and per-org rate limits and quotas PLUS per-source-IP and instance-wide admission limits on pre-authentication paths (login, token exchange) so identity rotation cannot exhaust Argon2id, audit storage, or global concurrency, bounded concurrency and queue depth, bounded payload AND response sizes, retry backoff with deduplication on adapter jobs. Recovery expectations (RPO/RTO, corrupt-backup handling) -> operations spec.

## Workload credentials
Service-account tokens scoped to (project, environment | explicit env list), read-only (only v1 workload capability), individually revocable, every fetch audit-logged with token identity.
Revocation semantics, stated precisely: revocation immediately stops FUTURE fetches. It cannot recall values already delivered (running processes, synced K8s Secrets, CI-pushed values). Blast radius of a leaked token = every snapshot version fetchable during its validity window for its scope — not one snapshot. Post-revocation the exposed values themselves must be rotated by the user; docs state this and the UI surfaces "values this token could read".

## Baselines
- Browser/session: concrete floor (detailed in human-auth + prototype tickets): httpOnly+SameSite+Secure cookies, CSRF tokens, session rotation on privilege change, no secret values in URLs or localStorage, reauthentication step before reveal (RBAC ticket decides exact ladder), proxy-trust configuration explicit. Tenant-controlled content (key names, descriptions, schemas, folder names, adapter config) MUST remain inert in every browser context — stored/DOM XSS from tenant input executing with a more-privileged viewer's authorization is a defended-against path, since malicious regular users are a defended attacker class; encoding/CSP mechanics -> UI spec via prototype tickets, bound by this outcome.
- Logging non-disclosure: goal — plaintext secrets never in logs/errors/traces. Enforced by mechanisms, not intent: constrained logging API (the only exported logger), redacting wrapper types for secret material, panic-recovery sanitization, adapter/provider error-body sanitization before logging, canary integration tests (known plaintext must never appear in captured log output). Residual risk documented: no mechanism catches every []byte copy; code review + canaries are the net.
- Telemetry, defined: NO unsolicited maintainer/vendor-controlled egress — no update checks, no crash reporting, no usage metrics in v1. The only outbound connections are user-configured functional destinations: the configured datastore, the K8s API for the operator, and deployment-module targets. Any future opt-in phoning feature must be off by default and enumerated in docs.
- Supply chain (mechanisms, details in architecture ADR). Defended: dependency substitution (module pinning + checksum db), unsigned artifact swap for consumers of official install/upgrade paths — official installers and upgrade tooling fail closed on signature verification against a pinned trust root (manual downloaders who skip verification are outside this guarantee, stated in docs); signing key held outside CI, tampered base images/toolchains (pinned digests). Accepted with mitigations, stated honestly: a compromised maintainer account or release pipeline can produce a validly signed malicious release — mitigations are protected release branches, mandatory 2FA, release authority limited to named maintainers, and provenance attestation as an extension path. SBOM published per release; minimal dependency tree (stdlib bias); ALL contributions touching crypto, auth, adapters, or delivery require maintainer security review.
