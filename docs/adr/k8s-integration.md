# Hikyo Kubernetes integration (ADR, locked 2026-07-31)

Context: the v1 persona ([#3](https://github.com/Hikyo-Org/Hikyo/issues/3)) self-hosts on a single box first and on K3s second, and Kubernetes/K3s support is part of the wedge. The K8s research ([#5](https://github.com/Hikyo-Org/Hikyo/issues/5), [k8s-delivery.md](../research/k8s-delivery.md)) compared five mechanisms and ranked an own minimal operator first; the machine-identity ADR ([#17](https://github.com/Hikyo-Org/Hikyo/issues/17)) already delegates the CRD shape, resync semantics and rollout triggering here, and fixes the credential kinds, the federation trust model and the conditional-fetch obligation. The Compose ADR ([#18](https://github.com/Hikyo-Org/Hikyo/issues/18)) fixes the stamp concept this ADR must share one explanation with, and propagates its integrity amendment and loader-control baseline for environment-variable delivery. This ADR fixes **which Kubernetes integration ships in v1, its CRD and identity model, how a publish reaches running workloads, what happens to the managed Secret across failure modes, and the documented paths beside and beyond the operator**.

## Declared amendment

> **Amends the revision ADR ([revision-model.md § Revision identity](./revision-model.md), [#11](https://github.com/Hikyo-Org/Hikyo/issues/11)), the schema ADR's propagation ([schema-model.md](./schema-model.md), [#12](https://github.com/Hikyo-Org/Hikyo/issues/12)) and the encryption ADR's rollout-wave expectation ([encryption-model.md § rotate-token-key](./encryption-model.md), [#14](https://github.com/Hikyo-Org/Hikyo/issues/14)) — the server change token is change-detection material, never a workload-visible value.** #11 states the Kubernetes operator writes the change token into the pod-template annotation; #12 requires #18 and #19 to "consume the delivery-manifest change token"; #14 prices token-key rotation as "one benign rollout wave". This ADR narrows the first, satisfies the second in its real sense, and deletes the third: the token is consumed **as the conditional-fetch cursor's change-detection input** (#17), and what reaches any workload-visible field is a **client-side keyed per-target stamp** — #18's label for Compose, this ADR's annotation for Kubernetes, one construction. Grounds: the server token is per `(org, project, environment)` and cannot be sliced per render target (#18's argument, inherited with the "one explanation for both" obligation #18 binds on this ticket), and an environment-granular annotation restarts every opted-in workload on any change in the environment — the rotate-one-key-restart-the-database outage #18 rejects. Consequence stated rather than discovered: **token-key rotation no longer causes any restart wave** — rotation invalidates conditional-fetch cursors, the resulting full fetch delivers unchanged content, and an unchanged per-target stamp moves nothing. #14's cache-invalidation protocol stands; its ordering rationale ("last, because it forces the wave") becomes harmless rather than load-bearing. The Compose ADR already embodied this amendment without declaring it; this ADR declares it for both integrations.

Granularity note: this is the wayfinding-level Kubernetes ADR. It fixes the mechanism, the API objects and where authority lives, the rollout trigger, the Secret lifecycle, the loader-control posture and the extension paths. Mechanism-level detail is delegated: concrete API group, kind and field spellings, CLI verbs and their authorization formulas → API & CLI ([#25](https://github.com/Hikyo-Org/Hikyo/issues/25)); event shapes → audit ([#24](https://github.com/Hikyo-Org/Hikyo/issues/24)); default resync interval, retry/backoff curves, JWKS bounds as applied per cluster, and every other concrete duration or quota → operations spec (fog); the operator's build/runtime stack → architecture ([#22](https://github.com/Hikyo-Org/Hikyo/issues/22)). Each delegated ticket MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

## The mechanism: an own minimal operator

**v1 ships one in-cluster integration: a minimal Hikyo-owned operator.** It watches a namespaced `HikyoSecret` custom resource, performs a conditional authorized fetch against the Hikyo server, and writes the result into a native Kubernetes `Secret` it owns. Workloads consume that Secret however Kubernetes lets them — `envFrom`, `valueFrom`, volume mount. The operator is the smallest thing that closes the loop: one CRD kind pair, one reconcile loop, one HTTP client, one small Deployment (Pi-class footprint, comparable to Reloader's ~10m CPU / 128Mi).

**Values land in native Secrets and therefore persist in the cluster datastore.** Stated plainly, not buried: on K3s that store (SQLite or embedded etcd) is **plaintext at rest by default**. The documentation MUST carry the K3s callout — enable `--secrets-encryption` — adjacent to every sync-to-Secret instruction, per #17's propagation. AES-CBC is the K3s default provider; `secretbox` is selectable **only on K3s releases that support it** (added in 2025 patch releases), so the runbook names a K3s version floor for `secretbox` and keeps AES-CBC guidance below it. In exchange the integration gets the entire native ecosystem for free: namespace isolation, RBAC on Secrets, `envFrom`, GC by ownership. The alternatives that avoid the datastore (CSI provider, webhook injector) were rejected in research on grounds this ADR adopts (§ *Beside and beyond the operator*).

**What "changes apply on restart" means here, split by consumption, because Kubernetes splits it:** environment-variable consumption (`envFrom`, `valueFrom`) is fixed at pod start — restart-to-apply holds exactly. A Secret consumed as a **normal volume mount is updated live and eventually by the kubelet** in running pods; that is Kubernetes' own semantics, outside the operator's control, and the documentation says so rather than claiming restart-only. A **`subPath` mount never updates** and behaves like environment. Immutable generation-named Secrets (one Secret per stamp, Compose-generation style) were considered to force restart-only semantics uniformly and rejected: a workload not opted into rollout triggering would reference a name that stops existing, converting delivery into pod-start failures for exactly the workloads that asked to be left alone.

*Rejected: ESO provider as the only v1 integration.* The delivery story would ride a third-party project's monthly release train and review queue. It returns as the named extension path.

## The API objects — authority never lives cluster-scoped

Two kinds, split on the **authority boundary**, not on ESO's connection/mapping boundary:

- **`HikyoInstance` (cluster-scoped)** — non-secret connection configuration only: server URL, CA bundle. **It never carries a credential, and the spec has no field that could hold one.** Creation is RBAC-gated to the cluster admin. **The endpoint and trust anchors are immutable**: changing the URL or CA means creating a new `HikyoInstance`, so "where do credentials and trust point" has an audit-visible identity, and a mutated object cannot silently redirect every referencing CR. **HTTPS is mandatory; there is no insecure-skip-verify field.** Server certificate verification against the pinned CA bundle (or system roots) is unconditional — a "TLS expectations" knob that can be loosened is the hostile-server hole reopened at a different layer.
- **`HikyoSecret` (namespaced)** — everything with authority or effect: the auth ref, the instance ref, the project/environment selector, the key mapping, the managed Secret reference and policies, the delivery projection, the loader-control acknowledgement.

The rule that generalizes: **a cluster-scoped Hikyo object may never carry authority.**

The split is a security decision, not an ergonomic one. If the server URL were a per-CR field, a principal holding only `create hikyosecret` in one namespace could point the CR at a **hostile Hikyo server** and needs no Hikyo authorization at all — the fake server answers every fetch. The resulting Secret is consumed by that namespace's workloads, and where consumption is environment variables, #18's amendment 1 makes delivery an **integrity capability**: `LD_PRELOAD`, `NODE_OPTIONS`, `PATH` in a hostile response is code execution in every consuming pod. Pinning the endpoint in a cluster-scoped, admin-gated, immutable object closes it.

Accepted consequence, stated: a namespace tenant cannot bring their own Hikyo instance without the cluster admin creating an `HikyoInstance`. For the target persona that is the right trade; it is a real limitation.

*Rejected: single CRD carrying connection + auth + mapping (Infisical shape).* Least YAML, and it is exactly the hostile-server hole above. *Rejected: ESO-shaped namespaced store.* A namespaced connection object is creatable by the same tenant it is supposed to constrain — same hole, one indirection later.

Names here are illustrative; #25 fixes the API group and spellings.

## Identity — the operator holds no Hikyo credential

**Every reconcile fetch runs under the identity the `HikyoSecret` names, and the operator itself holds none.** The operator is pure mechanism: it can move ciphertext and Secrets around, but it can authorize nothing of its own.

Two auth-ref forms, matching #17's two credential kinds:

1. **Bootstrap Secret** — a Kubernetes Secret in the **same namespace as the CR**, holding an `hikyo-token`. Simple, works everywhere, and is the at-rest credential #17 already prices honestly.
2. **ServiceAccount federation** — the CR names a ServiceAccount in its **own namespace**; the operator obtains a short-lived, **audience-bound token via the TokenRequest API** — an API-issued token held in operator memory, not a projected-volume token — and presents it under #17's `oidc-federation` kind. **No long-lived bearer credential persists in the cluster.** Honest residuals, stated: a TokenRequest token without a `boundObjectRef` is not bound to any pod or Secret lifetime, so the operator requests the shortest expiry the API server grants and #17's caps on token age and `exp - iat` bound it server-side; and because Hikyo validates offline against JWKS, a token remains acceptable until expiry even if the SA is deleted meanwhile — the same until-expiry window every offline OIDC validator has. This is the recommended form wherever the cluster's OIDC discovery endpoint is reachable by the Hikyo server.

**Naming a credential is not authority to use it — the referenced object must consent.** Same-namespace confinement stops cross-namespace theft, but within the namespace a principal holding only `create hikyosecret` — and **no** `get` on the bootstrap Secret, no token rights on the SA — could otherwise point a CR at either and have the privileged operator wield it: the confused deputy Kubernetes' own authorization guidance warns CR controllers about. Therefore, normative:

- A bootstrap Secret is usable only if it carries an **explicit designation** (label/annotation, spelling per #25) marking it for Hikyo delivery use **and naming the `HikyoInstance` it may be presented to**. Designating it is an act by someone holding write on that Secret — a strictly greater right than reading it.
- A ServiceAccount is usable for federation only if it carries the same designation, applied by someone holding write on the SA. The operator's RBAC `create` on `serviceaccounts/token` is granted per-namespace and **restricted by `resourceNames` to the designated ServiceAccounts** — mandatory, not best-effort; the install tooling maintains the list, and a namespace whose designated set is too volatile to pin has made the namespace boundary its real control and the docs say so plainly.
- A CR referencing an undesignated object does not reconcile; the status condition names the missing designation.

The instance-naming half closes a second hole: in a cluster with two approved `HikyoInstance`s, a CR pairing instance B with a bootstrap Secret designated for instance A would ship A's token to B's server. Federation does not need the equivalent — #17 makes the audience mandatory and per-instance, so a token minted for A fails B's validation.

**The confused deputy this design exists to avoid, named:** an operator holding one operator-wide Hikyo credential turns anyone with `create hikyosecret` in any watched namespace into a reader of everything that credential reaches. Namespace isolation collapses into a single cluster-wide principal — contradicting #17 (service accounts project-owned, grants confined to the project subtree) and pre-breaking tenant isolation ([#23](https://github.com/Hikyo-Org/Hikyo/issues/23)). *Rejected: operator-wide credential; rejected: a hybrid with an optional cluster-default credential*, which is the same hole behind a convenience flag.

Inherited from #17 verbatim, restated because it is load-bearing on Kubernetes: federation bindings match **byte-exact `(issuer, subject)`** with a **mandatory, non-default audience**; a namespace-pattern binding is forbidden, because *any ServiceAccount in namespace `prod`* hands an Hikyo principal to anyone holding `create serviceaccount` there. Hikyo-side caps on token age and `exp - iat`, the bounded JWKS staleness window, static JWKS for air-gap, and finite binding lifetimes all apply unchanged. TokenReview remains rejected (a per-cluster reviewer credential is a long-lived credential added to avoid one).

## The managed Secret is created, never adopted

Ownership is established at creation and only there. Normative, because "a Secret it owns" is otherwise a race and a takeover surface:

- The operator **creates** the managed Secret only when the target name is **absent**. It **updates** only a Secret whose controller ownerReference is this CR's UID. It **never adopts** an existing Secret, whatever its labels — a CR targeting an existing TLS, image-pull or application Secret is a takeover attempt and fails with a named condition, not a merge.
- An ownerReference is garbage-collection plumbing, not write authority; the controller-UID check is the authority test, and a Secret with a different or additional controlling owner is refused.
- **The managed Secret reference is immutable on the CR** (retargeting is delete-and-recreate, so a retarget cannot orphan-then-capture), and two CRs naming the same target is a conflict the operator refuses deterministically — first-created wins by CR UID, the loser gets a condition, never a write tug-of-war.

## Change propagation — one stamp story, annotation edition

**The operator owns rollout triggering, and consent lives on the workload.** A workload opts in by carrying an annotation that **names the managed Secret(s) it consumes** (spelling per #25); on a delivered change the operator patches the stamp annotation into that workload's **pod template**, which **requests** a rollout under the workload's own update strategy. Restart-to-apply for environment consumption; nothing mutates a running process.

*Rejected: an opt-in list on the `HikyoSecret`* — an earlier draft had one, and it is an escalation: a CR author would restart arbitrary Deployments/StatefulSets/DaemonSets they hold no `patch` on, contradicting this ADR's own "creating a CR is a far smaller right than editing Deployments". Consent to be restarted belongs to the object being restarted, where workload RBAC already governs it.

**"Requests", not "forces", stated honestly:** a paused Deployment does not roll; a StatefulSet with `updateStrategy: OnDelete` rolls nothing automatically; a partition or failed readiness can stall a rollout indefinitely. The operator surfaces a stalled or ignored rollout as a CR condition — delivered-but-not-rolled is a visible state, never a silent success — and claims completion only from the workload controller's own status.

**The annotation value is the same construction as Compose's stamp** (#18 requires one explanation for both): `HMAC(derived per-target stamp key, versioned canonical encoding of the target's delivered content)`, 128 bits, version-prefixed. Per **target**, so blast radius follows consumption: rotating one API key restarts the workloads that consume it and never the database beside them.

- **Never a bare content digest.** #11 fixed the keyed rule for exactly this field: a pod-template annotation is readable by anyone with `get deployments`, and an unkeyed hash there is an offline brute-force oracle for low-entropy secrets. The server token itself stays out of workload-visible fields per the declared amendment; it is cursor material only.
- **The stamp key is derived per target, not global.** The operator holds one local 256-bit random root (in an operator-owned Secret in its own namespace) and derives each target's key via **HKDF with domain separation over `(HikyoInstance UID, CR UID, managed-Secret name)`**. A single flat key would make equal content produce equal stamps **across namespaces and projects** — a cross-scope equality oracle for any principal who can read workloads in two namespaces but Secrets in neither, which is the exact comparison #11's scoped derivation exists to kill server-side. Derivation re-kills it client-side.
- **Compromise of the stamp root is a comparison-oracle incident, not plaintext disclosure** — stated because an earlier draft overstated the nil-blast-radius claim: reading the operator's namespace does not imply reading workload namespaces' Secrets, so the key is worth protecting for what it actually guards.

**RBAC cost, stated rather than papered over:** the trigger needs `get`/`list`/`watch` **and** `patch` on `deployments`, `statefulsets` and `daemonsets` in bound namespaces — read to discover the workload-side consent annotations and to confirm rollout status from the controller's own reporting, patch to write the stamp; these are distinct RBAC verbs and all four are required for triggering to function. Kubernetes RBAC **cannot scope a write by label or annotation selector**. "Only opted-in workloads" is therefore enforced by operator code, not by RBAC: a compromised operator can patch any workload in its bound namespaces, including images. The namespace binding (§ *Scoping*) is the only real boundary, and the docs MUST present it as such. Operators unwilling to grant workload-patch rights run with triggering disabled — delivery still works; restarts become the user's job.

*Rejected: ship nothing and document Reloader.* Reloader's **default** strategy injects an env var whose value is a hash of the changed resource — a bare content digest over secret material in a workload-readable field, i.e. the exact oracle #11 forbids, as a third-party default. Documenting Reloader honestly would mean mandating its non-default `annotations` strategy forever, resting a correctness property on someone else's default not changing. And it saves nothing: Reloader needs the same `patch` grant. Reloader is documented only as prior art with this caveat.

### Write ordering

Secret write, workload patches and cursor persistence are three separate API writes and the order is normative: reconciles are **serialized per CR**; the managed Secret is updated first with a **`resourceVersion` precondition** and verified; workload patches second; **the cursor is persisted last**, only after every write succeeded. A crash anywhere redoes the reconcile from a full authorized fetch — idempotent because the Secret write is content-convergent and the stamp is a pure function of delivered content. Workload-first could start pods against the old Secret under a new stamp; cursor-first could record delivery that never happened, which with a "current" answer would be permanent.

## Managed Secret lifecycle — three events, three different answers

The trap is treating these alike; they are distinct and the CR status names which one is in effect.

1. **CR deletion.** Default `creationPolicy: Owner`: the managed Secret carries an ownerReference and is garbage-collected with its CR. `Orphan` is the explicit opt-in for GitOps handover.
2. **Server unreachable, 5xx, or expired/invalid/revoked credential.** The operator **retains** the last-synced Secret unchanged, sets a loud status condition, emits an event, and keeps retrying. **No staleness bound.** Pods keep starting with stale-but-valid values — the sync-to-Secret model's central resilience property, and the stance #17 already locks (*failing closed on a refresh blip would stop every workload fetch cluster-wide*). Credential expiry is additionally surfaced ahead of time as a CR condition and event per #17.
3. **Authoritative refusal under a working credential.** The server authenticates the principal and answers that it no longer holds `read` on the environment, or the authorized manifest no longer contains keys the mapping names: the operator **converges the managed Secret to what is now authorized** — for a full grant removal, that is scrubbing it.

**The honest split between 2 and 3, because an earlier draft blurred it:** *revoking the credential itself* lands in case 2 — a dead credential can never make the "successful contact" that convergence requires, so the last-synced Secret persists until CR deletion or re-credentialing, and the server cannot recall it. An operator who wants the cluster to *converge* must **remove the grants while the credential still authenticates** (or replace the credential and let the new identity's manifest govern); revoke-the-token-and-done leaves delivered values standing. The documentation states this as the operational rule, not a footnote. During a partition neither case can bite — the operator cannot learn of a revocation it cannot fetch. The guarantee is *revocation of authorization converges the cluster at the next successful authenticated contact*; there is no timer pretending otherwise. A Compose-style hard maximum age was **rejected**: #18's snapshot enforces expiry client-side against its own ciphertext, but an operator scrubbing Secrets it merely cannot confirm converts every network partition into a cluster-wide outage — the self-inflicted failure #17 rejects. The residual after a scrub is also stated: running pods keep their environment until restarted, exactly as Compose's running containers do.

**Delivery is all-or-nothing against the resolved manifest** (#18, transferred), **scoped to the managed Secret's contents**: if the manifest contains secret occurrences the principal cannot reveal, nothing syncs, and the condition names the undelivered keys and the required per-project machine-`reveal` opt-in. A fresh workload principal therefore delivers config and secret-presence only — the five-step journey from #18 appears in the K8s docs too, with the CR condition as the failing step's voice. Partial sync is rejected for #18's reason: the symptom would otherwise surface as the application's own crash three layers away. One Kubernetes caveat sits **past** that boundary and is documented rather than owned: `envFrom` **silently skips** keys whose names are invalid environment-variable identifiers while starting the pod anyway — partial delivery by Kubernetes, after Hikyo's guarantee ends. Sync warns on mapped key names that `envFrom` would skip; #12's key grammar makes this rare, not impossible (a key legitimately consumed via volume mount may carry any name).

## Loader-control keys — same rule, consumption-agnostic, and honest about why

#18 propagates its loader-control baseline (`LD_*`, `PATH`, `NODE_OPTIONS`, …) to this ADR **for environment-variable delivery**. The operator, though, writes a Secret without knowing how it will be consumed — `envFrom` (the integrity risk) or a volume mount (a narrower risk: the content is data unless the application executes it). Inspecting referencing workloads at sync time was considered and rejected as TOCTOU theatre — a reference can appear one second after delivery.

**Therefore: the refusal is enforced at delivery, consumption-agnostic.** A sync whose mapping delivers a key on the baseline fails with a condition naming the keys, unless the `HikyoSecret` carries an explicit acknowledgement listing exactly those keys. **The acknowledgement is a CR-author act, stated as such** — an earlier draft called it an "operator act, API-server-audited", which oversold both halves: any principal who can edit the CR can set it (no separate authority gates it), and Kubernetes audit logging is a cluster option K3s does not even enable by default. What makes it a record is Hikyo's side: **the fetch request carries the acknowledged key list, and the server's fetch audit event records it** (#24) — so *which acknowledgement was in force, for which target, under which credential, for every delivery* is answerable from Hikyo's own append-only log regardless of cluster audit posture. What that log **cannot** answer, stated honestly, is *which Kubernetes principal edited the acknowledgement into the CR* — the fetch arrives under the workload credential, and attributing the CR edit needs cluster audit logging, a cluster option K3s leaves off by default; the docs recommend enabling it where that attribution matters. The cost is stated: a Secret destined only for file mounts still needs the acknowledgement for a key named `PATH`. That is the price of not pretending to know what cannot be known at delivery time. Baseline inheritance rules are #18's: #25 may extend, never silently shrink; declaration-time warning stays a UI affordance.

**File projection is the narrower risk #18 told this ADR to state separately, stated:** a file-projected Secret does not reach the loader; the risk is the application treating file content as executable configuration (a sourced shell fragment, an interpreted config). That is an application property Hikyo cannot see, and no name list addresses it; it belongs with the workload-integrity residual the permission model already carries.

**The delivery projection is a server-side authorized term, never a client-side filter** (#18, transferred): an `HikyoSecret` declaring config-only receives the config projection as its authorized manifest, the request is recorded as such in the fetch audit, and the projection is bound into the conditional-fetch cursor. The operator filters nothing.

## Refresh — conditional fetch is mandatory, and the cursor must prove local state

Locked by #17 and restated: the reconcile loop's periodic resync presents the **authorization-bound cursor**, so a resync interval in seconds does not become a per-key disclosure rate. A cursor-less fetch is never a normal resync; repeated cursor-less fetching by one credential is the signal #17 says the server surfaces. A "current" answer delivers no plaintext and writes nothing. Per-key disclosure events are never aggregated (#17).

**Cursor eligibility is #18's rule transferred, and it must cover cluster-side state, because "current" writes nothing:** a cursor is presented **only while the delivery it recorded is verifiably in effect** — the managed Secret exists, is controller-owned by this CR, and its content matches the last recorded stamp; and the cursor's bound terms are unchanged: credential identity, environment, pin generation, authorized delivery projection, **a digest of the full mapping** (source key ids *and* destination names — renaming a destination key changes delivery without changing the source set), the managed-Secret target, the `HikyoInstance` UID, and the stamp-key version. Any mismatch — a deleted or tampered Secret, an edited mapping, a retargeted CR — discards the cursor and performs a **full authorized fetch** with its per-key disclosure events. Without the local-state check, a deleted managed Secret meets "current", receives no plaintext, and stays gone forever. A cursor is never advanced after a rejected or failed sync (§ *Write ordering*).

Default `resyncInterval` and backoff curves are operations-spec values. Push/webhook-based instant sync is deferred, recorded not dropped — it would ride the same conditional-fetch machinery and is a differentiator Infisical paywalls — but a push channel is new attack surface and new availability coupling, and v1's restart-to-apply semantics make polling latency acceptable.

## Scoping — RBAC is the authority; configuration is derived from it, never beside it

**One operator install per cluster; the admin chooses its reach at install time**: cluster-wide, or an explicit namespace set. **RBAC is the authority in both modes.** In the namespaced mode the operator also needs to know which namespaces to open watches against — Kubernetes has no "watch wherever I happen to be authorized" verb, so a namespace list must exist in configuration. It is **derived, not authoritative**: the install tooling generates the RoleBindings *and* the watch list from the same single input, and the operator's effective reach is the **intersection** of the watch list and what RBAC actually grants — a namespace in the list without bindings produces visible authorization errors, never silent partial function, and a binding without a list entry grants nothing because nothing watches it. What this forbids is the common operator shape where RBAC is granted broad and a config allowlist does the real scoping — there, an auditor reading RBAC reads a lie, which is #15's second-authority-language argument landing here.

Visibility is honest per mode: in the cluster-wide install, a CR anywhere is seen, and one in a namespace the admin excluded from *authority* gets a visible unreconciled condition. In the namespaced install the operator **cannot see** a CR outside its watch list and makes no promise about it; surfacing orphaned CRs there belongs to CLI tooling and docs, not to a controller that would need cluster-wide read to keep the promise.

Verb surface, per bound namespace: get/list/watch on `HikyoSecret` **plus update/patch on its `status`**; create/patch on Events; get/create/update/patch on Secrets; get/list/watch/patch on Deployments/StatefulSets/DaemonSets (trigger only — omitted entirely when triggering is disabled); get on ServiceAccounts and create on `serviceaccounts/token` (federation path only, `resourceNames`-restricted per § *Identity*). Cluster-scoped: read on `HikyoInstance` and the CRDs. Nothing touches Secrets cluster-wide unless the admin chose the cluster-wide binding.

*Rejected: config allowlist with broad RBAC* — above. *Rejected: per-namespace operator instances* — N× footprint on Pi-class nodes, and the one thing needing centralization (the connection endpoint) is already the cluster-scoped `HikyoInstance`.

## Beside and beyond the operator

Ships with v1 at documentation cost only:

- **CLI-in-pipeline**: render at deploy time and `kubectl apply` — **render-and-apply, never render-and-commit**; the GitOps repo holds no values (#13's boundary, transferred). The docs page MUST state that this path is a `values export` under #15's full formula — granting CI `reveal` is the explicit opt-in #13 fixes, never implied by pipeline convenience.
- **User-authored init container**: `hikyo run`/export in an initContainer writing to a shared volume, for the operator-averse. A pattern page, zero Hikyo-side code. Its failure mode is stated with it: Hikyo unreachable at pod start blocks the pod — the inverse of the operator's stale-but-valid stance, chosen knowingly by whoever picks this pattern.

**Named extension path: an upstream ESO provider, post-API-freeze.** Committed as direction, not as a versioned deliverable: ESO supports only its latest minor, so shipping a provider means adopting a monthly upstream train, and that ongoing cost is recorded here rather than discovered later. Out-of-tree/forked providers are rejected as worst-of-both.

**Expansion-ready, as a binding constraint rather than a hope:** the fetch/manifest/cursor/projection API the operator consumes MUST be integration-neutral — no operator-special server endpoints — so an ESO provider, a future push channel, or any later mechanism is purely an additional client of the same surface. Binds #25.

**Recorded rejections** (research grounds, adopted): CSI provider — alpha rotation/sync, two DaemonSets on every Pi-class node, pod-start hard dependency on Hikyo, and its unique no-datastore-persistence property serves a compliance demand the target persona has not made. Webhook injector — highest build cost, webhook-down failure couples pod scheduling to Hikyo, sidecar renewal has no job under restart-to-apply. Revisit either only on a concrete never-in-etcd demand.

## Reconciliation with upstream ADRs

- **Threat model ([#8](https://github.com/Hikyo-Org/Hikyo/issues/8))** — workload credentials scoped `(project, environment)`, read-only allowlist; per-fetch audit with credential identity. The managed Secret is plaintext at rest *in the cluster's trust domain*, stated honestly with the K3s encryption callout; nothing here weakens the stolen-DB/backup headline, which concerns Hikyo's own store.
- **Revisions ([#11](https://github.com/Hikyo-Org/Hikyo/issues/11))** — the keyed-not-bare rule honoured in the annotation; **amended** on who supplies the annotation value (declared amendment above). Changes apply on restart via Kubernetes' own rollout for environment consumption; volume-mount live update is Kubernetes' semantics, stated.
- **Schema ([#12](https://github.com/Hikyo-Org/Hikyo/issues/12))** — the change token is consumed as cursor material (**amended** as declared above); key ids are the mapping's source identity; NUL-free UTF-8 relied on.
- **Encryption ([#14](https://github.com/Hikyo-Org/Hikyo/issues/14))** — the operator's stamp root is a client-side key outside the server hierarchy, HKDF-derived per target, following #18's precedent of matching #14's primitives; the rollout-wave expectation on token-key rotation is **amended** as declared above.
- **Permissions ([#15](https://github.com/Hikyo-Org/Hikyo/issues/15))** — every fetch is a `values export` carrying the full formula; machine-`reveal` stays the explicit per-project opt-in; the operator holds no authority of its own, so no new authorization path exists to audit.
- **Human auth ([#16](https://github.com/Hikyo-Org/Hikyo/issues/16))** — nothing in-cluster ever uses a human session; bootstrap-token display rules apply to the CLI mint that produces the bootstrap Secret's content.
- **Machine identities ([#17](https://github.com/Hikyo-Org/Hikyo/issues/17))** — both credential kinds; conditional fetch with the authorization-bound cursor; expiry as CR condition and event; byte-exact bindings, mandatory audience, K3s callout: all satisfied above.
- **Compose ([#18](https://github.com/Hikyo-Org/Hikyo/issues/18))** — one stamp explanation across both integrations (keyed HMAC, per-target, local key material, version-prefixed; label there, pod-template annotation here); integrity amendment inherited for env delivery with file projection stated separately; loader-control baseline inherited with the per-CR acknowledgement; all-or-nothing and the projection-as-authorized-term rules transferred; cursor eligibility extended to cluster-side state on #18's own pattern.

## Propagations (binding on downstream tickets)

- **Architecture ([#22](https://github.com/Hikyo-Org/Hikyo/issues/22))** — the operator is a separate deployable, not a server mode; MUST fix its stack (controller-runtime is the presumption) and the custody model for the operator's stamp root.
- **Tenant isolation ([#23](https://github.com/Hikyo-Org/Hikyo/issues/23))** — per-CR identity means cross-tenant reach in-cluster reduces to Hikyo-side grants; #23 owns proving the server never lets one project's credential resolve another's material, and inherits "no operator-wide principal" as a standing constraint.
- **Audit ([#24](https://github.com/Hikyo-Org/Hikyo/issues/24))** — event shapes for: operator delivering fetch, conditional fetch answering "current", all-or-nothing refusal naming keys, loader-control refusal, **the acknowledged-key list carried on a fetch**, authoritative-refusal convergence (scrub), config-only projection fetch.
- **API & CLI ([#25](https://github.com/Hikyo-Org/Hikyo/issues/25))** — integration-neutral fetch/manifest/cursor/projection surface (no operator-special endpoints); API group/kind/field spellings including the designation label and the workload opt-in annotation; the CLI verb that mints a bootstrap Secret's token honouring #17's display rules; MAY extend, never silently shrink, the loader-control baseline.
- **MVP boundary ([#26](https://github.com/Hikyo-Org/Hikyo/issues/26))** — explicit in/out for: rollout triggering in v1 (presumed in), federation path in v1 (presumed in, it is #17's recommendation), ESO provider timing, push-based sync (presumed out).
- **Operations spec (fog)** — default `resyncInterval`; retry/backoff and rate limits as they apply to operator fetch; JWKS bounds per cluster; operator resource requests/limits; stamp-root rotation guidance; the K3s `--secrets-encryption` runbook including the `secretbox` version floor.
- **UI (fog)** — the service-account and credential surfaces already carry the K8s-relevant affordances (#17); add the CR-condition vocabulary to the workload-integration setup screens so the five-step journey reads the same in `kubectl` and in the UI.

## Deferred (recorded, not dropped)

- **Push/webhook-based instant sync** — differentiator potential (Infisical paywalls it), same conditional-fetch machinery, new attack surface; nothing about restart-to-apply needs it.
- **ESO provider** — post-API-freeze, monthly-train cost stated above.
- **CSI provider / webhook injector** — revisit on a concrete never-in-etcd demand.
- **Per-namespace operator instances** — revisit only if a multi-tenant install demands hard operator-level isolation that RoleBindings cannot express.
