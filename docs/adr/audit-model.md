# Envweave audit logging & event model (ADR, locked 2026-08-02)

Details in [multi-instance.md](./multi-instance.md).

Context: the audit trail's *integrity and durability stance* is fixed by the threat model ([#8](https://github.com/Dunky13/envweave/issues/8)): append-only at the application layer with no delete/update API, durable-before-completion for internal operations, INTENT/OUTCOME pairs around external effects, growth retention-managed and never silently dropped, not tamper-proof against the operator in v1. The *cardinality* rules are fixed by the permission ADR ([#15](https://github.com/Dunky13/envweave/issues/15)) — one event per disclosed key, never "revealed 40 secrets", denials audited — and hardened by the machine-identity ADR ([#17](https://github.com/Dunky13/envweave/issues/17)): no successful fetch is ever aggregated, a conditional fetch emits one immutable access record, the fetch envelope is a container and never a substitute, aggregation is licensed for authentication-failure floods ([#16](https://github.com/Dunky13/envweave/issues/16)). The *tenancy* of audit rows and reads is fixed by tenant isolation ([#23](https://github.com/Dunky13/envweave/issues/23)): events carry the acted-on scope's id chain, audit reads are proof-scoped like any other tenant read. The *storage substrate* is fixed by the architecture ([#22](https://github.com/Dunky13/envweave/issues/22)): sqlite runs `synchronous=FULL` precisely so audit commits are durable, the adapter outbox carries linkage to its INTENT/OUTCOME records, and audit-retention pruning is one of the in-process scheduler's jobs. What every one of those ADRs explicitly delegated here is the rest: **who may read the trail, what an event is, how the catalogue is organized and kept complete, how denial volume is handled, how the trail is stored and exported, where the audit trail ends and operational logging begins, and the retention and tamper-resistance boundary.** This ADR fixes those.

Granularity note: this is the wayfinding-level audit ADR. It fixes the reader capability, the event envelope, the catalogue's organization and closure mechanism, denial durability, the storage and export shape, the log-redaction boundary, and the retention classes. Mechanism-level detail is delegated: the audit query/export endpoints and CLI verbs with their authorization formulas → API & CLI ([#25](https://github.com/Dunky13/envweave/issues/25)); the adapter event payloads' final field spellings → deployment-module seam ([#28](https://github.com/Dunky13/envweave/issues/28)); every concrete retention default, export response bound, free-text field bound and rate value → operations spec ([#32](https://github.com/Dunky13/envweave/issues/32)); the audit view's interaction design → the app-chrome prototype ([#29](https://github.com/Dunky13/envweave/issues/29)); in/out confirmation of the extension paths → MVP boundary ([#26](https://github.com/Dunky13/envweave/issues/26)). Each delegated ticket MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

> **Amends the permission ADR ([permission-model.md § Capability atoms](./permission-model.md), [#15](https://github.com/Dunky13/envweave/issues/15)), the human-auth ADR ([human-auth.md § Assurance](./human-auth.md), [#16](https://github.com/Dunky13/envweave/issues/16)), and the tenant-isolation ADR ([tenant-isolation.md](./tenant-isolation.md), [#23](https://github.com/Dunky13/envweave/issues/23)), five declared parts.** Both #15 and [#23](https://github.com/Dunky13/envweave/issues/23) explicitly delegate "the read capability's exact placement" to this ticket; the amendment shape follows #16's `credential-reset` precedent. **(1)** **`audit-read`** joins the capability set as an ordinary grant `(principal, audit-read, scope)`: grantable at environment, project, org or instance scope, additive, downward-inheriting, no denies. The **`admin` template seeds it** (org admins are trusted within their org per the threat model, and incident response needs the trail); the **`operator` template does not** — the operator set is crypto custody, not surveillance, exactly the argument that keeps `reveal` out of it; an operator holding instance `manage-members` can self-grant, audited and visible. **(2)** **`audit-read` joins #16's MFA-mandatory capability list.** The trail holds identities, source IPs, key metadata and incident history — surveillance-grade material; a session authenticated through a single-factor OIDC provider must not export it. The list was closed; this is a declared widening, not a reinterpretation. **(3)** **The `automation` machine allowlist gains `audit-read`** (amending #15's normative allowlist, restated by #17). A machine holding it can run the scheduled off-box export this ADR names as the interim tamper mitigation, and the post-v1 external-sink extension needs the same authority. The shape has locked precedent: `reveal` is MFA-mandatory for humans yet grantable to machines by explicit opt-in — machines do not reauthenticate ([#15](https://github.com/Dunky13/envweave/issues/15), [#17](https://github.com/Dunky13/envweave/issues/17)); their control is narrow scope, individual revocability, and the per-query audit event this ADR makes unconditional. The `workload` allowlist is untouched. **(4)** **#23's enumerated authorization-package interface gains exactly one write path: the denial writer.** That interface was enumerated as read-only resolution; a failed `authorize()` mints no proof, yet #15 requires the denial audited — so the fail path itself writes the denial event, in-transaction, import-bounded, covered by CI invariant 6. The trusted surface grows by one enumerated, fixture-pinned member; no general write authority is added. **(5)** **The audit tables carry the denormalized immutable id chain *without* #23's composite ancestry FKs.** An audit event must outlive its subject — a deleted key, a revoked credential, a released pin, a deleted environment — so referential integrity to live parent rows is structurally wrong for this one table family; enforcing it would either block domain deletions or cascade-destroy history. Everything else in #23's row discipline applies unchanged: declared scope class, chain columns immutable (analyzer-enforced, no `SET` ever), the top-level chain conjunct in every query. The composite-FK rule remains binding on every tenant-owned *domain* table; the audit tables are its single declared exception.

## The reader model — `audit-read`

Audit events are metadata-rich: key names, principal identities, who revealed what and when, who was denied what. Reading the trail is **surveillance power over colleagues** — distinct from managing them, distinct from reading their data. It therefore gets its own capability rather than riding on an existing one.

*Rejected: fold audit reading into `manage-members`.* Cheaper by one capability, but it bundles surveillance with administration — exactly the "separate grants, not bundles" rule #15 exists to enforce — and makes stripping audit visibility from one administrator impossible without dismantling their administrative authority. The `admin` *template* seeding `audit-read` as an independent revocable grant delivers the same default reach without the bundle.

*Rejected: a split `audit-read` (own actions only) / `audit-read-all` (scope-wide).* Self-view is a UI affordance, not an authority boundary — a principal's own actions are facts they already know. If a self-view ships, it is a filter over the scope-wide capability's UI, not a second capability doubling the model.

**Audit reads are ordinary proof-scoped reads.** Per #23, every audit query resolves through the same proof discipline as any other store access: tenant events carry the acted-on scope's id chain, the query is filtered in-SQL by the proof's chain, and a scope the caller may not `audit-read` is **nonexistent** in the uniform sense #15 fixes — same response shape, no counts, no timing signal from the application layer. `audit-read` at org scope reads every event chained under that org; at environment scope, only that environment's events. **Instance-scoped audit reads** (the instance trail below) run under an `InstanceProof` minted against an instance-scope `audit-read` grant — grant-evaluated like `backup-export`, never route-implied.

**Reading the trail is itself audited — unconditionally.** Every audit query and every export emits its own event(s) (§ *Storage and export* fixes the shapes), carrying the caller's **normalized filter parameters** and result count — never one event per row returned. One event per query is human-volume: cheap, and structurally free of self-amplification (an audit-read event does not trigger a read). A configuration toggle for this was considered and **rejected**: a knob on trail completeness makes "was this access recorded" installation-dependent — the one property an auditor must not need to check configuration to know — and the off-switch would sit in exactly the hand the record restrains, the same guard-holding-its-own-off-switch shape #15 rejects for `project-settings`. The cost avoided by a toggle is negligible; the invariant it would break is not.

**Assurance, stated as a recorded decision:** interactive queries and exports both require the MFA-mandatory assurance floor (amendment part 2) and both emit their own events; **no additional reauthentication ceremony gates them**. The reveal-window ceremony exists for plaintext disclosure; the trail contains none by construction, and the per-query audit closes the who-watched loop. Machines are governed by the allowlist entry, not assurance, per the locked machines-do-not-reauthenticate rule.

## The event envelope

Every event, regardless of type, carries:

| Field | Content |
|---|---|
| `id` | UUIDv7 — time-ordered, the project's id pattern |
| `seq` | **per-table** allocation-ordered integer, unique and strictly increasing at allocation within its trail (postgres `bigserial`; sqlite `INTEGER PRIMARY KEY AUTOINCREMENT`, which never reuses a value — plain rowids can). The two trails are two independent sequences; no cross-trail order is defined or promised — see § *Storage* |
| `occurred_at` | UTC. For offline-reconciled records this is **client-asserted** and flagged as such |
| `recorded_at` | UTC, server-assigned at durable insert — authoritative for retention and display ordering; diverges honestly from `occurred_at` for reconciled records |
| `type`, `schema_version` | catalogue type (`category.action`) plus the version of that type's payload schema |
| `actor` | principal id, principal class (`human` \| `machine` \| `system` \| `break-glass` \| `unauthenticated`), and the credential artifact id that authenticated the act (session id, machine credential id). **Nullable as a structured fact**: an unknown-account login failure, a bootstrap failed presentation, a pre-auth admission event have no principal and no credential — `class: unauthenticated` with null ids, never a dummy principal |
| `authority` | the **recorded authority principal** when the act runs under a standing delegation — adapter push, pinned fetch — distinct from `actor` per #15's authority-principal rule; null when the actor acts directly |
| `scope_class` + `scope_chain` | the acted-on scope's class (`instance` \| `org` \| `project` \| `env`) and its immutable id chain **to that class** (empty for `instance`), matching #23's per-class row shapes — never one universal tuple |
| `object` | acted-on type + immutable id — key id, revision number, pin id, grant id, credential id, service-account id, binding id, adapter id, CR target. Immutable ids, never mutable names, per the schema ADR's identity rule. **Nullable** where the event has no object (an admission-threshold crossing) |
| `outcome` | `intent` \| `success` \| `denied` \| `failure` \| `unknown` \| `disconnected` — one enum, no payload shadow-outcomes. **Which values a type may carry is registry data, CI-checked**: `intent` only on INTENT-phase events (`adapter.push_intent`, `audit.export_started`); `unknown` only on external-effect terminal outcomes where the effect's fate is genuinely indeterminate (#8's adapter OUTCOME); `disconnected` only on `audit.export_completed`; every other type is restricted to `success`/`denied`/`failure` |
| `correlation_id` | request id for request-scoped work; **outbox job id for adapter INTENT/OUTCOME pairs** (the #22 linkage); fetch-envelope id doubles as the correlation for a fetch's per-key events; export-started event id for the export pair |
| `source_ip`, `user_agent` | recorded on **every** event; null only where structurally absent — a system-principal act, an offline-reconciled record whose origin endpoint no longer exists. Absence is a structural fact, never a redaction |
| `origin` | `web` \| `cli` \| `api` \| `operator-fetch` \| `adapter-job` \| `offline-reconciled` \| `system` |
| `payload` | the per-type fields, validated against the type's registered schema at write time |

**Free-text hygiene — envelope fields included, not just payloads.** `user_agent`, client-supplied provenance claims (#13's `commit`/`ref`/`actor`), and every other caller-originated string is **attacker-influencable input landing in a durable surveillance record**, so it is treated at the trust boundary like any other input: **length-bounded** (concrete bounds → ops spec, under #8's bounded-payload baseline), UTF-8-sanitized, stored as data and never interpreted, and — using the scannability #17 built into the token format deliberately — **passed through a token-grammar redaction filter**: any substring matching the `ew_<v>_<type>_…` grammar is replaced with a redaction marker before write, so a bearer token accidentally pasted into a User-Agent, a provenance string or a filter value never persists in the trail. Filter parameters on `audit.*` events are recorded as the **parsed, normalized filter structure**, never the raw query string. What this filter cannot catch is stated plainly: an arbitrary secret *value* embedded in caller free-text has no recognizable grammar; the bound and the schema-typed fields limit the blast, and Envweave's own material never enters these fields by construction.

**What a payload must never contain**, restating the locked rules as one enforcement point: secret plaintext (the event records *that* key `K` at revision `R` was disclosed, never what it said); token or credential material (credential *ids*, never bearer strings, verifiers or their prefixes); password, MFA seed or recovery-code material; instance-derived JSON paths (schema locations only, per the schema ADR — the `/AKIA…` leak lands in the audit record otherwise); and reclassification events recorded under **the stricter of the pre- and post-change classification** (schema ADR, restated). Payload validation happens at the write boundary; an event that fails its schema is a bug that **fails the operation** (fail-closed — an internal operation without its durable audit record does not complete, per #8).

**The fetch envelope** (#17) is a storage-level container: a delivering fetch inserts one envelope row carrying the shared context — credential, service-account principal, principal class, project, environment, resolved revision, change-token version, projection, transport, outcome, the K8s acknowledged-key list where present (#19) — and one per-key disclosure event per delivered key referencing it. The envelope never substitutes for the per-key events; a conditional fetch that delivered nothing emits one access record and no per-key events. **An envelope and its per-key events are one retention unit**: same retention class, pruned together atomically, never a dangling reference in either direction (CI invariant 9).

**Offline records** (#18): the client's per-key local records are fsynced before plaintext release, then uploaded on authenticated reconnect. Reconciliation inserts them as ordinary events with `origin: offline-reconciled`, client-asserted `occurred_at`, server `recorded_at` and `seq` at insertion time, and the serving credential recorded **even when since revoked** — a since-revoked credential's offline serves are exactly the records reconciliation exists to surface. A client clock is not trusted for ordering or retention; both key off `recorded_at`.

## The catalogue — a closed registry

Event types are a **closed enum**, named `category.action`, each declared in one registry with its payload schema, schema version and retention class. An unregistered type cannot be written; an unvalidated payload cannot be written. **The normative completeness rule, which is the lock:** the registry MUST contain every event an upstream locked ADR requires — the MUST-emit propagations of #8, #11, #12, #13, #14, #15, #16, #17, #18, #19, #22, #23 — and shrinking it below any upstream requirement reopens the ADR that demanded the missing event. **Completeness is a CI invariant, not a review habit — wired to the registry that is actually total.** #23 has two registries: the authorization/formula registry (proof-bearing operations) and the **probe-classification registry**, which is total over *every* entry point — endpoints, CLI verbs, outbox job types, SSE emits, system entry points — across all four classes including `unauthenticated` and `system`, with unclassified failing the build. This ADR ties the catalogue to the **probe-classification registry**: every classified operation maps to one or more event types, or carries an explicit `audited: none` annotation. Because classification is total, login, bootstrap, boot, migration and break-glass are all covered — the authorization registry alone would miss exactly the principal-less paths. **`audited: none` is default-deny, not free-text-excused**: the build **permits** it only for operations that are probe-class *tenant-scoped*, whose authorization formula is **`read` alone**, and which mutate nothing — proof-scoped pure reads whose result the trail would only duplicate (a filtered environment listing). Every other operation — every `unauthenticated` and `system` class operation (upstream mandates auditing all of them: bootstrap, login, admission, boot, migration, break-glass), every `audit-read` operation, every formula beyond bare `read` — is refused the annotation and must map to event types. The reason field is for humans; the permit rule is for the machine.

## Denials — per-event, durable before the response, emitted where the truth lives

An authorization denial from an authenticated principal is an operation outcome, and it takes the same durability rule as every internal operation: **the denial event is durable before the error response is sent.** No async fire-and-forget path exists for it — a crash that loses the probe trail loses it precisely when someone is probing, which is the case the trail exists for.

**Emission is a function of the authorization package — inside #23's trusted set — not a store call carrying a proof.** #23's universal-proof rule exempts exactly one surface: the authorization package's enumerated resolution interface. That interface was enumerated **read-only**, so extending it with a write is not a reinterpretation — it is **amendment part 4, declared at the top**: the interface gains exactly one write path, the denial writer. A failed `authorize()` cannot mint a proof (there is nothing to prove), so the fail path itself writes the denial event within its own transaction. The surface stays enumerated, import-bounded, fixture-pinned and the highest-scrutiny code in the repo per #23; no general write authority is added, and CI invariant 6 asserts the denial writer is the interface's only writer.

**The scope chain recorded is the chain as resolved, never as claimed.** Two denial shapes exist, matching #23's zero-rows semantics:

- **Resolvable, unauthorized**: the addressed scope exists and resolved in-tenant, the capability check failed. The event carries the truthful resolved chain and lands in the tenant trail — org A's `audit-read` holders see org A being probed by org A's own principals.
- **Unresolvable**: the addressed identifiers matched zero rows — foreign tenant or genuinely nonexistent, indistinguishable by design and *recorded* indistinguishably: no chain exists, so none is recorded. The event lands in the **instance trail** with the addressed identifiers preserved in the payload as **caller-asserted claims**, bounded and sanitized like all free text. Recording a foreign org's real chain in that org's trail would itself be an oracle (org B's auditors learning org A's principal probed them presumes the resolution the response denied); recording it in the prober's org would attach a foreign chain to the wrong tenant. The instance trail is where cross-boundary probing is an operator-visible pattern.

Denial volume needs no new valve. Per-principal rate limits (#8's availability baseline) throttle an account spraying denied requests before audit storage feels it, and a denial spray from one principal is exactly the signal that must stay row-per-event: an account probing its authorization boundary. **The aggregation licence is #16's, restated at its locked width, not narrowed**: audit writes under **authentication-failure floods** — login, reauthentication, recovery, bootstrap and token presentation, admission-threshold events — are "aggregable under flood without silent loss". That licence covers authentication failures wherever they occur, including post-session reauthentication; it does not extend to authorization denials, which are #15's per-event obligation, nor to any successful operation (#17).

Denial events carry the operation attempted, the resolution shape (resolvable/unresolvable), and the formula that failed **by name, never by missing-grant enumeration** — a denial payload that lists which grants the caller lacks is an authorization oracle handed to the probing account the moment any audit surface leaks. The caller-facing response stays #15's uniform nonexistent; the trail records the richer truth for the `audit-read` holder.

## Storage and export

**Two append-only tables, because #23 demands declared scope classes and the trail spans two.** The **tenant trail** (`audit_tenant_events`) is declared **org-owned**: `org_id` always present and always the top-level chain conjunct #23's SQL analyzer requires; `project_id`/`env_id` are refinement columns, present exactly when `scope_class` is `project`/`env`, and refinement predicates compose on top of the org conjunct for narrower proofs. The **instance trail** (`audit_instance_events`) holds instance-, system- and unauthenticated-class events — rotations, backup/restore, recovery, bootstrap, admission events, unresolvable denials — and is read only under an `InstanceProof` minted against instance `audit-read`; its queries carry #23's content-pinned `instance-scoped` annotation. **Audit rows carry the chain as immutable denormalized ids, deliberately without ancestry FKs** — an audit event must outlive its subject (a deleted key, a revoked credential, a released pin), so referential integrity to live objects is structurally wrong here; #23's composite-FK rule governs tenant-owned *domain* rows, and the audit tables' conformance is via the declared scope class, the chain columns, the analyzer's conjunct rule and chain-column immutability, all of which apply unchanged. **Org deletion**: the org's tenant trail is deleted with the org — no orphaned surveillance data under an unreachable scope — and the deletion itself is an instance-trail `recovery.org_deleted` event recording org identity and per-category event counts; the docs direct an operator wanting the history to export it first.

**`seq`, honestly.** `seq` is unique and strictly increasing **at allocation, per table** — the tenant trail and the instance trail are two independent sequences, and no cross-trail order exists. On sqlite, the single write connection (#22) makes allocation order and commit order identical. On postgres, sequence allocation precedes commit and **commit order can differ** — stated, not papered over: `seq` is **not** a commit-order total, `recorded_at` is wall-clock, and neither is sold as a forensic total order under postgres concurrency. Display and pagination order is `(recorded_at, seq)`. **The hash-chain hook is schema headroom, not an ordering guarantee**: a future chain extension must introduce its own serialization point (a single-writer chain appender or equivalent) and its own pruning-anchor protocol; this ADR hands it stable ids, allocation-ordered `seq`, and content — nothing more. Gaplessness is promised nowhere: retention prunes rows, and `AUTOINCREMENT`/`bigserial` may skip.

**Durability is boot-enforced on both engines, not folklore on one.** sqlite: `synchronous=FULL`, already boot-refused by #22. postgres: **boot verifies `fsync=on` and `synchronous_commit=on` and refuses to start otherwise** — the same no-silent-downgrade posture #22 fixes for pragmas, extended to the engine where durability is a server setting; and the store package never issues `SET synchronous_commit` at session or transaction level (lint-banned alongside #23's analyzer rules). A deployment that wants async commit for other workloads runs Envweave against a database configured for durable commits or does not run it.

**The application layer holds INSERT and SELECT only.** No UPDATE or DELETE statement on either audit table exists in any query file — **a CI invariant in the same style as #23's analyzers** — with two named exceptions, both content-pinned like #23's `instance-scoped` allowlist entries: the retention-pruning job's deletion query, and the org-deletion cascade's trail deletion. Pruning runs are themselves security-class events, so pruning cannot erase the record of pruning within policy.

**Interactive queries are bounded pages, exports are sequences of bounded pages, and the event shapes differ accordingly.** A trail **query** returns a bounded page (#8's bounded-response rule) and emits **one event, durable before the response**, carrying normalized filters and the page's row count — implementable because the page is materialized before send. An **export streams a sequence of committed page reads**: each page is read in its own transaction under a **fresh transaction-bound proof, re-authorized per page** — #15's re-authorize-before-every-sensitive-step and #23's proof-dies-with-its-transaction rules applied literally, so revoking `audit-read` mid-export stops the stream at the next page boundary — and **only committed page data is ever emitted**, so no byte crosses the response boundary ahead of its transaction (#22's rule). The event pair takes the locked INTENT/OUTCOME shape for external effects (#8): **`audit.export_started`** durable **before the first byte**, carrying the normalized filters; **`audit.export_completed`** durable at termination, carrying rows streamed and terminal outcome (`success` / `failure` — including mid-export revocation, with cause / `disconnected`), correlated by the started event's id. An export with a started record and no completed record is a visible reconciliation case, exactly like an outbox push with INTENT and no OUTCOME. Page size → ops spec.

**Export format is JSONL**: one schema-versioned event per line, filterable by time range, category, type, scope and actor. It ships as an API route and a CLI verb, both gated `audit-read` at the addressed scope under the ordinary proof discipline. The export contains exactly what the table holds — payloads included, plaintext excluded by construction because it was never written.

## Operational logs are not the audit trail

The boundary, stated as rules:

- **Ops logs may carry metadata**: org/project/environment/key names, principal ids, event references, correlation ids. The threat model already classes names as secondary assets with accepted exposure, and the primary persona reads `docker logs` to debug — id-only logs would hand the homelab operator id soup to protect data their own DB already shows them.
- **Ops logs must never carry**: secret values of either classification, token or credential material (credential ids only — never bearer strings), password/MFA/verifier material, instance-derived JSON paths (the schema ADR's rule holds in logs identically), or the payload body of any disclosure-class audit event.
- **Enforcement is structural where the language allows and guardrail where it does not, stated as which is which.** The sensitive types — secret value, token, verifier, key material — hold their material in unexported fields and implement the **full formatting surface as redaction**: `String()` and `GoString()` returning a redaction marker (these are what `fmt` actually consults for `%v`/`%s`/`%#v` — `slog.LogValuer` governs `slog` only and `fmt` never calls it), `LogValue()` for slog, and `MarshalText`/`MarshalJSON` for encoders. An accidental `%v` on a sensitive type therefore prints the marker, not the fields. **The honest limits**: reflection-based access, deliberate field extraction inside the owning package, and third-party serializers that bypass the marshal interfaces can still leak — so a lint rule bans formatting or marshaling expressions on sensitive types outside their owning package, and the redaction story is a **guardrail with named evasion limits** in #23's sense, never a proof. The residual matches the threat model's stance: no memory-secrecy claim exists anywhere.
- **Audit events are never mirrored to the ops log.** A stdout copy of the trail is a second audit store with weaker retention, weaker integrity and no proof-scoped reader — every property this ADR fixes, silently unfixed in a log aggregator. The ops log records audit-subsystem **health** — "audit write failed, operation aborted", pruning-job errors, export failures — never event content.

## Retention — two classes; tamper resistance — the boundary stated

**Two retention classes, because the volume problem is one category.** Machine fetch traffic — per-key delivery events, envelopes, conditional-fetch access records — is the unbounded stream #11 names; grant history is not, and one knob covering both serves neither.

- **`access` class**: fetch envelopes and their per-key delivery events (one retention unit, § *Envelope*), conditional-fetch access records, denial events. Own retention period.
- **`security` class**: everything else — grants, credentials, federation, principals, definitions, value publishes, human disclosures, pins, adapters, settings, crypto, recovery, retention, audit-read events. Longer default.

Each class is independently configurable, including to **`unlimited`** — the same single explicit compliance setting #11 gives revision payloads. Class membership is fixed per event type in the registry, not configurable. Concrete defaults → ops spec ([#32](https://github.com/Dunky13/envweave/issues/32)).

**Audit retention is instance state under `instance-config` — never `project-settings`.** #15's `project-settings` names "retention/quota policy", and that is the **project-scoped revision-payload retention and pin quota of #11**, which #11 assigns to its own ADR and the ops spec; the audit log's retention is the thing #11 explicitly severs from it and assigns **here**. Placing audit retention at project scope would hand every project administrator the evidence-window knob for their own project's trail — the retention variant of the off-switch-in-the-restrained-hand shape, and #15 explicitly does not extend org-admin trust to project admins. `instance-config` is an instance capability, therefore MFA-mandatory under #16 already; every retention-class change is a security-class event recording old and new values. **The residual, stated rather than dressed up**: an instance-config holder can shorten retention, act, and wait out the pruning of the evidence including eventually the change event itself. That actor is instance-level — inside the boundary where the threat model already grants operator-equivalence and v1 audit rewriteability. Retention control does not weaken tamper resistance against tenants and low-privilege users, which is the only tamper claim v1 makes.

Pruning is the licensed deleter above: policy-driven, per-class, per retention unit, audited as a security-class event recording range and per-category counts, and **never silent** (#8's "retention-managed, never silently dropped", satisfied literally). Personal-data note for self-hosters, stated in docs rather than engineered around: `source_ip`/`user_agent` live under the same bounded retention, and the operator is the data controller.

**Tamper resistance: v1 is the threat model's stance, unchanged and undecorated.** Append-only at the application layer defends against tenants and low-privilege users; a datastore writer is operator-equivalent and can rewrite the v1 trail — stated, accepted, documented. **No hash chain and no external sink ship in v1.** Stable ids and the schema headroom above are the deliberate hooks; **hash-chaining and an external forwarding sink (syslog/webhook) are the named post-v1 extension path**, recorded at the MVP boundary ([#26](https://github.com/Dunky13/envweave/issues/26)) as explicit exclusions. The interim mitigation is documented, not built, and split honestly by reach: for a **project's slice of the tenant trail**, a scheduled `audit export` under that project's `automation` service account holding project-scope `audit-read` (amendment part 3) shipped off-box — service accounts are project-owned with grants confined to the project subtree (#17), so machine-driven export is **per project, never org- or instance-wide**, and this ADR does not amend that confinement. For **org-wide tenant history and the instance trail**, the off-box copy is the **backup container**: `backup-export` (an existing #15 instance capability) produces the age-encrypted container that includes both audit tables, and the **ops spec owns making it routine** — the threat model already delegates backup procedures there, and this ADR adds the audit-trail motive to that delegation rather than claiming a scheduled job upstream never defined. None of these copies is tamper *proof* — the exporting instance is still the writer — they are operator-independent *copies*, which is all v1 claims.

## CI invariants

1. **Registry closure**: every emitted event type exists in the registry with a payload schema, version and retention class; an unregistered emit fails the build; payload validation failure at runtime fails the emitting operation (fail-closed).
2. **Completeness linkage**: every operation in #23's **probe-classification registry** maps to event type(s) or an explicit `audited: none`; unannotated fails the build; `audited: none` is **default-deny** — permitted only for tenant-scoped, formula-`read`-only, non-mutating operations, refused everywhere else including all `unauthenticated` and `system` class operations.
3. **Append-only**: no UPDATE/DELETE on either audit table in any query file except the two content-pinned deletion queries (pruning; org-deletion cascade), fixture-pinned by name + SQL hash in #23's allowlist style.
4. **No plaintext**: the payload-forbidden-content rules are asserted by tests over every registered payload schema and by the dump-grep test #8 already mandates, extended to both audit tables; the token-grammar redaction filter has round-trip tests over the `ew_` grammar including embedded-in-noise cases.
5. **Cardinality**: fetch-path tests assert one per-key event per delivered key, one access record per conditional fetch, no counter columns, no mutable aggregate anywhere in the audit schema; aggregation appears only on authentication-failure flood paths.
6. **Denial durability and siting**: contract tests assert the denial event is committed before the error response on a denied operation (instrumented commit ordering, #23's effect-port style); the denial writer is import-bounded to the authorization package's enumerated interface **and is that interface's only write path** (amendment part 4) — a second writer fails the build.
7. **Durability settings**: boot refuses postgres without `fsync=on` and `synchronous_commit=on`; `SET synchronous_commit` is lint-banned in the store; sqlite pragma enforcement is #22's, asserted still present.
8. **Redaction**: sensitive types implement the full redaction surface (`String`, `GoString`, `LogValue`, `MarshalText`, `MarshalJSON`); a lint rule bans formatting/marshaling expressions on sensitive types outside their owning package; audit-event content in ops-log emission paths is lint-banned.
9. **Retention units**: an envelope and its per-key events carry the same class and prune atomically; a dangling reference in either direction fails the conformance suite.
10. **Class totality**: every registered event type carries exactly one retention class; unclassed fails the build.
11. **Export pair and paging**: contract tests assert `export_started` is durable before the first streamed byte, a terminal `export_completed` exists on success, failure, revocation and disconnect paths, each page read carries a fresh transaction-bound proof, and a mid-export `audit-read` revocation stops the stream at the next page boundary.
12. **Outcome restriction**: the registry fixes each type's permitted outcome values (`intent`/`unknown`/`disconnected` only where § *Envelope* licenses them); an event written with an unlicensed outcome fails validation, and no payload field shadows the envelope outcome.
13. **FK exception is named, not counted**: `audit_tenant_events` is the **single named** tenant-owned table permitted to omit composite ancestry FKs (amendment part 5 — `audit_instance_events` is instance-scoped and outside the rule); **any other** tenant-owned table without them fails the migration-metadata check, exactly as #23 fixes.
