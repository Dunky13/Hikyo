## 1. Tenancy: the per-org SCIM binding

**SCIM is configured per organisation, as a *binding*: an org-owned configuration object referencing exactly one instance-configured identity provider `(kind ∈ {oidc, saml}, issuer)`.** One IdP provisioning app per org; the binding is the tenant boundary. Uniqueness: **at most one binding per `(org, provider)`**, enforced by constraint — the concurrent-create race resolves to one row, the loser fails closed with the named conflict.

- Provider *configuration* stays instance-scoped under an instance capability ([human-auth.md](./human-auth.md)). The binding holds a **read-only reference** to a configured provider; creating a binding grants no authority over the provider. **While the referenced provider is disabled or removed, the binding's entire wire surface fails closed** — every SCIM request, read or write, is refused with a named error — state is preserved for repair, and the binding enters the attention state (§9). Nothing is silently deleted.
- Binding creation, mutation and deletion, mapping-table administration (§3), and credential mint/rotate/revoke (§7) all require **`manage-members` held at org scope exactly** — not project scope. Mapping rows cause grants the author need not hold, and unheld-capability granting is an org/instance power under the locked escalation asymmetry ([permission-model.md](./permission-model.md)); a project-scope `manage-members` holder must not reach it through SCIM.
- What a binding can cause is bounded by the org subtree: accounts (instance-level principals, as invitation already creates them) plus grants at org/project/environment scopes **inside its own org**. A mapping row naming a scope outside the org is refused at authoring time and again at sync time.

*Rejected: instance-scoped SCIM under `instance-config`.* It makes the operator the membership authority for every org — the operator≡org-admin hardening the SaaS non-preclusion gate ([mvp-boundary.md](./mvp-boundary.md) §3) forbids in API shape. *Rejected: instance-configured, org-consumed.* Two authority languages for one feature.

## 2. Grant origins — the declared permission-model amendment

**Declared amendment to [permission-model.md](./permission-model.md) ([#15](https://github.com/Hikyo-Org/Hikyo/issues/15)): every grant row carries one or more *origins*.** An origin is one of:

- `manual(granted_by)` — every grant that exists today has exactly this;
- `scim(binding, mapping_row, group)` — created by sync under §3;
- `lockout-retention(cause)` — system-minted, §2.4 below;
- `structural(binding)` — system-minted with a SCIM binding, holding exactly the provisioning connection's `scim-provision` grant (§7); released only by the binding-deletion state machine (§6), which retires the principal and the grant atomically. The origin set is exhaustive again: every grant row, including the structural one, carries a valid origin.

The amendment is bookkeeping on the row, **not** a change to evaluation:

1. **Authority is still the bare triple.** `(principal, capability, scope)` remains the only thing evaluated. Origins are never consulted by `authorize()`; there is no origin-conditional permission, no deny rule, no second permission language.
2. **A grant row exists while at least one origin holds it, and is revoked — atomically, with the locked session-generation advance — when its last origin is released.**
3. **Overlap is exact.** When a sync wants a grant that already exists, it adds a `scim` origin to the existing row rather than duplicating it — **origin keys are unique per `(grant row, origin identity)`**, and origin mutations on a shared row run serializably with bounded retry, so two bindings (or a binding and a human) touching one row lose no origin and never trigger a premature last-origin revocation. Group removal releases only that group's origin; a row with a `manual` origin beside it survives, and vice versa.
4. **Origins are visible, on the grant line.** The locked inspection surface — **each expanded capability visible on its own line and revocable on its own** — is unchanged; origin chips annotate each `(principal, capability, scope)` line. The app-chrome `(member, scope)` grouping stays visual grouping only; inspection and revocation remain per capability line. "Who can read production secrets?" stays answerable by inspection, and "*why* can they?" becomes answerable too.
5. **Origins are auditable.** Origin addition and release on a surviving row emit `grant.modified` with origin fields; last-origin release emits `grant.revoked` (§10).

The template linkage: applying a template — by a human or by a sync — still expands at grant time into independent per-capability rows; the locked "separate grants, not bundles" bind is untouched. Mapping-row origins key on the mapping row id, so mapping-table edits reconcile precisely (§4).

### 2.4 The universal release algorithm and lockout retention

**One algorithm governs every SCIM-side origin release**, whatever triggered it — user deprovision or delete, group membership removal, group delete, mapping-row delete or narrowing, binding delete: release the named `scim` origins; revoke rows whose last origin that was; advance the affected principals' session generations in the same transaction; emit the audit events.

**The lockout interplay is a declared #15 amendment, not an exception smuggled in.** The locked refusal — removing the last org `manage-members` holder is refused — binds *human revocation* unchanged. For SCIM-side release, where refusal would wedge the IdP into infinite retry while the departed user kept all access, the algorithm instead **converts**: if releasing an origin would revoke the last `manage-members`-holding grant at org scope, the `scim` origin is still released (origin truth stays honest — the IdP *did* withdraw it), and the system mints a `lockout-retention(cause)` origin on that row in the same transaction, recording the triggering operation. The row survives on the retention origin; the binding enters the attention state naming the retained grant and principal; `scim.lockout_retention` fires. **Deterministic release:** the moment a transaction leaves the org with another `manage-members` holder (a manual grant to someone else, a sync granting it elsewhere), that same transaction releases every `lockout-retention` origin whose cause is thereby cured — audited on entry and on exit. A `lockout-retention` origin is system-owned: not hand-revocable (the cure is adding another holder), not IdP-addressable. The instance-scope invariant cannot arise: an org binding cannot touch instance grants.

*Rejected: SCIM-side shadow bookkeeping with #15 untouched.* A private table of grant ids breaks overlap in both directions and hides provenance from the membership UI — letter-compliant, intent-violating. *Rejected: `(principal, role, scope)` rows for SCIM grants.* Re-introduces the evaluation-time expansion #15 rejected. *Rejected: whole-operation SCIM refusal on lockout.* Maximum retained authority (the departed user keeps everything) as the price of purity, plus a permanently wedged IdP.

## 3. Group→template mapping

**Each binding owns a mapping table; a row is `(IdP group → role template @ scope)`.** Multiple rows per group are allowed; a user in multiple mapped groups gets the additive union — the grant model's only combining rule. Unmapped groups are inert: pushed, recorded, granting nothing.

- **Templates only, the eight locked ones.** A mapping row targets a template, not a capability checklist — a saved named capability set per group is a custom role template with the serial numbers filed off, and custom templates are post-v1 ([mvp-boundary.md](./mvp-boundary.md) §4.2; its register row already assigns grant provenance to this ticket, discharged by §2). When custom templates arrive post-v1, mapping rows inherit them. **Structurally mappable: the seven org/project/environment-applicable templates**; `operator` is instance-scoped and out of an org binding's reach by construction.
- **Expansion at sync time is expansion at grant time.** A sync applying `publisher@staging` creates the same per-capability rows a human applying that template would, each carrying the `scim(binding, mapping_row, group)` origin.
- **Mapping create/widen applies immediately to the group's current members**: the authoring transaction creates the origins (and any new rows) for every member the group already has — the same transaction that shows the human the blast warning. There is no "waits for the next push" gap.
- **The blast-radius moment moves to mapping authoring.** The locked rule demands the org-scope blast warning "at grant time," when a human is present — under SCIM no human attends the sync, so the warning fires at **mapping-row creation and widening**: an org-scoped row, or any row expanding to `reveal`/`reveal-history`, renders the same consequence language the grant modal uses ([#29](https://github.com/Hikyo-Org/Hikyo/issues/29)), scope picker defaulting narrow, production never preselected. The warning still precedes every grant's existence.
- **Mapping rows reference the binding's group resource by its server-minted SCIM id**, never by displayName — IdP-side renames follow the id and orphan nothing.

## 4. Hand-mutation semantics: refuse, and name both levers

**Revoking a grant whose only live origin is `scim(...)` is refused, naming the two real remediations**: remove the user from the group at the IdP, or edit/delete the mapping row here. No allow-and-let-the-sync-re-add (silent reversal of an admin's revocation within minutes), no standing suppression (a deny rule; the permission model is additive-only, locked).

- **Mapping-table edits reconcile immediately, in the authoring transaction**, under §2.4's algorithm. Deleting or narrowing a row releases every origin keyed on it — no IdP round-trip. The org admin is never stuck behind an IdP they don't control; they are only forced to act on the actual source of the grant.
- A grant with a manual origin beside the SCIM origin: revoke removes the **manual** origin; the row survives on the SCIM origin and the UI says so in place.
- The symmetric case — a human applies a template over grants a sync also wants — is §2 overlap: one row, two origins.

## 5. User lifecycle

### 5.1 Identity: protocol-specific subject derivation

The binding declares, **immutably at creation**, its *subject source*: which SCIM attribute path carries the identity material — **`externalId` or a declared enterprise/custom extension path; `userName` is refused as a subject source by name** (core SCIM defines `userName` as `caseExact: false` and server-unique, which contradicts byte-exact identity material; it keeps its RFC semantics as a lookup attribute, nothing more). The derived subject must equal, byte-exact, what the login path computes — and that is protocol-specific:

- **OIDC provider binding:** the subject source value **is** the OIDC `sub`, consumed as opaque bytes. This requires an IdP whose login `sub` is a stable directory attribute expressible in a SCIM mapping (Okta, Keycloak: yes). **Named limitation, stated rather than papered over:** a provider whose `sub` is pairwise or unavailable to its provisioning app (Microsoft Entra's OIDC `sub` is per-app-derived, not a mappable directory attribute) cannot use OIDC-bound SCIM pre-linking; the supported Entra shape is a SAML provider binding. The binding documentation names this; the E2E criteria require a real provision-then-login fixture proving the provisioned identity reaches the known-identity login path.
- **SAML provider binding:** the locked SAML subject is the **injective encoding of (NameID value, Format, NameQualifier, SPNameQualifier)** ([saml-sp.md](./saml-sp.md)) — a scalar SCIM attribute cannot carry it. The binding therefore declares the **NameID profile**: the Format URI and fixed qualifier values (typically absent, presence-byte-encoded exactly as the login path does), and the SCIM subject-source attribute supplies the **NameID value** alone; Hikyo runs the **same encoder** the SAML login path runs. If the provider was admitted under the `emailAddress` carve, the same opaque-bytes discipline composes unchanged.

**The subject is write-once per SCIM user resource.** A PUT/PATCH that would change the derived subject is refused by name — an IdP-side identifier migration is the rebinding hazard the identity model exists to prevent; deprovision-and-recreate is the explicit path. When `externalId` is the subject source it is therefore write-once and unique per binding; when it is not, `externalId` stays mutable with RFC semantics.

### 5.2 Create: a pre-linked account with zero grants

A SCIM user create makes the account with its external identity `(kind, issuer, subject)` **already bound** — no invitation token, no credential-establishment authority, no session, no assurance. The human logs in later through that provider and matches the known-identity path. The SCIM credential *is* the authority to assert identities for its one `(kind, issuer)`; pre-binding is its whole job. Grants come only from group mappings; a pushed user with no mapped groups authenticates and sees nothing — the same zero-grant posture as JIT ("provisioning an identity and authorizing it are separate acts," [human-auth.md](./human-auth.md)).

- **Idempotent attach, no cross-org oracle — under a declared #23 amendment.** If the asserted identity already exists instance-wide (invited earlier, or provisioned by another org's binding), create attaches that account and adds this org's SCIM resource. Instance-wide identity lookup is exactly what the login path already does; **the provisioning create joins [tenant-isolation.md](./tenant-isolation.md)'s import-bounded identity-resolution interface as a named member** — it never runs through tenant-scoped stores, follows one query path whether the identity exists or not, and returns a response **byte-shape-identical** between fresh-create and attach. The upstream "identity lookup cannot resolve across an org boundary" propagation clauses ([human-auth.md](./human-auth.md), [machine-identities.md](./machine-identities.md)) are **restated by their banners as binding tenant-scoped surfaces**, with the resolution interface (login and provisioning create alike) their single named exception — declared, not implied. The cross-org oracle criteria: response equality, single-query-path equality, and the application-layer timing discipline #23 already claims (engine microtiming stays #23's stated residual). The instance-wide `(kind, issuer, subject)` uniqueness constraint arbitrates concurrent creates; the loser retries and attaches.
- **Email and profile attributes are delivery/display metadata only.** Never matched, never a linking key, never verified authority — stored for the org's directory view and round-tripped.
- **The SCIM `password` attribute is refused by name.** Provisioning never establishes credentials; the credential-establishment authority contract ([human-auth.md](./human-auth.md)) remains the only path to a local credential.

### 5.3 Deprovision and delete

**`active: false` and DELETE are org-grant-scoped, never account-scoped.** The account and its identity links are instance-level and survive — other orgs' memberships and other providers are not this IdP's to kill. Atomically, in one transaction: every `scim` origin this binding holds for the user is released under §2.4 (lockout conversion included); **the user's session generation advances unconditionally on the `active:true→false` and DELETE transitions — a declared #16 amendment adding SCIM deprovision to the generation-advance trigger list** — even when no grant row changes, because the IdP has declared this human gone and surviving sessions must re-prove. Manual grants in this org survive — the IdP was not their source — and the binding raises the loud per-user attention flag: *"IdP deprovisioned this user; manual grants remain."* **Stated honestly:** those manual grants remain usable, including after a fresh login through this or any other linked provider — push-only SCIM cannot prove the IdP will refuse SSO, and this ADR claims nothing it cannot observe. The flag exists precisely because a human must decide about the manual remainder.

DELETE = the same release plus removal of the user from the binding's directory, **including removal of every member reference to that user from the binding's groups, in the same transaction**. `active: false` round-trips as resource state.

### 5.4 Transition table

Every resource mutation has exactly one row here; sync applies desired state, never event replay. "Release" and "create origins" always mean §2.4's algorithm (lockout conversion, session-generation advance, audit events included).

| Transition | Directory state | Origin/grant effect | Notes |
|---|---|---|---|
| User create (new identity) | resource + account + identity link created | origins from current group memberships × mapping rows | one transaction with the identity uniqueness constraint |
| User create (identity exists) | resource created, account attached | same | response byte-shape identical to fresh create |
| User update (attributes) | resource updated | none | subject change refused by name (write-once) |
| `active: true → false` | resource kept, inactive | release all this binding's origins for the user | unconditional generation advance; attention flag if manual grants remain |
| `active: false → true` | resource active | **recreate origins from current group memberships × mapping rows** | reactivation is desired-state, deterministic |
| User DELETE | resource + directory entry removed; member references removed from all groups | release all this binding's origins for the user | unconditional generation advance; account + identity links survive |
| User re-create after DELETE | fresh resource, fresh SCIM id | as user create | stale member references cannot exist (removed at DELETE) |
| Group create | group resource | origins for members × existing mapping rows for that group (normally none — mapping rows reference the id minted here) | |
| Group membership add/remove | membership updated | create/release origins for exactly the affected users × that group's mapping rows | |
| Group update (rename) | displayName updated | none | mapping rows key on id |
| Group DELETE | group removed | release that group's origins for all members | referencing mapping rows flip to **inert** + attention state; human edits or deletes them |
| Mapping row create/widen | — | create origins for the group's current members, in the authoring transaction | blast warning precedes; org-scope/`reveal` consequence language |
| Mapping row narrow/delete | — | release origins keyed on the row (narrow: the no-longer-covered part) | authoring transaction; no IdP round-trip |
| Binding delete | see §6 | release **all** the binding's origins | atomic state machine, §6 |

## 6. Group contract and binding lifecycle

**Groups** are binding-scoped resources: server-minted SCIM id, displayName, externalId, members. **Members are references to this binding's provisioned users**; a member reference resolving to no provisioned user in this binding is refused by name (the IdP can only reference ids this server minted). **Group-type members (nested groups) are refused by name** — v1 is flat; Okta and Entra provision direct user members. The User resource's `groups` attribute is **response-only (read-only per RFC 7643)**; membership is authored exclusively through Group operations.

**Binding deletion is an atomic state machine, in order:** (1) revoke every credential of the binding's provisioning connection — no new wire transaction can begin, in-flight transactions fail at their next proof; (2) release every `scim` origin the binding holds, under §2.4 — lockout conversion applies, and any resulting `lockout-retention` origins **survive the binding** with their cause recorded, still cured by adding another `manage-members` holder; (3) **retire the provisioning connection: release the `structural(binding)` origin, revoking the `scim-provision` grant, and delete the principal — atomically with** the directory resources, mapping table, and the binding row; (4) **identity links survive** — they are account property, exactly as they would be had the user been invited; unlinking remains the account-security mutation it always was. The deletion is audited as binding lifecycle plus the per-principal grant events it causes.

## 7. The provisioning connection: a new machine principal class, one structural grant

**Declared amendment to [machine-identities.md](./machine-identities.md) ([#17](https://github.com/Hikyo-Org/Hikyo/issues/17)), in the instance-connection shape: one new machine principal class, the *provisioning connection*, beside (not inside) the service-account taxonomy.** Org-owned, one per binding, created and administered under `manage-members(org)` ∧ reauthentication. The service-account rules (project ownership, subtree confinement) neither apply to it nor weaken.

- **It authenticates into the same proof model as everything else — no structural bypass.** A new org-scoped capability atom, **`scim-provision`**, joins [permission-model.md](./permission-model.md)'s closed atom set by declared amendment. The provisioning connection's grant surface is **structurally `{scim-provision}` at its own org**: the grant is system-created with the binding **carrying the `structural(binding)` origin (§2)** — the origin invariant holds for it as for every row — retired with the binding by §6's state machine, and the grant API refuses `scim-provision` for every other principal class and refuses every other capability for this class — the normative-allowlist mechanism, one row: `provisioning-connection → {scim-provision}`. `scim-provision` is machine-only; no human session can hold it. Every SCIM wire operation is registered in the authorization registry with formula `scim-provision(org)`, `authorize()` mints an operation- and transaction-bound proof, and the store boundary rejects anything else — the multi-instance `instance-directory` precedent followed exactly, not approximated. Grant-shaped *effects* (the origins §2 creates) are recorded with the connection as actor and mapping row + group as event fields.
- **The mint formula is `manage-members(org)` ∧ reauthentication** — grant-shaped authority, so the grant power gates it. #17's `manage-identities ∧ reveal ∧ reauth` formula governs plaintext paths; `scim-provision` reaches no value, no reveal, no fetch — nothing it authorizes returns plaintext — so `reveal` is not in the formula and `manage-identities` (a project capability) is the wrong language for an org object.
- **The token grammar's closed type list gains `scim`**: `ew_<version>_scim_<body><checksum>` — declared #17 amendment, one scanner family preserved. Everything else inherits unchanged from the locked machine-credential mechanics: ≥256-bit CSPRNG body, checksum, display-once at mint, unsalted SHA-256 verifier under a unique index, overlap rotation (several live credentials, identical authority), lifetime ceiling + `allow_indefinite` instance opt-in, revocation bites at next request, credential epoch carried, **restored verifiers permanently dead**, pre-auth admission on presentation with uniform unknown/revoked responses.
- Machines do not reauthenticate; the MFA-mandatory rule binds human sessions (multi-instance amendment precedent). The humans administering the binding are under `manage-members`' MFA mandate already.

*Rejected: authority-by-eligibility alone (the R1 draft).* An eligibility row without a grant and a proof is a second authority language and a structural bypass of the locked chokepoint — exactly what tenant-isolation forbids. *Rejected: an `automation` service account with carve-outs.* Breaks project ownership, subtree confinement, and the no-`manage-members`-for-machines rule in one move. *Rejected: reusing the instance-connection class.* Wrong owner, and its single-operation eligibility is spent.

## 8. Wire surface

**Mount: `/api/v1/orgs/{org}/scim/v2/{binding}/…`, inside the version prefix, contract-tested, frozen with everything else.** RFC 7644 fixes the relative path shapes; IdPs take a configurable base URL, so the per-binding base composes cleanly. The credential presented **must match the binding in the path** — mismatch is a named authentication failure, audited; no ambient routing by credential.

- **Resource set, closed:** `Users` and `Groups` (GET/POST/PUT/PATCH/DELETE), plus `ServiceProviderConfig`, `ResourceTypes`, `Schemas` (discovery; content is the closed truth of what this server implements). No Bulk, no `/Me`, no sorting, no `.search` — each advertised absent in `ServiceProviderConfig`, each refused with the RFC 7644 error shape (`scimType` set), never half-implemented.
- **Filter grammar, closed:** `userName eq "…"` and `externalId eq "…"` on Users; **`displayName eq "…"` and `externalId eq "…"` on Groups** — the four probes Okta and Entra actually issue (both discover a group by `displayName eq` before creating or updating it). Comparison semantics follow the attribute: `userName` and `displayName` compare per their RFC `caseExact: false` definitions (lookup attributes, not identity material); `externalId` compares byte-exact. Any other attribute, operator, or compound filter: refused with `scimType: invalidFilter`.
- **List responses are RFC-shaped:** `totalResults`, 1-based `startIndex`, `itemsPerPage`, `Resources`; page size bounded (bound registry, §9); an out-of-range page returns an empty `Resources` with truthful `totalResults`.
- **PATCH contract: a closed operation×path matrix.** Accepted cells, everything else refused with `scimType: invalidPath`:

  | op \ path | *(none: pathless value object)* | plain attribute path | `active` | `members` | `members[value eq "…"]` |
  |---|---|---|---|---|---|
  | `add` | ✓ (merge) | ✓ | ✓ | ✓ (add refs) | — |
  | `replace` | ✓ (merge) | ✓ | ✓ | ✓ (replace set) | — |
  | `remove` | — | ✓ (non-required only) | — | ✓ (clear set) | ✓ (remove ref) |

  The matrix is per-resource: `active` cells apply to Users only, `members` cells to Groups only — a cross-resource path (`members` on a User, `active` on a Group) refuses with `invalidPath`. Entra's stringified booleans for `active` (`"True"`/`"False"`) are normalized on ingest, a named tolerance. The remaining named refusals carry exact codes: nested-group member and unknown member reference → `invalidValue` (400); `password` → `invalidValue` (400, unsupported attribute named); Bulk, `/Me`, sorting, `.search` → SCIM error body with HTTP 501 (no `scimType` — that field is a 400-class discriminator); credential-vs-binding-path mismatch → 401 authentication failure, never a SCIM 400. **A PATCH is atomic**: any invalid operation fails the whole request with nothing committed. **PUT is RFC replacement**: omitted mutable attributes clear to their defaults; **`active` defaults `true`** (on create, and on PUT omission — an omitted `active` reactivates, per the transition table); `userName` is required on create and on PUT (`invalidValue` if absent); the subject source is exempt from replacement (write-once, §5.1); `groups` on Users is ignored on input (response-only). **Error mapping, closed:** unknown/unsupported filter → `invalidFilter`; unaccepted PATCH cell → `invalidPath`; type/missing-required violations (incl. absent `userName`) → `invalidValue`; subject-change and other write-once violations → `mutability`; duplicate `userName`/subject-source collision → `uniqueness`; PATCH path resolving to nothing → `noTarget`. Each carries the RFC 7644 error body; each is a distinct named fixture.
- **The exception class, restated.** The [api-cli-surface.md](./api-cli-surface.md) closed auth-protocol endpoint exception class is restated as **identity-protocol endpoints** — authentication *and* provisioning, same admission test (protocol-shaped, client-specific by nature, never a domain endpoint) — and gains the SCIM set. SCIM endpoints are meaningless to the SPA and to a human at a CLI; they are the IdP's wire. Declared #25 amendment, banner operative; exact spellings at [#27](https://github.com/Hikyo-Org/Hikyo/issues/27).
- **Parity.** The SCIM wire endpoints join the closed parity-exemption list as protocol paths. The **administrative surface is domain surface with full UI↔CLI parity**: binding CRUD, mapping-table administration, credential mint/rotate/revoke, the provisioned directory view (users, groups, attention flags, last-contact) — verbs join #25's closed noun-verb set at a declared join point, exactly as the adapter verbs did; no new grammar, no new output class.
- SCIM bodies are JSON under the locked parse-don't-cast discipline; IdP-supplied strings are attacker-influencable free text at a trust boundary — bounded, UTF-8-sanitized, `ew_`-grammar-redacted wherever they land in audit or error text ([audit-model.md](./audit-model.md)).
- The `/api/v1/meta` allowlist is **not** amended: SCIM support is configuration-shaped, not a protocol a login client selects; the IdP learns the base URL from the org admin, not from discovery.

## 9. Operational posture

**Push-only; staleness surfaced, never self-healed.** Hikyo never calls the IdP — the provisioning connection is inbound-only; no outbound trust exists (zero-egress posture preserved). The binding records last-contact and per-resource last-sync; past a threshold the binding surface shows a staleness warning. Repair is the IdP's own reconciliation cycle (Entra ≈40 min; Okta similar). *Rejected: outbound IdP polling* — a second credential pointing the other way, a new trust direction; post-v1 with its own ticket if demand shows. *Rejected: staleness-TTL grant expiry* — converts an IdP outage into org-wide access revocation, the scrub-on-timer failure shape the K8s ADR rejected by name.

- **Concurrency, honestly:** per-binding writes serialize (one reconciliation transaction at a time per binding — SCIM clients are sequential in practice, and serialization keeps a single binding's origin arithmetic trivially race-free). **Across bindings, contention on shared grant rows is real** — two providers linked to one account can race on one `(principal, capability, scope)` row — and is handled at the row: unique origin keys, serializable transactions with bounded retry (§2.3). The two-binding race is a named fixture.
- **Admission**: credential presentation sits under the machine pre-auth budget with uniform unknown/revoked responses; authenticated SCIM operations carry bounded body sizes, bounded page sizes, and per-binding rate limits — entries in the ops-spec bound registry, values at synthesis. The envelope fits the calibration floor: low-frequency administrative traffic, bounded pages, no fan-out.
- **Sessions**: the locked grant-addition invalidation applies unchanged — a group-driven grant logs the affected user out; new authority is exercisable on next login. Stated, not softened: being granted anything logs you out, and a sync is a granter. Deprovision transitions advance the generation unconditionally (§5.3).
- **Attention states are one enumerated surface on the binding**, each audited on entry and exit, each naming cause and remediation: provider disabled/removed (§1, wire fails closed), lockout retention (§2.4), manual-grants-remain-after-deprovision (§5.3), inert mapping rows (§5.4), staleness (§9), post-restore reconciliation (§9.1). The binding view is the org admin's answer to "what does SCIM think is wrong?"

### 9.1 Restore

Composes from inherited rules plus one SCIM-specific rule, closing the stale-grant window rather than narrating it:

- The connection's credential verifiers are **permanently dead** (locked, [machine-identities.md](./machine-identities.md)); the org admin must re-mint.
- Restored grants are quarantined data until the operator commits the reconciled set (locked, [permission-model.md](./permission-model.md)). **The SCIM-specific rule: restored `scim` origins are dropped at reconciliation commit, not committed** — the operator's commit covers `manual` origins only; a row whose only restored origins were `scim` is not re-activated. **The IdP's re-assertion recreates SCIM origins from live truth**: after re-mint, the next IdP cycle walks users and groups and §5.4's desired-state table rebuilds exactly what the IdP currently asserts. A user deprovisioned after the backup was taken is therefore never re-authorized, not even for a window — the IdP no longer asserts them, so nothing recreates their origins. **Restored SCIM-bound identity links follow [human-auth.md](./human-auth.md)'s locked restore rule unchanged: inert until the operator's per-principal reconciliation under local authority — SCIM re-assertion does not substitute for it and does not re-bless a link.** Re-assertion rebuilds directory state and origins; a rebuilt grant is reachable only once its principal can authenticate, which requires the operator-reconciled link — the two controls compose, neither bypasses the other.
- The binding sits in the post-restore attention state from restore until re-mint + first completed re-assertion cycle.

**v1 payload schema discipline, normative here:** the field lists above are the schemas, under these complete typing rules — every field is required unless marked nullable; `binding`, `resource id`, `group id`, `account id`, `principal`, `actor`, `credential id`, `mapping row`, and grant references are UUIDv7; `scope` is a `(level ∈ {org, project, environment}, scope id UUIDv7)` pair; `template` is the closed template-name enum; counts (`released-origin`, `member-references-removed`, added/removed lists ≤200 ids) are non-negative integers; flags are booleans; IdP-originated strings (displayName, attribute names) are UTF-8-sanitized, redacted, and bounded at ≤256 bytes (changed-attribute lists ≤50 entries); the subject never appears in plaintext — `subject digest` is its SHA-256 hex; `filter shape` ∈ `{none, userName_eq, externalId_eq, displayName_eq}`; `page` is `(startIndex ≥ 1, count ≥ 0)`; `cause` ∈ `{deprovision, user_deleted, member_removed, group_deleted, mapping_deleted, binding_deleted}`; `state` (attention) ∈ `{provider_unavailable, lockout_retention, manual_grants_remain, inert_mapping, stale, post_restore}`; attach-vs-create ∈ `{create, attach}`; resource type ∈ `{user, group, discovery}`; `provider ref` is the provider row UUIDv7. Each entry's schema is versioned `v1` in the registry and validated on write, per the locked registry rule.

- **Reads are events too.** User/Group GET, list, and filter are authenticated machine reads and land in `scim.directory_read` (`access` class, like the fetch stream) — the earlier "every SCIM operation is mutating" claim was false and is withdrawn; discovery endpoints (`ServiceProviderConfig`/`ResourceTypes`/`Schemas`) are static protocol documentation under the binding's authentication and admission, carrying no tenant data; they are the one SCIM surface annotated `audited: none`-equivalent **by explicit registry annotation on their probe class**, not silence.
- **Origin arithmetic on surviving rows is visible:** origin addition/release where the row survives emits `grant.modified` with origin fields (binding, mapping row, group); last-origin release emits `grant.revoked`; creation emits `grant.created` — the existing `grant` category, gaining origin event fields by this amendment.
- **Actor/authority**: the provisioning connection is the actor (`class: machine`, credential id recorded) for wire-driven events; administering humans are actors for binding/mapping/credential lifecycle. Authn failures vs authz denials stay distinct; denials are per-event, durable before the error response.
- **No aggregation.** The aggregation licence covers authentication-failure floods only, at its locked width; a 500-user initial push emits 500 `scim.user_provisioned` events plus their grant events, per-event, durably — bounded by admission, priced as evidence.
- Registry-completeness CI covers every SCIM operation via the probe-classification registry; no SCIM operation qualifies for silent `audited: none`.
