# Envweave SAML SP support (ADR, locked 2026-08-06)

Context: the MVP boundary ([mvp-boundary.md](./mvp-boundary.md) §2.2, [#26](https://github.com/Dunky13/envweave/issues/26)) promoted SAML (SP) into 1.0 as wedge proof — SAML is the classic `/ee` paywall item — and fixed this ticket's boundary conditions: the local floor stays never-disableable, the assurance policy model extends to SAML assertions, byte-exact external-identity matching transfers unweakened, "known library means proven" gets a measurable three-criteria bar, and a defined fallback ladder (narrowed profile → procedural demotion) governs the case where no Go SAML library meets it. This ADR resolves the design: library selection under the bar, the normative policy the library does not choose, assertion→identity mapping, assurance handling, session binding, multi-IdP coexistence with OIDC, JIT posture, metadata lifecycle, and the §1.1-format acceptance criteria.

***Amends the human-auth ADR ([human-auth.md](./human-auth.md), [#16](https://github.com/Dunky13/envweave/issues/16)), declared.*** The amendment, in full: (a) the "LDAP and SAML are out of v1" decision is discharged for SAML — **SAML SP login ships in v1** under this ADR's design; LDAP stays out ([mvp-boundary.md](./mvp-boundary.md) §4.2). (b) The identity key gains a **protocol discriminator**: `(kind, issuer, subject)` where `kind ∈ {oidc, saml}` — required because an IdP's OIDC issuer URL and SAML entityID can be the **same string** (a Keycloak realm publishes exactly that), so the unqualified key would merge two protocol identities with different subject semantics through the very uniqueness constraint that exists to prevent merges. Existing OIDC rows backfill `kind = oidc` in the schema migration, on both engines, covered by an executable criterion (SA2); no OIDC behaviour changes. The provider row id is deliberately **not** in the key — removing and re-adding a provider must resolve the same humans, not mint a parallel population — and the complementary constraint that makes this safe is **one active provider per `(kind, issuer)`** (§ *Coexistence*). (c) The per-provider assurance policy model gains its SAML form (§ *Assurance*), and the session-deletion-on-provider-change rule binds SAML providers identically, with certificate-set changes added as a deleting cause. (d) **One narrow, named carve to the email rule.** Human-auth's "email is never a linking key, at any point, for any provider" stands as the governing rule; this amendment adds its single exception, stated at full width: an IdP whose NameID format is `emailAddress` may be admitted by **per-provider explicit opt-in**, in which case the NameID is consumed as **opaque bytes in the subject position** — never parsed as an address, never matched against any account email, never used to locate an account outside the `(kind, issuer, subject)` constraint. The residual risk the opt-in accepts is named in the configuration itself: the IdP reassigning the address silently rebinds the identity to a different human. Without the opt-in, `emailAddress`-format NameIDs are refused. This is an amendment because an email-shaped subject is an email-shaped subject — the ADR does not pretend the opaque-bytes treatment makes the rule inapplicable. Everything else in human-auth stands unchanged. The amendment follows the locked-ADR amendment procedure ([oss-mechanics.md](./oss-mechanics.md) § Governance): #16 is reopened for the record and re-closed with the amendment noted, the banner lands in [human-auth.md](./human-auth.md), and the adversarial cross-model review that locks this ADR covers the amendment text.

***Amends the API & CLI ADR ([api-cli-surface.md](./api-cli-surface.md), [#25](https://github.com/Dunky13/envweave/issues/25)), declared.*** That ADR's auth-protocol endpoint exception class is closed and enumerated, and adding a member is a spec-review event; this ADR adds members rather than pretending they were implied. The amendment, in full: (a) the exception class gains the **per-provider SAML ACS endpoints** and the **SP metadata endpoint** — both protocol-shaped (browser POST / unauthenticated GET), neither a domain endpoint, exactly the class's admission test; (b) SAML provider configuration joins the **existing** instance-config verb surfaces under the existing grammar — no new verb family, no new output class; metadata refresh is an action on the provider resource, not a new noun. Exact spellings → synthesis ([#27](https://github.com/Dunky13/envweave/issues/27)). Procedure: #25 reopened for the record and re-closed, banner in [api-cli-surface.md](./api-cli-surface.md), covered by this ADR's review.

Granularity note: this is the wayfinding-level SAML ADR. It fixes the library and its wrapper obligations, the protocol profile, the validation algorithm and its failure semantics, identity mapping, assurance, metadata trust, SP-side material, and coexistence — **including the concrete default values for every bound it introduces**, so its criteria are executable against this text alone; the values join the ops spec's composable-maxima catalogue at synthesis as tunable entries with the defaults fixed here. Mechanism-level detail delegated: exact endpoint paths and CLI/UI spellings → synthesis ([#27](https://github.com/Dunky13/envweave/issues/27)); provider-configuration interaction design → the app-chrome instance-administration surfaces ([#29](https://github.com/Dunky13/envweave/issues/29)). Each delegated site MUST satisfy the constraints stated here.

## Library selection: gosaml2 under an Envweave-owned policy wrapper

**The landscape verdict is stated before the choice** (full survey: [go-saml-libraries.md](../research/go-saml-libraries.md)): every maintained Go SAML implementation — crewjam/saml, russellhaering/gosaml2, hashicorp/cap/saml, Dex's connector — stands on one foundation, `beevik/etree` + `russellhaering/goxmldsig`, a single-maintainer XML-DSIG core; Go's `encoding/xml` round-trip instability (the December 2020 disclosure class) was never fixed in the standard library, and the ecosystem's mitigation is containment (`mattermost/xml-roundtrip-validator` + single-parse discipline), not cure.

**Selected: [russellhaering/gosaml2](https://github.com/russellhaering/gosaml2)** (with `goxmldsig` and `mattermost/xml-roundtrip-validator` in the chain). **It meets mvp-boundary §2.2's three-criteria bar on the evidence, so the fallback ladder never triggers** — rung (a) is not invoked, and this ADR claims no rung:

1. **Actively maintained** — v0.11.0 (2026-03) and v0.12.0 (2026-08) are security releases within the last 12 months; the maintainer ran a public 60-CVE cross-ecosystem SAML self-review (2026-03) and enrolled the library in oss-fuzz. *Pass.*
2. **Public CVE/security-response history with fix releases** — GHSA-pcgw-qcv5-h8ch (unsigned LogoutRequest acceptance, 7.5) fixed in v0.11.0 alongside a CBC-padding panic fix and in-envelope assertion-signature verification; v0.12.0 rejects unsigned LogoutResponse and caps token floods. Evidence the project *responds* — the bar's own definition. *Pass.*
3. **Named production use / vendored inclusion** — vendored (wrapped) in `hashicorp/cap/saml`, the SAML core of HashiCorp Vault's supported SSO path; Mattermost ships its maintained fork of the same codebase. *Pass through the bar's vendored-inclusion route, stated honestly: production use runs through wrappers and forks, which is the ecosystem's universal pattern (Grafana and Teleport fork crewjam/saml; nobody ships any of these raw).*

**Passing the bar is necessary, not sufficient.** The bar measures whether the *project* is proven to respond; it does not make the library's raw behaviour acceptable, and mvp-boundary's own text makes XML signature wrapping a named attack class this ADR must cover **regardless** of the bar. The raw library fails Envweave's posture in enumerated ways — and the profile and wrapper below are therefore **mandatory hardening chosen by design**, standing on this ADR's own authority, not on the fallback ladder. The failure map, each row carried by an adversarial fixture (§ *Acceptance criteria*):

| Failure in the raw library / foundation | Profile/wrapper element that removes it |
|---|---|
| #219: assertion sig unverified when response-signed | Assertion signature mandatory + the structural verification algorithm (§ *The validation algorithm*) binding verification to extraction |
| Unsigned LogoutRequest/Response acceptance history | SLO excluded from profile — no logout endpoint exists |
| IdP-initiated SSO accepted implicitly | Unsolicited responses refused by name (`InResponseTo` mandatory) |
| Audience/Conditions violations returned as warnings | Wrapper promotes **every** `WarningInfo` to a hard error — an empty warning set is a precondition of login |
| `Destination` checked only if present | Wrapper requires `Destination` present and exact |
| No `InResponseTo` validation | Wrapper binds to the server-side transaction store (§ *The SAML transaction*) |
| No replay cache | Wrapper maintains a durable one (§ *The validation algorithm*) |
| No Response/Assertion `IssueInstant` freshness check | Wrapper bounds `IssueInstant` age on both (§ *The validation algorithm*) |
| goxmldsig accepts RSA-SHA1 on verification | Closed algorithm-URI allowlist enforced before any validation result is accepted (§ *XML processing*) |
| No exclusive-C14N pinning | CanonicalizationMethod/Transform URIs pinned to exclusive C14N without comments (§ *XML processing*) |
| RelayState handling integrator-owned (open-redirect risk) | RelayState is a server-minted opaque handle; no URL from the wire is ever followed (§ *The SAML transaction*) |
| XML token floods / entity expansion | Pre-parse document bounds: size, depth, token count; DTD refused (§ *XML processing*) |
| Comment/namespace round-trip differentials (2020 class) | roundtrip-validator + single-parse invariant + duplicate-ID/structural checks with fixtures (§ *XML processing*) |
| xmlenc (CBC padding) surface | Encrypted assertions refused by name — the decryption path is never invoked |

**The wrapper is relying-party policy, not a reimplementation.** Human-auth's no-hand-rolled-primitive invariant distinguishes what a library supplies (parsing, canonicalization, signature verification) from what it cannot choose (which validations are fatal, what binds to what, what is refused). Signature verification stays in `goxmldsig`; the wrapper adds structural checks and refusals *around* verified results — exactly the layer where "library selection is not policy selection" says Envweave's decisions live. The wrapper implements no XML parsing of its own (it walks the one existing parse tree), no canonicalization, no cryptographic verification.

**Pinning and watch are CI invariants.** gosaml2, goxmldsig, etree and xml-roundtrip-validator versions are pinned; a CI job watches their advisory feeds and fails the build when an unpatched advisory affects a pinned version, so upgrades are prompted by the pipeline rather than by memory.

*Rejected: crewjam/saml (fork + pin).* Strongest in-library defaults (`AllowIDPInitiated=false`, hard errors on Destination/InResponseTo/audience/freshness), but upstream fails the maintained criterion — last substantive commit >12 months ago, tags-only releases, bus factor 1 — so choosing it means maintaining a security-critical fork ourselves, the Grafana/Teleport road with a fraction of their staffing. *Rejected: hashicorp/cap/saml.* The composed-proven-wrapper story with HashiCorp's name on it, but a thin public track record of its own, and it demonstrably lagged upstream's 2026 security releases — middleman latency on security patches becomes Envweave's exposure while the wrapper above already owes every policy check regardless. *Rejected: no native SAML (documented Keycloak/ZITADEL/Authentik bridge).* The honest fallback if the landscape had failed the bar; not needed — the bar passes — and demotion is defined as a declared mvp-boundary amendment reopening [#26](https://github.com/Dunky13/envweave/issues/26), a road this ADR does not take. The bridge recipe ships as documentation anyway for shops that prefer it; documentation is not the 1.0 capability.

## Profile: narrow by deliberate design

The profile below is the **design**, chosen on security grounds — not a concession extracted by the fallback ladder (which never triggered). Every exclusion is a refusal by name with a stated trigger, never a silent absence.

- **SP-initiated Web Browser SSO only.** Envweave sends an `AuthnRequest`; the IdP answers. **Unsolicited (IdP-initiated) responses are refused by name**: a Response whose `InResponseTo` is absent or unknown to the transaction store fails with a distinct error naming IdP-initiated SSO as unsupported. IdP-initiated SSO severs the response from any request the SP made — no `InResponseTo`, no transaction binding, the CSRF/replay-shaped surface every SAML security survey names first. Shops whose IdP portal is the entry point still work: the portal link targets Envweave's login page, which starts an SP-initiated flow.
- **Bindings: HTTP-Redirect for the AuthnRequest, HTTP-POST for the Response.** Exactly one binding per direction; a Response arriving on any other binding, or an AuthnRequest endpoint invoked with a Response, is refused. Artifact binding (extra round trips, near-zero deployment) and POST-binding requests are out.
- **No Single Logout.** Envweave sessions are Envweave's ([human-auth.md](./human-auth.md)); logout ends the Envweave session and does not contact the IdP; no SLO endpoint exists in either direction. SLO is the profile's historically buggiest surface (both of gosaml2's 2026 advisories live there) and its semantics — best-effort fan-out logout with partial-failure ambiguity — deliver a guarantee nobody can state. The IdP session simply outlives the Envweave session, which is already true of OIDC today.
- **No assertion encryption (xmlenc), refused by name.** TLS covers transport; encrypted assertions add a second cryptographic attack class (CBC padding oracles, key-transport quirks — gosaml2's padding panic sat exactly there) for the marginal gain of hiding assertion content from the user's own browser. A provider configured at an IdP that mandates encryption fails at configure time with the refusal naming this decision; an `EncryptedAssertion` element anywhere in a Response is a hard refusal. **Named revisit trigger**: concrete demand from an onboarding org whose IdP policy cannot be changed, plus a proven decryption path in the pinned library version.
- **Signed Assertion mandatory; a Response signature is accepted in addition but is never sufficient alone.** The signature that authorizes login is the one covering the Assertion element consumed, bound structurally (§ *The validation algorithm*). Response-only signing (some IdPs' default) is a one-switch change on the IdP side, and accepting it would reopen exactly the coverage-walking ambiguity that XML signature wrapping exploits — and gosaml2 issue #219's live gap.

## XML processing

Every inbound SAML document is bounded **before parsing**: decoded size ≤ 256 KiB, element depth ≤ 32, XML token count ≤ 50,000; a DTD declaration anywhere is refused; external entity resolution does not exist (etree does not fetch, and the DTD refusal closes the vector at the door). It then passes `mattermost/xml-roundtrip-validator` — the ecosystem's containment for Go's unfixed `encoding/xml` round-trip instability — and is parsed **once**; every subsequent check (signature verification, structural assertions, field extraction) operates on that single parse tree. Parse-once is an invariant, not a style preference: the 2020 bypass class was precisely divergence between two parses of one document.

**The algorithm allowlist is closed, enumerated by exact URI, and enforced before any verification result is accepted** — because goxmldsig itself still accepts RSA-SHA1:

- `SignatureMethod`: `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`, `http://www.w3.org/2001/04/xmldsig-more#rsa-sha384`, `http://www.w3.org/2001/04/xmldsig-more#rsa-sha512`, `http://www.w3.org/2001/04/xmldsig-more#ecdsa-sha256`, `http://www.w3.org/2001/04/xmldsig-more#ecdsa-sha384`, `http://www.w3.org/2001/04/xmldsig-more#ecdsa-sha512`. Nothing else.
- `DigestMethod`: `http://www.w3.org/2001/04/xmlenc#sha256`, `http://www.w3.org/2001/04/xmldsig-more#sha384`, `http://www.w3.org/2001/04/xmlenc#sha512` (the SHA-384 digest URI lives in the `xmldsig-more` namespace, not `xmlenc` — recorded literally so nobody "fixes" it into a wrong guess). Nothing else.
- `CanonicalizationMethod`: `http://www.w3.org/2001/10/xml-exc-c14n#` (exclusive C14N **without** comments). Nothing else — inclusive C14N and with-comments variants are refused by URI.
- `Transforms`: exactly the pair `http://www.w3.org/2000/09/xmldsig#enveloped-signature` + `http://www.w3.org/2001/10/xml-exc-c14n#`, in that order. Any other transform (XPath, XSLT, with-comments) is refused by URI.

An algorithm or transform not on the list is **refused, not evaluated** — the check reads the URIs from the signature element and fails before verification runs.

## The validation algorithm

The wrapper's acceptance decision is one closed conjunction over the single parse tree; every clause is a hard error with a distinct, enumerated, audited cause. Library validation runs first and the wrapper promotes **every** `WarningInfo` to a hard error (an empty warning set is a precondition); the wrapper then asserts, in order:

**Structural XSW defence — verification bound to extraction:**

1. XML IDs are **unique and nonempty document-wide** (duplicate or empty `ID` attributes anywhere = refusal).
2. The Response contains **exactly one** `Assertion`, as a **direct child** of the Response element; zero `Assertion` elements anywhere else (nested, in extensions, in `SubjectConfirmationData`); zero `EncryptedAssertion` elements anywhere.
3. That Assertion carries **exactly one** enveloped `Signature` as its direct child, whose single `Reference` is a same-document URI equal to that Assertion's ID. Zero references, multiple references, empty-URI references, external references, or a reference resolving to any other node = refusal.
4. `goxmldsig` verifies **that exact node**, against a certificate in the provider's pinned set (§ *Metadata*), under the closed algorithm allowlist; and **every** field subsequently consumed — Issuer, Subject/NameID, Conditions, AuthnStatement — is extracted **from the node the verifier returned**, never from the pre-verification tree. Verification and consumption cannot disagree because they address the same node.
5. If a Response-level signature is present it must **also** validate (same allowlist, same certificate set) — a document carrying any invalid signature is refused — but it contributes nothing to the assertion's acceptance: no envelope signature counts as assertion evidence.

**Transaction and provenance:**

6. `InResponseTo` matches a live, unconsumed transaction (§ *The SAML transaction*); the transaction is consumed on first presentation, success or failure, **atomically with** replay-cache insertion and session minting — one database transaction covers all three, so concurrent presentation of one Response races on a uniqueness constraint and exactly one wins.
7. The **Response `Issuer`** (required present) and the **Assertion `Issuer`** (required present) are each **byte-equal** to the entityID of the provider recorded in the transaction.
8. The Response arrived at the **per-provider ACS endpoint** belonging to that same provider, and `Destination` is present and byte-equal to that ACS URL.
9. The **initiator binding** holds: the browser presenting the Response carries the transaction's initiator cookie (§ *The SAML transaction*); mismatch or absence = refusal. Purpose-specific bindings (reauth/link: the initiating authenticated session and target account) hold likewise.

**Content:**

10. `AudienceRestriction` is present and contains Envweave's SP entityID.
11. Subject confirmation method is `bearer`; its `SubjectConfirmationData` carries `Recipient` byte-equal to the ACS URL, `NotOnOrAfter` **present** and satisfied, and `InResponseTo` **present and byte-equal to the transaction's request ID** — required, not optional, because the SCD sits *inside* the signed Assertion: it is the one request binding the IdP's signature actually covers, so without it an unsigned-envelope Response leaves the signed assertion unbound to any request. Every major IdP sets it in SP-initiated flows; an IdP that omits it fails loudly here by design.
12. Conditions `NotBefore` (when present) and `NotOnOrAfter` (**required present**) are satisfied within the skew allowance.
13. Response `IssueInstant` and Assertion `IssueInstant` are each within the freshness bound (age ≤ 5 minutes + skew; future-dated beyond skew = refusal).
14. The Assertion contains **exactly one `AuthnStatement`**; `AuthnInstant` and the assurance context are read from that statement (§ *Assurance*).
15. The Assertion `ID` (nonempty, per clause 1) is **absent from the replay cache**; on acceptance it is inserted — the cache is a **durable table under a uniqueness constraint** (it survives restart; an in-memory cache is a replay window shaped like a reboot), rows retained until the assertion's Conditions `NotOnOrAfter` + skew and garbage-collected after.

**Values** (defaults fixed here; catalogued as tunable ops-spec entries at synthesis): clock skew 60 s (the machine-identity precedent), transaction TTL 10 min, `IssueInstant` max age 5 min, document bounds as § *XML processing*.

**Refusals are enumerated, not generic**: unsolicited response, unknown/consumed transaction, initiator mismatch, purpose mismatch, issuer mismatch (each leg), wrong ACS, destination mismatch, structural-XSW refusals (duplicate ID, assertion cardinality, reference shape, extra signature invalid), unknown certificate, disallowed algorithm/transform/canonicalization, audience missing/mismatched, confirmation-method unsupported, missing `NotOnOrAfter` (either), stale/early conditions, stale `IssueInstant`, replayed assertion, AuthnStatement cardinality, encrypted-assertion present, DTD present, document bounds exceeded, warning-set nonempty. Each maps to a distinct audited failure cause (§ *Audit*), because "SAML login failed" is not a diagnosable event.

**`SessionNotOnOrAfter` is ignored, and the ADR says so plainly.** Without SLO, Envweave does not track IdP session state; honouring one field of it would claim a coupling that does not exist. The Envweave session minted from a SAML login lives under Envweave's own lifetimes ([ops-spec.md](./ops-spec.md)), exactly like an OIDC-minted session.

## The SAML transaction

The OIDC transaction's server-side shape transfers, extended. Every AuthnRequest mints a **server-side transaction record**: request ID, the provider row it was sent to, purpose (**`login` | `reauth` | `link`** — the same purpose binding human-auth fixes for OIDC, so an induced login round-trip cannot satisfy a reveal gate, and a login response cannot complete a linking flow), the initiator binding, the RelayState handle, creation time, and a TTL (10 min). A transaction is **single-use**: consumed on first presentation of its `InResponseTo`, success or failure.

**Initiator binding closes login CSRF.** A SAML response is a bearer artifact; without binding the response back to the browser that started the flow, an attacker completes their *own* login at the IdP and causes the victim's browser to POST the resulting valid Response — logging the victim into the attacker's account. Therefore:

- **`login`**: minting the transaction sets a server-generated, single-use **initiator cookie** (≥128-bit opaque), `httpOnly`/`Secure`/**`SameSite=None`**, **path-scoped to the ACS path prefix** and expiring with the transaction TTL. `SameSite=None` is load-bearing, not a lapse: the IdP's POST to the ACS **is** a cross-site request, and a `Lax` cookie would simply not accompany it — the defence would refuse every legitimate login. The narrow path scope and TTL keep the relaxation confined to the one endpoint whose entire job is receiving that cross-site POST; the CSRF work is done by the cookie↔transaction match, not by SameSite. The ACS accepts the Response only from the browser presenting the transaction's cookie, and consumes it with the transaction.
- **`reauth` and `link`**: the transaction additionally records the **initiating authenticated session and the target account**; the ACS requires that same session, and for `reauth` the ceremony result binds to exactly the recorded account and purpose (human-auth's purpose rule), for `link` the identity in the assertion is bound to exactly the recorded account under the atomic-linking transaction human-auth fixes.
- **CLI login**: the transaction records the outer RFC 8252/8628 handoff transaction it serves ([api-cli-surface.md](./api-cli-surface.md)); the browser leg carries the same initiator cookie; the handoff's own code+state machinery is untouched.

**RelayState is a server-minted ≥128-bit opaque handle, compared exactly, single-use, consumed with the transaction.** Any continuation ("return the user to the page they were on") is stored **server-side against an internal allowlist of application routes** at mint time. **No URL that arrives from the wire is ever followed** — a RelayState that is not exactly a live handle is a refusal, and the open-redirect class is closed structurally: there is no code path from wire bytes to a redirect target.

## Identity mapping

**The identity pair is `(kind = saml, issuer = IdP entityID, subject = enc(NameID value, Format, NameQualifier, SPNameQualifier))`, matched byte-for-byte, no canonicalization, under the database uniqueness constraint** — the mvp-boundary's transfer of human-auth's matching rule, unweakened. The qualifiers are inside the subject: the same NameID string under a different Format or qualifier pair is a **different identity** — omitting them would perform silently the merge the byte-exact rule exists to forbid.

**The subject encoding is injective.** Each of the four fields is encoded as `presence-byte ‖ length ‖ bytes` — the presence byte distinguishes **absent** from **present-but-empty**, because a bare length-prefix encoding maps both to length zero and collides them, quietly weakening byte-exactness at the one place it must not bend. (The encryption ADR's length-prefix discipline is the ancestor; the presence byte is this ADR's required strengthening for optional fields.) The NameID value itself must be nonempty; an empty NameID is a refusal.

**Accepted NameID formats, per provider**:

- `persistent` and `unspecified` — accepted by default. Persistent is the purpose-built stable pseudonym; unspecified is the pragmatic default of half the IdP fleet (Keycloak, ADFS) and is stable in practice — and the byte-exact rule means Envweave never interprets it, only matches it.
- `transient` — **refused always, not configurable.** Transient is fresh-per-login by definition; linking it is linking noise, and any "works in testing" behaviour would be an IdP failing its own format contract.
- `emailAddress` — **refused by default; per-provider explicit opt-in under the declared human-auth carve** (amendment clause (d) above): opaque bytes in the subject position, never parsed, never matched against account email; the opt-in names the reassignment-rebinding risk in its own configuration surface and is audited when set or unset.

**An unknown SAML identity is not a login** — human-auth's rule transfers verbatim: it matches a pending invitation (claimed by presenting the invitation token itself), or it is refused. Linking a SAML identity to an existing account is the same explicit act, under the same atomic transaction and uniqueness constraint, as linking an OIDC identity — carried by the `link` transaction purpose (§ *The SAML transaction*). Email and every other assertion attribute are **never** linking keys; attributes are not consumed for identity at all in v1 (no attribute-mapping surface exists — a deliberate absence, not an oversight: attribute mapping arrives with SCIM's provisioning model, [#38](https://github.com/Dunky13/envweave/issues/38), where reconciliation semantics exist to receive it).

## Assurance

Human-auth's rule — authorization consults *how this session authenticated*, per-provider policy is not a boolean — extends to SAML in its SAML-native form:

- The accepted Assertion carries **exactly one `AuthnStatement`** (clause 14); `AuthnInstant` and the `AuthnContextClassRef` are read **from that same statement** — cardinality is pinned precisely so freshness and context cannot be assembled from different statements. **Zero or multiple `AuthnContextClassRef` values in the statement**: zero yields single-factor assurance on login and **fails reauth whenever the provider has an assurance policy**; multiple is a refusal (the spec allows one per statement; a document carrying more is malformed by the profile).
- Each SAML provider's assurance policy is a set of **accepted `AuthnContextClassRef` values** (SAML has no `amr` analogue; the ADR does not invent one). A session authenticated through the provider gains multi-factor assurance only when the statement's ACCR is in the accepted set.
- **A provider with no assurance policy configured yields single-factor assurance** — sufficient to log in, insufficient to reveal. Identical to the OIDC default, and the safe one: an IdP that "does MFA" globally is an assertion the protocol does not carry.
- **`RequestedAuthnContext` is never sent.** Requesting a context proves nothing about the response — verification is the control either way — and IdP handling of exact-match requests is a notorious quirk surface (Entra's is the canonical example). Envweave verifies what came back; it does not negotiate.
- The session's assurance record stores the method as `saml:<entityID>`, **the provider row id** (for deterministic session invalidation on provider change), the asserted ACCR, and `AuthnInstant` — the direct analogue of the OIDC record's `acr`/`amr`/`auth_time`.

**Reauthentication re-runs the ceremony with `ForceAuthn="true"`** (asserted on the outgoing request by fixture), purpose `reauth`, initiator-bound, and is accepted only when the returned assertion carries the **same identity pair**, an `AuthnInstant` within the freshness bound (**5 minutes + skew**, the value fixed here and catalogued), and an ACCR satisfying the provider's assurance policy — the SAML rendering of human-auth's `prompt=login` + `max_age=0` + same-`(issuer, subject)` rule, with the same stated caveat: `ForceAuthn` alone proves neither freshness nor factors (an IdP may honour it weakly), which is why `AuthnInstant` and the policy check are load-bearing and `ForceAuthn` is merely the request.

Sessions authenticated through a SAML provider are **deleted when that provider is disabled, removed, or has its assurance policy or certificate set changed**, and when the identity linking them is unlinked — human-auth's session-deletion rule, keyed by the provider row id in the assurance record, with certificate-set changes added because for SAML the certificate set *is* the trust anchor.

## JIT provisioning: none for SAML

**No `jit_provision` policy exists for SAML providers.** Provisioning is invitation ([human-auth.md](./human-auth.md)) or SCIM ([#38](https://github.com/Dunky13/envweave/issues/38)) — SAML is authentication only. Two grounds, either sufficient: (1) SAML JIT beside SCIM is a second provisioning language — two mechanisms answering "how does an enterprise user come to exist", with the reconciliation gap (#38's named obstacle) doubled; (2) human-auth's JIT rule requires naming an issuer-specific **verified** claim, and SAML has no per-claim verification semantics to name — every attribute is equally IdP-asserted, so the rule does not translate; reading "signed assertion" as verification would loosen a locked rule in the act of transferring it. **Named reopen trigger**: if [#38](https://github.com/Dunky13/envweave/issues/38) demotes SCIM out of 1.0, this decision reopens — recorded here so the gap cannot arrive silently. The no-surface claim is executable: SA2 asserts no SAML JIT configuration field exists in the API schema.

## Metadata and trust

**Three trust roots, named separately, never conflated:**

1. **Fetch-channel trust** — the one-shot metadata URL fetch rides ordinary WebPKI TLS under the threat model's outbound-request class (no redirects off-origin, size-capped, one shot, admin-initiated). File upload has no channel at all. The channel authenticates the *download*, nothing else.
2. **Metadata-signature trust** — when the metadata document is signed, the signing certificate's fingerprint is **displayed at first configure and explicitly confirmed by the admin** (the CLI SPKI trust-establishment ceremony's shape); the confirmed key is pinned. A later refresh signed by the pinned key verifies silently; **a changed metadata-signing key is a new ceremony** — refused until the admin confirms the new fingerprint. An unsigned document is accepted **with the fact recorded and shown** (most IdP metadata is unsigned-over-TLS; refusing it would be theatre while the channel is the real root), and an unsigned *refresh* of a previously-signed provider is a refusal — signature stripping is a downgrade, not a variant. **Verification is structurally bound to the descriptor consumed, by the same discipline the login path uses**: the metadata document passes the same pre-parse bounds, roundtrip validation, single-parse and unique-ID rules; the signature's single same-document `Reference` must resolve to the **selected `EntityDescriptor` or an ancestor element containing it** (under the closed algorithm/transform allowlist), and every field consumed — endpoints, KeyDescriptors, validUntil — is extracted **from the verified subtree** returned by the verifier, never from the pre-verification tree. A signature covering anything else, or a selected descriptor outside the verified subtree, is a refusal: metadata signature wrapping is the same attack as assertion wrapping and gets the same structural answer.
3. **Assertion-signing trust** — the certificates Envweave actually validates logins against. Extracted from **exactly one `EntityDescriptor` whose entityID equals the configured provider's** (a multi-entity aggregate contributes nothing else; zero or multiple matches = refusal), from its **`IDPSSODescriptor` supporting the SAML 2.0 protocol**, taking `KeyDescriptor` entries with `use="signing"` or no `use` attribute (spec semantics: absent = both). The certificates are consumed as **raw pinned public keys**: no PKIX chain building, no EKU evaluation, no trust-store consultation — the pin *is* the trust decision, stated plainly. X.509 validity dates are recorded and surfaced as warnings (an expired pinned cert is an operational smell), **not enforced** — pinned-key semantics, consistent with how every SAML IdP fleet actually rotates.

**Every refresh is a diff-and-confirm ceremony**: endpoint changes and certificate additions/removals are displayed as a diff with fingerprints, and **applying any new certificate or endpoint requires explicit admin confirmation** — under `instance-config` authorization (provider configuration is instance-scoped state, [tenant-isolation.md](./tenant-isolation.md)), audited with the diff summary. The certificate set holds multiple certificates simultaneously, so IdP rollover is: refresh while the old cert still signs → both trusted → IdP switches → refresh to drop the old. No outage window, no scheduled job.

**No background poller exists** (the architecture ADR ships no generic job framework, and a poller is standing egress the air-gapped install cannot perform); refresh is the same admin action re-run. **`validUntil` is honoured fail-closed**: expired metadata refuses logins through that provider with the distinct error naming the cause; absent `validUntil` = no expiry bound. In-product warnings surface ahead of expiry (the expiry-warning transport human-auth already fixes: in-product first, SMTP additive), and `doctor` nags. The local floor is never disableable, so metadata expiry is never lockout — it is a loud, attributable SAML outage an admin resolves by refreshing, which is the fail-fast posture chosen over silently trusting stale metadata. `cacheDuration` is ignored (it is a polling hint; there is no poller), stated plainly.

## SP-side material

- **SP metadata is published at an unauthenticated endpoint** — entityID, ACS URLs (per provider), the SP signing certificate set, `WantAssertionsSigned="true"`, `AuthnRequestsSigned` per configuration. Its content is documentation-class by construction (nothing secret is in SP metadata); the endpoint sits under the pre-auth admission limits every unauthenticated path carries ([human-auth.md](./human-auth.md)) and is probe-classified unauthenticated ([tenant-isolation.md](./tenant-isolation.md)).
- **One SP signing keypair**: **RSA-3072**, generated at first SAML provider configure, wrapped in a **self-signed certificate** (SAML metadata convention; the certificate is a key container, not a trust statement — IdPs pin it from metadata). Private key stored **encrypted under the instance DEK with the existing `instance_field` AAD schema** ([encryption-model.md](./encryption-model.md)), the AAD's owner tag naming the SP-key row — **no new AAD schema kind is introduced and the locked per-kind table is untouched**. Key states: `active` | `retiring`. Rotation is a manual verb: mint-new (new active, old retiring) → both certificates published in SP metadata → IdPs refresh → retire-old (removed from metadata, key erased). **Compromise procedure**: immediate retire (skip the overlap — a compromised key signs requests, and request signatures are the IdP's control, so the blast radius is IdP-side policy bypass, stated honestly), mint, then the IdP-refresh runbook; audited throughout.
- **AuthnRequests are signed when the IdP's metadata declares `WantAuthnRequestsSigned="true"`, or when the per-provider override forces it** (for IdPs that require signing but publish sloppy metadata — ADFS policy commonly). Redirect-binding signing follows the binding specification **exactly**: the signature is computed by the library over the **exact octet sequence** `SAMLRequest=<url-encoded-deflated-request>[&RelayState=<url-encoded-value>]&SigAlg=<url-encoded-algorithm-URI>` — RelayState included when present, the same encoded octets that go on the wire (re-encoding between signing and sending changes the signed message and is a fixture-guarded bug class). `SigAlg` is **exactly** `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`. Unsigned otherwise: request signing authenticates the SP to the IdP and is the IdP's call to demand; response security carries Envweave's side of the load.

## Coexistence, sessions, CLI

SAML providers sit **beside** OIDC providers in the same instance-scoped provider configuration: same table shape, same per-provider assurance policy slot, same audit events on configuration change, same session-deletion semantics, same "unauthorized ≡ nonexistent" surface behaviour. **One active provider per `(kind, issuer)` is a database uniqueness constraint**: two simultaneously-active SAML providers claiming one entityID would resolve the same identity population under different certificate sets and assurance policies — the weaker configuration authenticating identities established through the stronger one is provider mix-up reintroduced at the configuration layer, and the constraint closes it structurally (a second registration of a live entityID is refused by name). The login page lists both kinds indistinguishably (a user picks "their" IdP, not a protocol). The mix-up defence across the whole provider set is the conjunction in § *The validation algorithm*: per-provider ACS, transaction-recorded provider, both Issuer legs byte-exact — strictly stronger than either of the two options human-auth licenses for OIDC alone.

A SAML login mints the **ordinary opaque server-side session** — same artifact, same rows, same generation/invalidation machinery; the assurance record (with provider row id) is the only SAML-shaped content. **CLI login and reauth ride the locked browser-handoff transports unchanged** ([api-cli-surface.md](./api-cli-surface.md)): the browser performs the SAML ceremony exactly as it performs OIDC; the loopback/device handoff carries code+state, never the artifact; the SAML transaction records the handoff it serves (§ *The SAML transaction*). The device-fallback and local-floor paths are untouched.

## Audit

SAML events join the closed `category.action` registry ([audit-model.md](./audit-model.md)) by the same mechanism every upstream ADR's MUST-emit list joined it — this ADR's list, **enumerated as registry entries, each with a versioned payload schema** (all: category `auth`, retention class `security`, standard envelope per audit-model — UUIDv7, seq, actor/authority, scope class + id chain, IP+UA, server timestamp; payload schemas below are **v1** and evolve only by registry version bump):

- `auth.saml_login` — outcome `success | failure`; payload v1: `{provider_id, entity_id, purpose, cause?, name_id_format?, authn_context_class_ref?, transaction_id}` — `cause` on failure only, from the **closed cause-code enum** matching § *The validation algorithm*'s refusal list, one code per named refusal; the identity pair joins only on success (a failed login must not oracle identities). Aggregable under flood per audit-model's licence; successes never aggregated.
- `auth.saml_reauth` — same outcome + payload schema, `purpose = reauth`, cause enum extended with purpose/initiator mismatch codes.
- `auth.saml_provider_configure` / `auth.saml_provider_refresh` / `auth.saml_provider_remove` — outcome `success | failure`; payload v1: `{provider_id, entity_id, source: file|url, signed: bool, diff: {endpoints_added[], endpoints_removed[], certs_added_fps[], certs_removed_fps[], valid_until?}, confirmed_fps[]}` — fingerprints and endpoints, never key material.
- `auth.saml_cert_change` — payload v1: `{provider_id, entity_id, change: added|removed|confirmed, fingerprint}`.
- `auth.saml_nameid_email_optin` — payload v1: `{provider_id, entity_id, state: set|unset}`.
- `auth.saml_sp_key` — payload v1: `{action: mint|rotate|retire|compromise_retire, key_fingerprint, prior_key_fingerprint?}`.
- `auth.saml_metadata_expiry_warning` — payload v1: `{provider_id, entity_id, valid_until, threshold}`.
- Identity link/unlink reuse the **existing** identity events and their schemas, now kind-qualified by the amended key (their payload gains the `kind` field in the same registry version bump that lands the key amendment).

Registry-completeness CI ([audit-model.md](./audit-model.md)'s invariant against the probe-classification registry) covers every SAML operation the moment it is registered — the SAML endpoints and verbs are probe-classified like everything else, so an unregistered SAML path fails the build.
