Context: the product positioning ([#3](https://github.com/Dunky13/wenv/issues/3)) fixed **Go, single binary, pluggable datastores (sqlite + postgres in v1)** as the delivery shape; the threat model ([threat-model.md](./threat-model.md)) fixes what the runtime must and must not promise; ten further locked ADRs fix the behaviour the architecture must carry (inheritance, schema, revisions, source-of-truth, encryption, permissions, human auth, machine identities, Compose, Kubernetes). This ADR fixes the **component set, the concrete stack, the API contract mechanism, the transaction and authorization chokepoints, the encryption boundary's placement in code, transport/TLS posture, and the release artifacts** — the decisions an implementing team would otherwise make on day one and find expensive to reverse.

Granularity note: this is the wayfinding-level architecture ADR. It fixes the stack and the structural chokepoints. Mechanism-level detail is delegated: the tenant-isolation chokepoint pattern → [#23](https://github.com/Dunky13/wenv/issues/23); the concrete API and CLI surface → [#25](https://github.com/Dunky13/wenv/issues/25) (bound by [#19](https://github.com/Dunky13/wenv/issues/19)'s integration-neutrality constraint); operational bounds, tuning values, and runbooks → the ops spec. Each delegated ticket MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

## Component set — modular monolith, one multicall binary

**Confirmed: modular monolith.** No microservices; no concrete need was found in any locked ADR, and the deployment envelope (1–3 orgs, ≤25 users, ≤10k entries, single node, no HA in v1 — #3) argues the opposite. The system is **one Go multicall binary** exposing subcommands:

- `wenv server` — the control plane: API, embedded web UI, SSE, scheduler, adapter outbox, migrations-at-boot. **The only mode that loads the keyring.**
- `wenv operator` — the Kubernetes operator ([k8s-integration.md](./k8s-integration.md)). Per that ADR's binding propagation, the operator is a **separate deployable: its own Deployment, its own process, its own pod** — never a mode of the running server process. "Same binary" is an *artifact* statement, not a *process* statement: the operator Deployment runs the same multicall executable with a different entrypoint. Stack fixed: **controller-runtime** (the #19 presumption, confirmed), version pinned in-module. Single replica default; leader election enabled so a second replica is safe, not split-brained.
- `wenv migrate` — explicit migration application. Loads no keyring (DDL only).
- Client verbs — `login`, `run`, `render`, `sync`, `adopt`, `doctor` ([compose-integration.md](./compose-integration.md)), `definitions export|check|plan|apply` ([source-of-truth.md](./source-of-truth.md)), service-account/credential management ([machine-identities.md](./machine-identities.md)), rotation/backup verbs ([encryption-model.md](./encryption-model.md)), remainder fixed by #25. Client verbs never load the keyring and hold no resident state: per the Compose ADR's binding constraint, **there is no resident client-side agent; `sync` is one-shot, timer-invoked.**

One artifact, one version string, one install story. Version skew between CLI, operator, and server is eliminated *as a release problem* by construction (an old CLI against a new server is an API-versioning matter, #25).

**Consequences of the multicall shape, stated honestly (not just download size):** every artifact carries the union of server, auth, crypto, migration, adapter, datastore, and operator code. A CVE anywhere in that union obliges a release of *the* artifact; the SBOM and scanner surface are unioned; a workstation CLI download contains server code it never runs. The alternative — several binaries built from one repo and tag — reduces *code surface per artifact* but not the *release train* (one repo, one tag, one pipeline either way), and reintroduces artifact-matrix and doc complexity for a small team. Decision: **multicall retained**, with the consequence managed rather than denied:

- **Mode-pinned deployment**: the Helm chart and reference compose pin the command per workload (`server` vs `operator`); no deployable ever runs with a mode-selectable entrypoint exposed to config injection.
- **Runtime hardening baseline**: distroless/`scratch` image, non-root UID, read-only root filesystem, no shell in image; each mode mounts only its own credentials (the operator pod mounts no root key; the server pod mounts no stamp root).
- Distinct *images* with the same binary reduce configuration mistakes, not code surface — recorded so nobody mistakes image-splitting for attack-surface reduction later.

*Rejected:* two binaries (`wenvd` + thin CLI) and three binaries (server/CLI/operator) — smaller per-artifact code surface, but permanent split-pipeline and skew-matrix costs against a small OSS team, and the security gain is marginal when the release train is shared anyway (a compromised pipeline signs all artifacts alike).

## Backend — Go, chi over stdlib

Go is inherited from #3 and reaffirmed by everything since: the human-auth ADR selected composed Go libraries (`scs`, `argon2`, `go-oidc`, `pquerna/otp`, `go-webauthn`), the encryption ADR selected `x/crypto` XChaCha20-Poly1305, noted constant-time software crypto matters on Pi-class hardware, recorded the Go-zeroization residual as an input here (accepted; see § Encryption boundary), and fixed a **minimum toolchain of Go 1.24** (stdlib `crypto/hkdf`) — that floor is binding on this ADR.

**HTTP layer: [chi](https://github.com/go-chi/chi).** Thin, stdlib-compatible (`http.Handler` end to end), no reflection, no binding magic — compatible with parse-don't-cast. It buys route groups/mounting — the API has distinct middleware stacks (browser-session surface, token surface, SSE, metrics/health) — at the cost of one small, stable, widely-known dependency.

**Middleware extracts authentication artifacts; it never authenticates or authorizes.** This is a binding structural rule, forced by three locked propagations: the permission ADR requires every sensitive operation to call one `authorize(principal, capability, scope)` reading current policy **inside the operation's own transaction**, uncached; the human-auth ADR requires session resolution and the session-assurance check to run **inside that same chokepoint**; the machine-identity ADR requires machine-credential resolution at the same chokepoint, in-transaction, uncached. A request middleware runs before the domain transaction exists and runs once — it structurally cannot satisfy any of the three. So middleware does **syntax only**: it extracts the presented artifact (session cookie, bearer token) from the request, checks its shape, and attaches the *unverified artifact* to the request context — **no datastore lookup, no verification, no principal**. **Resolution of the artifact to a principal — session lookup, verifier-hash comparison, credential epoch and session generation checks, session-assurance, tenant-ownership, recovery-mode state — happens inside the service-layer transaction at the same chokepoint as `authorize()`**, exactly as the three locked propagations require. There is no "authenticated principal" outside a transaction anywhere in the system. Handlers cannot reach the datastore directly: `internal/store` is importable only by `internal/service` — enforced by the same import-boundary test machinery as the crypto chokepoint (§ Encryption boundary). Long-running work re-authorizes before every sensitive step against the recorded authority principal, per the permission ADR — the scheduler and outbox (§ Jobs) route through the same chokepoint, not around it.

The architecture also provides, as boot obligations fixed by the human-auth ADR: the **Argon2id parameter floor check as a startup failure**, the **instance-wide pre-authentication admission semaphore** (bounded concurrency + queue depth on login/token-exchange paths; values → ops spec), and **immutable RP ID / WebAuthn origin configuration** (never request-derived). The machine-identity ADR's **JWKS cache** lives server-side with its bounded staleness window and rate-limited refresh; the threat model's **recovery mode** (restored credentials inert until operator reconciliation) is a server state the chokepoint consults — restored artifacts are refused *at authorization*, not by ad-hoc checks.

*Rejected:* bare `net/http` 1.22 mux — viable, but hand-rolling groups/mounting for four middleware stacks is chi rewritten badly; echo/gin — context-magic and reflection-based binding fight parse-don't-cast; framework churn is a maintenance tax on a decade-scale OSS project.

## Data layer — sqlc, pgx, modernc.org/sqlite, goose

**Both engines ship in v1** (confirmed from #3): **postgres** via `pgx`, **sqlite** via `modernc.org/sqlite` — the pure-Go port, keeping the binary **CGO-free** and trivially cross-compilable. sqlite is the tiny-install path; postgres the multi-user default. Remote postgres connections require TLS with certificate verification or a same-host socket — threat-model boundary, restated here because the connection string is architecture's to validate (fail-fast at boot, no `sslmode=disable` on a non-loopback host).

**Query layer: [sqlc](https://sqlc.dev).** SQL in `.sql` files; sqlc generates type-safe Go per query — no reflection, no `interface{}` scanning: the query layer obeys parse-don't-cast structurally. The authorization formulas, serializable publish pipeline, and append-only audit want *explicit* SQL, not an ORM's approximation.

**Dual-dialect discipline** (the honest cost, managed): dialect-divergent queries live in per-dialect query files; **all generated code sits behind per-aggregate repository interfaces in `internal/store`** — no service code ever sees a pgx or sqlite type. Canonical cross-engine semantics are fixed in one place (`internal/store`): timestamps stored and compared as UTC RFC 3339 text on sqlite / `timestamptz` on postgres, booleans as integers on sqlite, JSON as text validated at the boundary; a **cross-engine conformance suite** runs the same scenario corpus against both engines in CI — not just unit tests per dialect. **SQLite connection policy is fixed and boot-enforced**: `foreign_keys=ON`, WAL journal mode, `synchronous=FULL` (the threat model's audit-durable-before-completion rule requires per-commit durability; WAL+`NORMAL` can lose the last commits on power failure), `busy_timeout` set, and a **single write connection** (pool of one for writes, read pool separate). If any pragma cannot be established, boot refuses — no silent downgrade.

### Transaction boundary — one package owns "serializable"

The revision ADR requires publish serialization per project; the permission ADR requires in-transaction authorization. One package (`internal/store/tx`) owns the transactional boundary, and its contract is fixed here:

- **Postgres:** `SERIALIZABLE` isolation for publish-class operations; the entire operation closure retries (bounded, with backoff) on SQLSTATE `40001`/`40P01`. 
- **SQLite:** publish-class operations open `BEGIN IMMEDIATE` (write intent acquired before reads — a deferred begin can read an old WAL snapshot and die on `SQLITE_BUSY_SNAPSHOT` mid-way); `read_uncommitted` prohibited; busy/locked failures retry the whole closure. Stated honestly: sqlite serializes **all** writes globally, not merely per-project — an accepted throughput property at this envelope, not a correctness problem.
- **Retries are bounded on both engines** — bounded attempt count with backoff, sqlite exactly as postgres; exhaustion surfaces as a loud operation failure, never an infinite loop or a silent drop.
- **On both engines:** the retried unit is the *whole closure* — authorization included, per the permission ADR's in-transaction rule — and **no external effect (adapter push, SSE emit, response write) may escape before commit**; effects are emitted after successful commit, or through the outbox (§ Jobs) which is itself committed state.

**Migrations: [goose](https://github.com/pressly/goose)**, embedded via `embed.FS`, per-dialect directories where SQL diverges, **library mode with locking**: on postgres, goose's session-level advisory lock (`SessionLocker`) serializes concurrent migrators (boot racing an explicit `wenv migrate` racing an old server); on sqlite, per-migration transactions do **not** lock the whole run against a second process, so the **entire migration run holds an advisory file lock** (`flock` on a lockfile beside the database — sound because sqlite is same-host by construction) taken by both boot-time migration and `wenv migrate`. Policy fixed: **roll-forward only** (no down-migrations in production paths); a failed migration leaves the process **refusing to serve** (fail closed, loud) — never a half-migrated server taking traffic; readiness reports not-ready until migrations complete. Auto-apply at `server` boot remains the default (single-node v1); a config flag disables it for operators who insist on explicit `wenv migrate`. Version-compatibility window and downgrade guidance → ops spec.

**Upgrade/backup protocol** (binding, because the encryption ADR's backup design makes casual "backup before upgrading" advice wrong): the pre-upgrade backup is the encryption ADR's **`backup-export`** — an age-encrypted, *consistent* datastore export — not a file copy. Consistency mechanism fixed per engine: SQLite Online Backup API / `VACUUM INTO` (a raw copy of a live WAL database can be torn); a serializable-snapshot export on postgres. Ordering rule: **backup-export with the old binary before any new binary runs DDL**. As defense-in-depth at the tiny-install tier, sqlite boot-time migration additionally runs an automatic **`backup-export`** (age-encrypted, consistent — the same pipeline, never a raw file copy: a retained plaintext snapshot would be exactly the unencrypted backup artifact the threat model and encryption ADR reject) **iff one or more public backup recipients are configured** (the instance holds public recipients only, per the encryption ADR); with none configured it is skipped with a loud boot warning — the encryption ADR refuses zero-recipient exports, and inventing an implicit recipient would be a silent fallback. Retention count → ops spec. Restore-testing cadence and runbooks → ops spec.

*Rejected:* hand SQL over `database/sql` — every scan is hand-written boilerplate, the cast-shaped bug surface sqlc deletes; ent — easiest dual-dialect story but a query DSL that fights the explicit SQL the locked ADRs require; GORM — reflection-based, contradicts the code standards outright; river and similar postgres-only infrastructure — dead on arrival against the sqlite commitment.

## Frontend — React + TypeScript + Vite, embedded

The matrix UI is a heavy stateful client: virtualized environment-matrix grid, per-cell edit state, draft/publish flows, SSE-driven advisory updates, WebAuthn ceremonies ([#20](https://github.com/Dunky13/wenv/issues/20)/[#21](https://github.com/Dunky13/wenv/issues/21)). That is an SPA; server-rendered HTML or htmx would fight the ceremony modal and the live matrix at every step.

**React + TypeScript + Vite**, served from the server binary via `embed.FS`. Selection checked, not defaulted: React's contributor pool is the largest of the candidates (the ticket's own criterion for an OSS project — recorded as a qualitative judgment, not a citation-bearing count) and its ecosystem is deepest exactly where this UI is hard: virtualization (TanStack Virtual), server-state (TanStack Query), WebAuthn. Strict TypeScript; every API response crosses generated runtime schemas at the boundary (§ API contract). The prototypes are deliberately framework-free single-file HTML; the design language transfers, no code does.

**Embedded serving is specified, not assumed** (`embed.FS` has no SPA semantics of its own):

- **Route partitioning:** `/api/`, `/metrics`, `/healthz`, and the hashed-asset prefix are reserved and **never** fall back to the SPA; unknown paths under them 404 as JSON/text. SPA fallback to `index.html` applies only to non-reserved `GET`/`HEAD` requests that accept `text/html`. A missing hashed asset 404s — it is a build error, not a route.
- **Caching:** hashed assets `Cache-Control: immutable`; `index.html` no-cache; secret-plaintext API responses already carry `no-store` (#21).
- **Security headers:** a baseline ships in v1 — CSP (no inline script, self-only by default), `frame-ancestors 'none'`, `nosniff`, referrer policy; exact header set → #25/ops spec, but the *existence* of the baseline is fixed here.
- **Base path:** v1 serves at the domain root only; subpath mounting is deferred (documented), root-only keeps RP ID/origin and asset resolution trivial.

*Rejected:* Svelte 5 (smaller bundle, smaller pool), SolidJS (best grid performance, smallest pool), htmx/server-rendered (wrong shape for ceremony + live matrix).

## API contract — OpenAPI 3.0.3, spec-first, generated both sides, contract-tested

**REST/JSON with a hand-written OpenAPI document as the single source of truth** (`api/openapi.yaml`). **OpenAPI 3.0.3, not 3.1** — chosen for the toolchain that exists, not the spec that's newest: `oapi-codegen` (the Go generator this ADR pins) does not support 3.1; pinning 3.0.3 is honest, and a later 3.1 migration is a tooling change, not an architecture change. Nobody hand-writes API types:

- **Go:** `oapi-codegen` **strict-server** mode generates chi-compatible server interfaces and request/response structs — handler signatures are compile-checked against the spec. **Request validation at runtime** via the kin-openapi validation middleware (strict-server generates types; it does not validate incoming payloads by itself — stated so nobody assumes otherwise).
- **TypeScript:** `@hey-api/openapi-ts` generates the typed client **plus Zod schemas**; the SPA *parses* responses at runtime (parse-don't-cast on the client), not merely annotates them.
- **CI, three layers because each catches what the others cannot:** (1) regeneration + `git diff --exit-code` — stale generated code is a red build; (2) **HTTP contract tests**: the Go test suite runs real handlers via `httptest` and validates *actual wire responses* against the spec with the kin-openapi response validator — this is what catches a handler emitting spec-inconsistent data despite compiling; (3) the cross-engine conformance suite (§ Data layer) runs under the same harness. Generated code is committed (reviewable diffs, tarball-buildable).

The spec is the reviewable contract #25 details, the artifact whose freeze #19's ESO-provider extension path waits on, and the single document the integration-neutrality constraint (no operator-special endpoints) is checked against.

Authorization posture restated for the API layer: there is **no authorization cache** (permission ADR); authorization is evaluated in-transaction per operation (§ Backend). Unauthorized ≡ nonexistent shapes every route's error behaviour, including bulk counts and timing — the contract tests assert the *same status and body shape* for missing vs unauthorized on every object route.

*Rejected:* OpenAPI 3.1 today (generator support absent where it matters); code-first OpenAPI (the spec drifts to whatever the code does); gRPC + gateway (browser needs the gateway anyway = two surfaces, operators lose curl); GraphQL (resolver-level authorization is the re-implemented-per-endpoint trap #23's chokepoint rule exists to prevent; unauthorized-≡-nonexistent is hostile to introspective schemas).

## Transport — TLS posture and proxy trust

The threat model requires authenticated TLS on **every non-loopback boundary**; the human-auth ADR requires immutable RP ID/origin and explicit proxy trust. Architecture fixes the model; values go to the ops spec.

- **Native TLS ships in v1**: the server terminates TLS itself given a certificate and key (file-based; reload → ops spec). No ACME/autocert in v1 — it adds unsolicited egress the threat model's telemetry stance forbids by default; documented as an extension.
- **Plaintext binds are constrained**: permitted on loopback without ceremony; a non-loopback plaintext bind **refuses to start** unless the operator explicitly configures reverse-proxy mode, which requires naming the **trusted proxy CIDRs**. Forwarded headers (`X-Forwarded-For`/`-Proto`) are believed **only** from those CIDRs — an unauthenticated header is not evidence (human-auth ADR).
- **WebAuthn RP ID and expected origins are immutable instance configuration** (human-auth ADR), never derived from Host/forwarded headers; the server refuses to start if reverse-proxy mode is configured without them.
- **Reference artifacts carry the posture**: the reference `compose.yaml` shows the TLS-terminating-proxy pattern with the trust configuration filled in; the Helm chart defaults to Ingress-terminated TLS with the proxy trust preconfigured for the cluster's ingress; both fail closed when unset.
- `/metrics` and `/healthz` bind separately (loopback/cluster-internal default) so operational surfaces don't ride the public listener.

## Real-time — SSE, polling fallback

Confirms the revision ADR's recommendation: **Server-Sent Events** for the advisory update channel — plain HTTP, native `EventSource`, curl-debuggable, one-directional exactly like the data (advisory, metadata-only, per-event authorized, recipient-projected — all fixed in [revision-model.md](./revision-model.md)). Stated honestly: SSE is *not* proxy-transparent by default — nginx buffers responses unless told otherwise, and intermediaries impose idle timeouts. The v1 requirements that make it work are fixed here:

- Stream responses set `Cache-Control: no-cache` and `X-Accel-Buffering: no`, flush per event, and send **heartbeat comments** on an interval (value → ops spec) to defeat idle timeouts and detect dead peers.
- **Bounded per-connection buffers with slow-client disconnect**: a client that cannot keep up is dropped, never buffered unboundedly.
- **Connection admission**: per-principal, per-org, and instance-wide SSE connection caps (values → ops spec) — the stream endpoint sits under the same resource-exhaustion posture as every other attacker-triggerable path (threat model availability baseline). Reconnect uses `EventSource`'s retry with server-suggested jitter.
- **`Last-Event-ID` replays nothing.** Events are advisory; a reconnecting client performs a normal authorized refetch of current state and resubscribes. No event history is retained for replay — retention would be a second audit log with weaker rules.
- The SSE endpoint authenticates on the same session artifact as the browser surface; every event passes the revision ADR's per-event authorization at emit time. **Polling fallback** ships for environments where streaming remains hostile.

*Rejected:* WebSocket — bidirectional capability nothing in the locked model uses; costs upgrade negotiation and its own auth path. WebRTC was already rejected in #11.

## Jobs — no generic framework; one domain-specific outbox

Inventory of durable/periodic work across the locked ADRs: `reencrypt` (designed per-row resumable and lock-free in [encryption-model.md](./encryption-model.md)), rotation finalization (dual-wrapped root transition), retention/GC sweeps (revision payloads, superseded draft versions, expired pins, render generations), credential-expiry warnings, JWKS refresh, audit-retention pruning — all periodic or resumable-by-design, handled by an **in-process scheduler** (ticker/cron) with progress recorded in domain tables and resumed at boot. Failures surface loudly: health endpoint + structured logs.

**One piece of durable machinery is required now, not speculatively: the adapter outbox.** The threat model *already* requires — for the v1 Forgejo adapter, not a hypothetical — durable INTENT records before any external call, terminal OUTCOME records (success/failure/unknown) after, retry backoff **with deduplication**, bounded queue depth and concurrency; the permission ADR requires re-authorization against the recorded authority principal before **every** retry and push. So the architecture defines a **domain-specific outbox** (not a generic job queue): a table carrying job identity, the **authority principal**, idempotency/dedup key, attempt count and next-attempt time, a **lease** (crash recovery — a worker that dies mid-push loses its lease and the job is retried, deduplicated), terminal state, and the linkage to its audit INTENT/OUTCOME records. Works identically on both engines (it is ordinary transactional table state); bounded concurrency enforced by the scheduler. #28 fills in adapter semantics; the machinery shape is fixed here so #28 designs against it rather than inventing it.

*Rejected:* a generic DB-backed job framework — the outbox is the one durable queue the locked ADRs demand, and generalizing it is speculative machinery doubled across two engines; river/gocraft — postgres-only or unmaintained.

## Encryption boundary — implementing the locked chokepoint

The encryption ADR fixed the chokepoint (its CI-enforced invariant 12: no cryptographic-primitive import outside the envelope package; age nowhere outside the backup package) and handed this ticket the Go-zeroization residual. This section **implements** those decisions in the code structure — it does not add a new invariant, and an import check is a **guardrail, not a cryptographic boundary**: it cannot catch a wrapper re-exporting a primitive, unsafe code *inside* the allowed package, or a hostile transitive dependency. Those are covered by the threat model's mandatory security review on crypto-touching contributions, the encryption ADR's test vectors and CI invariants, and dependency pinning — the import check just makes accidental drift loud.

- **`internal/crypto` is the envelope package**: keyring (root → master → tier-3 DEKs), the seven per-kind AAD schemas and length-prefixed encoding, versioned ciphertext envelope, DEK cache (bound → ops spec), rotation state machines. `internal/crypto/backup` is the sole `filippo.io/age` importer. The import-boundary test enumerates exact allowlists (direct imports per package, dependency direction service→store, handlers never importing store) and fails the build on violation.
- **Plaintext exists only in an explicitly owned operation scope** — a request, a delivery fetch, an adapter push attempt, a `reencrypt` batch, a backup export/restore — and is never retained past its operation. Not all of these are request-scoped (reencrypt and outbox pushes are not); the rule is *ownership and non-retention*, not "requests only". The repository layer stores and returns ciphertext exclusively — a query path is never a plaintext path. No plaintext in caches, logs, audit records, SSE events, or error strings — each locked upstream; the placement makes them one structural fact.
- **Keyring lifecycle by mode:** only `wenv server` loads the keyring. The root key is read at boot (file or systemd credential preferred), unwraps the master key, and is zeroed; it is re-read on `rotate-root-key`. The `WENV_ROOT_KEY` environment residual is the encryption ADR's, restated: an env-delivered root key sits in process memory for the process lifetime and cannot be wiped — documentation steers to the file path. Operator and client subcommands never touch the keyring.
- **Zeroization, honestly:** Go's GC gives no wipe guarantee; key-material buffers are best-effort zeroed, `RLIMIT_CORE=0` / `PR_SET_DUMPABLE=0` per the encryption ADR, and **no memory-secrecy claim is made** — consistent with the threat model's running-server-compromise stance.

*Rejected:* transparent decrypt in the repository layer (every query path becomes a plaintext path; the chokepoint dissolves); a crypto sidecar process (real memory isolation, but two processes against a threat — running-server compromise — the model already concedes).

## Client local state — protection model

The Compose ADR binds this ADR to provide it: the client state directory (stamp key, snapshot key, offline snapshots, render generations, offline per-key audit records) lives under the XDG state directory, `0700` directory / `0600` files, ownership checked; `doctor` verifies and reports violations; the stamp and snapshot keys are **client-side secrets outside the server key hierarchy** — their loss fails delivery closed (full fetch / no offline serve), never open. Backup guidance for them → ops spec. The K8s operator's stamp root is the same concept in-cluster: a Kubernetes Secret owned by the operator's namespace, mounted as a file, RBAC-restricted to the operator ServiceAccount, **excluded from Wenv server backups** (it is client-side material); rotation = replace the Secret — by #19's amendment this invalidates cursors and forces full fetches, **no restart wave**; loss is recovered identically (regenerate, full fetch). Custody runbooks → ops spec.

## Packaging & release artifacts

- **Container image:** one image, distroless/`scratch`, the single static CGO-free binary with UI and migrations embedded, non-root, read-only rootfs (§ Component set hardening baseline). **Multi-arch `linux/amd64` + `linux/arm64`** — arm64 is load-bearing (Pi-class targets in the encryption and Kubernetes ADRs). Published to **ghcr.io**. Server vs operator = command pinned per workload by the deployment artifacts.
- **Bare binaries:** goreleaser; linux/darwin/windows, amd64+arm64.
- **Supply chain — the threat model delegated mechanisms here; fixed now:**
  - **Trust model: long-lived signing key pair with custody outside CI** — the threat model's locked text ("signing key held outside CI") rules out keyless/OIDC CI signing, which would make the CI pipeline the signing authority. Release flow: CI builds reproducibly pinned artifacts, checksums, and images; a **named maintainer signs locally with the offline cosign key-pair — both the checksum manifest for bare binaries *and* the container image digests** (cosign image signatures pushed to ghcr.io alongside the images). The public key is the **pinned trust root** shipped with installers, docs, and the Helm chart.
  - Official install/upgrade paths **fail closed** on signature verification against that pinned root; manual downloaders who skip verification are outside the guarantee (documented, per threat model). The Helm chart references images **by digest**, and the published admission-verification policy (cosign public key, for cluster admission controllers) ships alongside the chart — a policy that verifies signatures that exist, not a promise of one.
  - **Pinned everything:** Go toolchain version, base image digests, module checksums (`go.sum` + `GOFLAGS=-mod=readonly`), goreleaser version, **frontend toolchain (pinned Node version + pnpm lockfile with frozen installs), and CI workflow actions pinned by commit SHA**. **SBOM published per release** covering both Go modules and frontend dependencies; provenance attestation is the named extension path (threat model). Re-key/revocation procedure → ops spec/OSS-mechanics, but the *existence* of a documented re-key path is required here.
- **Reference `compose.yaml`:** first-class, versioned in-repo, carrying the TLS/proxy posture (§ Transport). Wenv-in-a-stack is a scenario the Compose ADR designs for; the reference stack doubles as documentation and test fixture.
- **Helm chart:** first-class, in-repo; server Deployment, operator Deployment (separate deployable, § Component set), CRDs (`WenvInstance`, `WenvSecret`), mode-pinned commands, hardening defaults on.
- **Datastore defaults, fail-fast:** `--dev` runs sqlite zero-config for evaluation. A production start refuses to boot without explicit datastore configuration — nothing silently conjures a database. Reference compose and chart set `WENV_DB` explicitly.

## Tooling defaults (non-load-bearing, recorded to stop re-litigation)

Structured logging via stdlib `log/slog`, JSON in production, through the threat model's **redacting logger types** (no plaintext-capable log sink exists); Prometheus text-format `/metrics` (cardinality budget → ops spec); strict fail-fast env/file config parsing at boot (unknown keys warn, missing prod-critical keys refuse to start); Go stdlib `testing`; Vitest + oxlint + oxfmt on the frontend. None are architectural commitments; any may be swapped without reopening this ADR.
