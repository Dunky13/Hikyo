# Hikyo multi-instance management (ADR, locked 2026-08-06)

Context: Hikyo installations multiply in practice — one on a k3s cluster, one on a VPS, one local — and the humans who run them hop between them. Raised during the app-chrome prototype ([#29](https://github.com/Hikyo-Org/Hikyo/issues/29), reacted to on the iteration-4 instance surface at `prototype/app-chrome/4/`): should one installation be able to see and manage others, Portainer-style? This ADR fixes what "manage" means, the credential and trust model that carries it, its tenant-isolation and audit consequences, the CLI/API surface it joins, and its v1 scope. The spectrum considered ran from a deep-link directory through an authenticated directory and a browser-federated workspace up to server-side API proxying and central state management.

**The decision, in one paragraph:** Hikyo ships **two tiers, both in v1**. The **directory tier** is server-side: an instance stores named **remote** entries (URL + pinned identity + one metadata-scoped credential) and renders a directory of connected instances — reachability, version, org/project names and counts — fetched on view, cached as a last-known snapshot. The **workspace tier** is browser-side: main's UI reads and edits a remote's values by talking to that remote's ordinary `/api/v1` **directly from the browser**, authenticated as the human via a popup ceremony on the remote's own origin. **No Hikyo server ever proxies, stores, or sees another instance's secret values.** Server-side reach stops at directory metadata; value-bearing authority never leaves the user↔remote pair. There is no "main" designation: any instance may hold remotes, gated by its own grants; the model is fully symmetric.

**Two trust models, stated as two.** The directory tier's server-to-server traffic is authenticated by the entry's **SPKI pin, verified on every connection**. The workspace tier's browser-to-remote traffic **cannot** be pinned — browser JavaScript has no access to certificate material, and HPKP is dead — so workspace calls trust the browser's WebPKI plus the remote's ordinary TLS, exactly as the remote's own UI does. The connection pin never authenticates workspace calls, and this ADR nowhere implies it does. Residual, recorded: a CA/DNS compromise the browser accepts can man-in-the-middle a workspace where it could not touch the pinned directory channel; the workspace's exposure equals visiting the remote directly, no worse, and the step-up ceremonies live on the remote origin either way.

*Rejected: server-side API proxy* (main's server relays calls to remotes) — a compromised main becomes plaintext access to every connected instance, the confused-deputy shape the Kubernetes ADR ([k8s-integration.md](./k8s-integration.md)) rejected for an operator-wide credential, at fleet width; it also pulls foreign org data through main's tenant-isolation model and re-attributes remote audit to main's credential instead of the human. *Rejected: central state management* (orgs/projects administered from main and pushed) — everything the proxy costs plus sync/conflict semantics against immutable instance URLs and an additive-only API. *Rejected: deep-link-only ceiling* — the owner's explicit call (recommendation was to stop at the directory or defer the workspace; both leans reversed, recorded): the friction this feature exists to remove includes *working across* installations, not merely finding them, and the CLI already crosses instances per invocation under the API/CLI ADR's context model ([api-cli-surface.md](./api-cli-surface.md)) — the workspace is the UI catching up to authority the CLI already carries, not a new power class.

## Declared amendments

This ADR amends seven locked ADRs. Each follows the locked-ADR amendment procedure ([oss-mechanics.md](./oss-mechanics.md) § Governance) in full: the amended ticket is reopened for the record and re-closed with the amendment noted; the amendment is recorded in the amended ADR file itself at this ADR's commit; and the adversarial cross-model review that locks this ADR covers every amendment text as part of its scope.

- ***Amends the permission ADR ([#15](https://github.com/Hikyo-Org/Hikyo/issues/15), [permission-model.md](./permission-model.md)):*** (a) one new **instance-scope capability atom, `instance-directory`** — "may read the directory of connected instances, and the identity/listing of this instance as served to connected instances". Granted to humans on the viewing side (see the card and its names) and to the **instance-connection principal** on the serving side. Custody of connections (add, remove, credential storage, origin allowlist) is deliberately **not** a new atom: it rides the existing `instance-config`. (b) #15's rule that **no machine principal may hold any instance capability** gains its single named exception: the instance-connection principal class may hold exactly `instance-directory` and nothing else — the exception is per-class and per-atom, enforced by the grant API, and does not soften the rule for service accounts. No other formula moves.
- ***Amends the human-auth ADR ([#16](https://github.com/Hikyo-Org/Hikyo/issues/16), [human-auth.md](./human-auth.md)) twice:*** (a) the "every instance capability is MFA-mandatory" rule is restated as binding **human sessions**; the instance-connection machine principal — which has no assurance record and never reauthenticates, per the machine-identity ADR — is its single named machine exemption, carrying exactly `instance-directory` (the `audit-read` machine-allowlist amendment is the precedent). (b) one new session artifact class, the **workspace session** (§ *The handoff and the workspace session*): a server-side session row on the issuing (remote) instance in every locked mechanical respect — opaque bearer, fast-hash verifier, artifact type, idle/absolute clocks, assurance record, generation binding — differing from the browser session only in transport (presented in an `Authorization` header, never a cookie) and in two added bound fields: the **requesting origin** and the handoff transaction that issued it. Workspace sessions join every locked lifecycle rule: active-session listing, explicit revocation, grant-change and generation invalidation, account disablement, restore invalidation — plus one of their own: **removal of an origin from the allowlist atomically revokes every workspace session bound to that origin**.
- ***Amends the machine-identity ADR ([#17](https://github.com/Hikyo-Org/Hikyo/issues/17), [machine-identities.md](./machine-identities.md)) twice:*** (a) one new machine principal class, the **instance connection**, beside (not inside) the service-account taxonomy — instance-owned, mintable only under `instance-config`; #17's SA rules (project ownership, project-subtree confinement) neither apply to it nor weaken. (b) the token grammar's **closed type list gains one member**: the instance-connection type (working spelling `ic`), so the credential is scannable as what it is. All other #17 token mechanics inherit unchanged (§ *The instance-connection principal*).
- ***Amends the API/CLI ADR ([#25](https://github.com/Hikyo-Org/Hikyo/issues/25), [api-cli-surface.md](./api-cli-surface.md)) three times:*** (a) the closed v1 noun-verb taxonomy gains the **`remote` family** (`remote add|list|show|remove`) and the **`remote-credential` family** (`remote-credential create|list|show|revoke`), joining under #25's existing grammar — context resolution, output rules unchanged, no new output classes; (b) the **closed auth-protocol endpoint exception class** gains the **cross-origin UI handoff** endpoints (§ *The handoff*), the browser edition of the RFC 8252 shape #25 already fixed for the CLI; (c) the **artifact-eligibility matrix** gains the instance-connection credential as a new row, eligible for **exactly one operation: directory-serve** — eligibility is per-artifact-per-operation, so a future operation reusing the `instance-directory` formula does **not** widen what this credential reaches; a CI invariant asserts the credential type is rejected on every other endpoint.
- ***Amends the threat model ([#8](https://github.com/Hikyo-Org/Hikyo/issues/8), [threat-model.md](./threat-model.md)):*** the server's enumerated outbound destinations gain one class: **configured remote Hikyo instances**, under the full user-configured-outbound control set (§ *The outbound client*). The threat model's "only enumerated functional destinations" rule is preserved by enumeration, not weakened.
- ***Amends the audit ADR ([#24](https://github.com/Hikyo-Org/Hikyo/issues/24), [audit-model.md](./audit-model.md)):*** the closed `category.action` registry gains **`remote.*`** (§ *Audit*), including workspace-session lifecycle events and handoff failures; these events carry the **normalized requesting origin** and session artifact id as event fields — the envelope itself is unchanged. Authentication failures and authorization denials stay distinct, per the locked catalogue's existing split.
- ***Amends the ops spec ([#32](https://github.com/Hikyo-Org/Hikyo/issues/32), [ops-spec.md](./ops-spec.md)):*** the composable-maxima catalogue gains the directory outbound client's bounds (per-remote deadline, response cap, remote count, fan-out, coalescing window, per-viewer rate) and the workspace session's lifetime values; the air-gap statement gains the sentence that a directory with zero configured remotes performs zero outbound connections — air-gap behavior is unchanged by construction.

Granularity note: this is the wayfinding-level multi-instance ADR. It fixes the two-tier architecture, the trust and credential model, the capability and principal additions, the federation mechanism's shape and its security posture, the CLI verb families, and the v1 scope. Mechanism-level detail is delegated: exact endpoint paths and flag spellings, the handoff's parameter serialization, CORS header minutiae, and UI states → the synthesis specs ([#27](https://github.com/Hikyo-Org/Hikyo/issues/27)); concrete bound *values* fixed structurally here → the ops spec's composable-maxima catalogue ([ops-spec.md](./ops-spec.md)). Each delegated site MUST satisfy the constraints stated here.

## Vocabulary

- **Remote** — a named connection entry held by an instance: display name, URL, pinned server identity, one directory credential. `remote` is the CLI noun; git's mental model (a named pointer to another repository) is the intended reading.
- **Instance connection** — the machine principal a remote instance mints to represent "some other installation may read my directory listing". The credential of a remote entry authenticates *as* this principal.
- **Instance identity** — a server-generated opaque id minted at `init`, preserved by backup/restore (a restored instance *is* the instance), returned **only in the authenticated directory listing**, never pre-auth. Two live installations sharing an identity (a restored clone left running) are a detectable misconfiguration, not a supported state: a viewing instance that receives its **own** identity from a fetch marks the entry self-connected and refuses it loudly; one that receives the **same identity from two different entries** marks both duplicated and serves neither as current.
- **Directory** — the served listing: instance identity, version, health, org/project names and counts. Also the viewing card that aggregates them.
- **Workspace** — the browser-federated tier: main's UI operating on a remote's data via the remote's own API, as the human.
- **Origin allowlist** — a remote's explicit consent list of exact UI origins whose browsers may perform the handoff and call its API cross-origin.

There is deliberately **no "main"** term: directory-holding is not a designation, a mode, or a flag — an instance that has remotes configured shows a directory; one that hasn't, doesn't. A flag that gates nothing real would be a second permission language, the shape the permission ADR forbids. Two instances may connect to each other; the relationship is per-direction and symmetric. **Self-connection is refused by instance identity** at the first authenticated fetch `remote add` performs, and re-checked on every subsequent fetch — the pre-auth meta endpoint stays exactly its locked closed allowlist (version, API revision, protocol capabilities; [api-cli-surface.md](./api-cli-surface.md)) and carries no identity, so a URL that later comes to resolve to the instance itself fails loud at fetch time rather than rendering the instance as its own remote.

## The directory tier

### The connection entry

`remote add <name> <url>` is interactive-only (TTY required, per #25's ceremony rules) and performs, in order: TLS connection; **SPKI fingerprint display and human confirmation** — the API/CLI ADR's client-side trust establishment, transplanted to a server-held entry; the pre-auth meta endpoint read (#25's closed allowlist) to confirm the target speaks Hikyo's protocol at a compatible revision; then the **directory credential paste** (the token minted on the remote by `remote-credential create`), verified by one authenticated directory fetch — which returns the remote's instance identity, at which point self-connection and duplicate-identity refusal fire — before the entry is committed.

**URL and pin are immutable per entry.** Re-pointing a stored credential at a different host is the credential-redirect attack the API/CLI ADR closed for CI contexts — whoever can edit the URL of an entry holding a valid credential redirects that credential to an attacker's validly-certificated server. There is no `remote edit`; re-pointing = `remote remove` + `remote add`, which re-runs the full ceremony including the human fingerprint confirmation. The display name is the one mutable field.

**The credential is write-only after storage.** It is encrypted under the instance keyring at rest, is never re-displayable through any surface, and leaves the process only inside TLS to the pinned remote. `remote remove` destroys it with the entry (and the snapshot, § below) — and prints, every time, that the serving side's credential remains valid until revoked *there*: destroying the local copy is not revocation, and the CLI does not pretend otherwise. Rotation = `remote-credential create` on the serving side, `remote remove` + `remote add` on the viewing side, `remote-credential revoke` of the old one — in that order, so the directory never goes dark.

Custody — creating, removing, and thereby holding these credentials — is gated by **`instance-config`**: connection entries are instance configuration, and holding a foreign credential is custody in exactly the sense the audit ADR's operator arguments use. Viewing the directory is gated by **`instance-directory`**, its own grantable atom, following the audit ADR's precedent that *reading is power and is never bundled*: on a solo-admin install the two collapse into the same person; on a multi-user install the admin grants the hop to exactly the humans who work across instances. The org/project **names** in the listing are the reason this gate exists: they are foreign structure, visible to whoever can see the card, and the remote cannot scope them per-viewer without the proxy machinery this ADR rejects — so the viewing instance gates its audience instead.

### The instance-connection principal and its credential

The serving side mints an **instance connection**: a machine principal that is instance-owned, created and deleted only under `instance-config`, and whose grant surface is structurally exactly `{instance-directory}` — the grant API refuses any other capability on this principal class (#15 amendment above). Capability confinement alone would not confine the *credential*: a future operation whose formula accepts `instance-directory` would widen every existing token without any grant changing. So the confinement is **double**: the grant API caps the principal, and #25's artifact-eligibility matrix caps the credential to the directory-serve operation alone (declared above), with a CI invariant rejecting the token type on every other endpoint. The principal exists so the audit trail has a real actor (the audit ADR's actor/authority split) — *rejected: a bare capability token with no principal row*, which would leave the serving instance auditing an authority with no actor.

Its credential is an `hikyo-token` mechanically, under its own new type in the closed grammar (#17 amendment above — scannability is a security property, and this credential should scan as what it is): `ew_` prefix, ≥256-bit body, unsalted SHA-256 verifier, server trusts nothing inside the token, display-once at mint under the output triad (TTY / `O_EXCL` `0600` file / explicit flag), no `--token` flag anywhere, finite-or-`indefinite` lifetime under the instance ceiling with `allow_indefinite` default off, never re-activated on restore (re-mint and re-add afresh). **Lifecycle**: `remote-credential create` mints principal + credential as one unit with a stable immutable id; one credential per principal, ever — `revoke` kills the credential and retires the principal with it (rotation is a new create, above), so no orphan principals accumulate and no revoked principal is re-armed. `remote-credential list`/`show` expose metadata — id, label, created, expiry, last-used — and **never the value**, inheriting #17's list/get rule unchanged. `create` names the intended peer in a free-text label for the audit trail; the label is descriptive, not enforced — the serving instance cannot verify who holds the token, and does not pretend to.

What the credential authorizes, exhaustively: the **directory-serve operation** — instance identity, version, health signal, and the names and counts of orgs and projects — and nothing else. No values, no keys, no environments, no membership, no settings, no audit. The listing is an **instance-scope read crossing org boundaries by design**; it is registered as its own operation in the tenant-isolation registry, probe-classified instance-scope, and served under an `InstanceProof` evaluated on the connection principal's `instance-directory` grant ([tenant-isolation.md](./tenant-isolation.md)). The owner chose names over counts-only knowingly (recommendation was counts-only; lean reversed, recorded): names make the directory's deep links real, and the leak they represent is bounded by the viewing side's `instance-directory` gate rather than denied.

### The outbound client

The directory fetch is a **new outbound surface on the server**, and it is treated as the threat model treats user-configured outbound targets — the #8 amendment above enumerates it; this section is its control set, all normative:

- **URL grammar**: canonical `https://` origin only — no userinfo, no path, no query, no fragment, no plaintext HTTP. The fetch path is appended by the client from the API contract, never from configuration.
- **Pin before bytes**: the SPKI pin is verified on **every** connection before any request is written; a pin mismatch is a hard, loud entry error, never a retry-through.
- **No redirects, ever** — a redirect response is a fetch failure by name.
- **DNS-rebinding hardening**: the connection dials a resolved IP and validates the pin against that exact connection; the pin check inherently defeats rebinding to a foreign server (the rebound host cannot present the pinned key), which is the control — private-range targets are **explicitly permitted**, because remotes on LAN addresses are the homelab's normal case, and the pin plus the closed Hikyo protocol bound what a fetch can reach into.
- **Response bounds**: per-remote deadline, response size cap, parse-before-trust with the same sanitized-error discipline every foreign byte gets ([import-paths.md](./import-paths.md) fixed the pattern); listing fields are length-capped on ingest.
- **Fan-out bounds**: remote count cap, parallel fan-out cap, a coalescing window (concurrent viewers share one fetch), a per-viewer trigger rate **and an instance-wide aggregate trigger rate** — per-viewer limiting alone does not bound many principals, so the aggregate cap is the one that actually protects the fleet; a human (or many) refreshing the card is not a DoS amplifier. Concrete values → ops spec catalogue (#32 amendment).
- **Proxy handling, explicit**: egress through a forward proxy is supported only via explicit instance configuration (never ambient environment discovery), is tunneled (`CONNECT`) so TLS and the SPKI pin verify **end-to-end against the remote**, and plaintext-to-proxy is refused — a proxy is a network hop, never a trust party.

An instance with zero configured remotes performs zero outbound directory connections — the air-gap posture is unchanged by construction.

### Freshness: on-view fetch plus last-known snapshot

The directory fetches **when a holder of `instance-directory` views it** — card open in the UI, `remote list`/`remote show` in the CLI — server-to-server, in parallel under the bounds above. A successful fetch updates the entry's **last-known snapshot**: the listing plus a server-side timestamp. An unreachable remote serves its snapshot **marked stale with its age** — the card's "unreachable 2h — last known state shown" — never silently as current. A `401/403` from a revoked or expired credential is its own loud state ("credential rejected"), distinct from unreachable, because the operator's fix differs.

**There is no background poller.** The architecture ADR ([system-architecture.md](./system-architecture.md)) fixed *no generic job framework* with the adapter outbox as the single deliberate exception; a directory poller would re-open that for a health dot nobody is looking at, and would put a standing authenticated heartbeat toward every remote on the wire for the same nothing. On-view fetch covers the only moment health matters — a human looking — and bounds the credential's use to human-initiated moments. *Rejected: live-only with no snapshot* — it discards the genuinely useful "was fine 2h ago" signal and saves nothing.

The snapshot is **foreign structure at rest on the viewing instance**: instance-scope rows (identity, names and counts, no values — there is nothing value-bearing for it to hold), readable only through proofs evaluated on `instance-directory`, deleted with the entry. It is not encrypted beyond the database's own posture: its contents are exactly what the credential may read anyway, and pretending it is secret material would misstate the boundary.

## The workspace tier

The workspace lets a human read and edit a remote's actual data — matrices, values, publishes, reveals — inside the viewing instance's UI. Its one structural rule, from which everything else follows: **the browser talks to the remote directly; no server in the middle.** The viewing instance's server contributes the shell, the directory, and the deep links, and never touches the session, the calls, or the values.

### Consent: the origin allowlist

A remote participates only by explicit configuration: an **origin allowlist** under its `instance-config` — exact origins (`https://hikyo.went.io`), no wildcards, no subdomain matching. What the allowlist actually gates, stated precisely: **handoff issuance** (the `redirect_uri` authority and transaction origin binding) and **browser readability** (CORS echoes only a matching origin, without credentials mode — cookies never cross origins here). It is *not* bearer authorization: CORS controls what a browser can read, not what a token can do — anyone who exfiltrates a workspace bearer can replay it from a non-browser client until it expires or is revoked, exactly as the human-auth ADR states for bearer artifacts generally. The server-side controls carry the rest: workspace-session rows are **bound to their requesting origin**, browser requests must present that origin, and **removing an origin from the allowlist atomically revokes every session bound to it** (#16 amendment above) — so de-allowlisting is a real kill switch, not a headers change.

The allowlist names *UI origins*, not instances, deliberately: what the remote is trusting is precisely *the code served at that origin* — that is the true trust statement, and it is what the admin must be able to point at when auditing why cross-origin access exists.

### The handoff and the workspace session

Authentication to a remote happens **on the remote's own origin**, always — a deliberate design rule, not a claim of platform impossibility: WebAuthn's spec admits permitted-iframe arrangements, but Hikyo's locked `frame-ancestors 'none'` and immutable RP ID (#16/#22) reject that architecture, so the ceremony is top-level on the remote origin, full stop.

From the viewing UI, "open workspace" opens the remote's authorization page in a popup **with `noopener`** — a hostile or compromised remote must not be able to navigate the opener into a phishing page — so the return path is not `window.opener`: the popup's final redirect lands on a **same-origin callback page of the viewing UI**, which hands the result to the shell over a **nonce-named `BroadcastChannel`** and closes. The human authenticates in that popup with the remote's own ceremonies (password+TOTP, passkey, OIDC — per that instance's human-auth configuration). On approval the remote redirects **code + state** to the exact pre-registered callback (the allowlist entry is the `redirect_uri` authority), and the shell redeems the code **cross-origin with PKCE (S256)** at the remote's token endpoint — #25's RFC 8252 loopback shape, browser edition, same rule: *the front channel carries code+state only, never the artifact*.

The handoff is carried by a **short-lived server-side transaction on the remote**, the human-auth ADR's own transaction pattern: it binds state, the exact callback URI, the requesting origin, the PKCE challenge, the purpose (initial establishment vs step-up), and the target human once authenticated. An **establishment** transaction additionally records that no prior session exists (purpose alone licenses issuance); a **step-up** transaction binds the **initiating workspace session id**, the **exact operation being elevated**, and — where the operation is key-scoped, per the locked ceremony content the remote's own UI uses — the **environment and enumerated key set**, so an elevated consent cannot be replayed against a different operation, environment, or key set. Every transaction is **single-use and atomically consumed**, and expires in minutes. Every handoff path (start, callback, redemption) is classified pre-authentication and sits under the remote's pre-auth admission limits.

Redemption yields a **workspace session**: an opaque bearer whose server-side row on the remote carries everything the locked session model requires — fast-hash verifier, artifact type, principal, assurance record, generation, idle and absolute clocks — plus its two bound extras: requesting origin and issuing transaction (#16 amendment above). It differs from a browser session **only in transport**: presented in an `Authorization` header, never a cookie — which is why CORS runs without credentials mode and the remote's CSRF posture is untouched; there is nothing ambient to forge. Client-side the bearer lives **in JS memory only** — never a cookie, never localStorage or sessionStorage, gone on tab close. Workspace sessions appear in the remote's active-session listing as their own artifact type and die with every locked invalidation trigger: explicit revocation, grant change, generation bump, account disablement, restore — and origin removal, above. Reauth and step-up re-open the popup on the remote's origin and run the remote's own locked ceremonies — the workspace session never substitutes for them. Expiry surfaces in the shell as "session expired — reconnect": one click, popup, back.

*Rejected: persistent workspace sessions* (refresh token in storage) — XSS on the viewing origin must never yield a durable credential for the fleet; re-establishing per browser session costs one passkey tap. *Rejected: cookie-borne cross-origin sessions* (`SameSite=None`) — re-opens CSRF and third-party-cookie fragility for zero gain over the header bearer. *Rejected: stateless short-lived bearers* — a token the server cannot revoke row-by-row is the JWT revocation window the human-auth ADR already rejected, whatever its lifetime.

### What the workspace is, and is not

Inside a workspace the viewing UI renders the remote's data with its own components against the remote's ordinary `/api/v1` — the same endpoints, formulas, ceremonies, and audit the remote's own UI uses. Authorization is entirely the remote's: the human's grants *on that remote* decide everything; the viewing instance's grants (including `instance-directory`) confer nothing over there. Remote audit records the human as actor — correct attribution falls out of the architecture instead of needing repair. Admission, rate limits, and the aggregation licence are the remote's own; a workspace browser is just another client.

**Live updates**: the locked update channel is native `EventSource` authenticated by the browser session artifact — and native `EventSource` cannot set an `Authorization` header, so the SSE path is structurally unavailable to workspace clients. The workspace uses the **polling fallback the architecture ADR already ships** — ordinary authenticated GETs, which carry the header fine — at the architecture's sanctioned polling cadence. Stated honestly as a degradation: workspace views refresh at poll cadence, not push latency; no amendment to the architecture ADR is needed because polling is already a first-class mode there, and no implementer is licensed to weaken SSE authentication to close the gap.

**Version skew**: before establishing or resuming a workspace, the shell performs a **live** pre-auth meta read against the remote (the meta endpoint's exact closed response is CORS-readable for allowlisted origins — it is already the pre-auth public surface, and its allowlist of fields doesn't move) and applies #25's per-operation minimum-revision registry from that live value. The directory's cached version is **display-only** and never feeds a compatibility decision — a snapshot can race a downgrade or restore. The shell refuses, **by name**, workspace operation against a remote older than its floor — degraded rendering of a secrets matrix is not a graceful state.

The workspace adds **no viewing-server state and no cross-instance account mapping** — the precise claim, narrowed from "no server-side state": the remote holds workspace-session rows (it must, per the locked session model) and its origin allowlist; the viewing server holds nothing new. The human's accounts on the two instances are simply both theirs; nothing in either database relates them. (A shared OIDC IdP makes the popup near-instant; nothing requires it.)

**CSP note (#22):** the viewing instance's locked CSP baseline extends `connect-src` with exactly the origins of its configured remotes — served dynamically from the connection entries, still a closed list, never `*`. The popup is a top-level navigation to the remote origin and needs no frame allowance; the workspace never iframes a remote, and `frame-ancestors 'none'` stands everywhere.

### The residual, stated plainly

The workspace's irreducible residual: **the viewing origin's served frontend becomes attack surface for every remote its users link, and the workspace bearer is extractable.** An XSS or supply-chain compromise of the viewing SPA can read and exfiltrate the in-memory bearer (and PKCE verifiers, codes, and any remote values on screen), and an exfiltrated bearer **replays from outside the browser** — CORS and CSP do not bind a stolen token — until its expiry or revocation, surviving tab close. While the page lives, the attacker can additionally initiate or intercept fresh handoffs. In-memory storage narrows the *at-rest* window (nothing durable to steal from storage); it is not non-stealability and this ADR does not sell it as such. The bounds that remain real: hard-short workspace lifetimes (values → ops spec), workspace sessions visible as their own artifact type in the remote's active-session list for immediate revocation, origin-removal as an atomic kill switch, step-up ceremonies still gating the remote's most sensitive operations on the remote's origin, and blast scoped to the compromised human's grants per remote — never a fleet credential; the rejected proxy design would have made it one. Accepted, recorded, not blocking.

## Parity and the CLI

Both tiers respect the API/CLI ADR's structural parity rule — every UI feature exists as public surface:

- **Directory**: `remote add <name> <url>` (interactive ceremony), `remote list` (the card: per-entry state — reachable / stale+age / credential-rejected / self-connected / duplicated — and the listing), `remote show <name>` (one entry, full detail), `remote remove <name>` (typed-name confirm; destroys credential + snapshot; prints the serving-side-revocation reminder). All under `/api/v1` domain endpoints on the viewing instance, `instance-config`- or `instance-directory`-gated per the split above.
- **Serving side**: `remote-credential create|list|show|revoke` (§ lifecycle above; display-once mint under the output triad, metadata-only list/show). The origin allowlist rides existing `instance-config` surfaces.
- **Workspace**: needs **no new CLI** — #25's context model already gives the CLI per-invocation cross-instance operation with a stronger trust story (local SPKI pins, per-invocation contexts, no persistent active context). The workspace tier *is* parity: the UI catching up to the CLI. The handoff endpoints join #25's auth-protocol exception class (declared above), exactly where login transports live.

`remote add`'s paste step and fingerprint confirmation are interactive-only; there is deliberately no non-interactive `remote add` in v1 — scripting fleet directory setup is a named post-v1 candidate (→ [#26](https://github.com/Hikyo-Org/Hikyo/issues/26)), gated on a design that preserves the pin-confirmation and no-argv-secret rules in automation.

## Audit

New category `remote.*`, both sides, in the locked envelope (origin and artifact ids are event fields; the envelope does not change):

- **Viewing side** (instance trail): `remote.added` (name, URL, pin digest), `remote.removed`, `remote.renamed`, `remote.fetch_failed` (unreachable / credential-rejected / pin-mismatch / redirect-refused / identity-conflict, per the outcome enum), `remote.directory_viewed` — the snapshot/listing read, audited because it is foreign structure and `instance-directory` is a read-is-power grant (the audit ADR's own argument applied to this ADR's own data). Successful fetches ride `remote.directory_viewed` (the fetch happens because of the view); they are not separately per-remote evented.
- **Serving side** (instance trail): `remote.credential_minted`, `remote.credential_revoked`, `remote.origin_allowlist_changed`, `remote.directory_served` — one event per authenticated listing serve, actor = the instance-connection principal, in the **`access` retention class** (it is the machine-fetch stream shape) — and, distinctly: `remote.auth_failed` for **authentication** failures of the directory credential (expired, revoked, malformed, unknown — no authenticated actor exists; the locked catalogue's machine-authn-failure handling applies), separate from an authenticated **authorization denial**, which lands as a per-event durable denial like any other. Workspace lifecycle gets its own events: `remote.workspace_session_issued` / `revoked` / `expired` and `remote.handoff_failed`, each carrying the normalized requesting origin and the **handoff transaction id**, plus the session artifact id where one exists — a failed handoff predates any session, so its session field is explicitly nullable and the transaction id is the correlating key. Ordinary workspace API traffic needs nothing new beyond that: it is human API traffic, already fully audited under existing categories with the human as actor — and those events identify the session artifact, so workspace-borne actions are distinguishable from same-origin ones.

## v1 scope and acceptance

Both tiers are v1, by the owner's explicit call against the recorded recommendation to defer (twice: pre-workspace and post-workspace; both leans reversed). For the MVP boundary ([#26](https://github.com/Hikyo-Org/Hikyo/issues/26)), the acceptance criteria this ADR feeds:

1. Two instances; B mints a `remote-credential`; A's admin runs `remote add` with fingerprint confirm; A's directory shows B's identity, version, org/project names and counts. Stop B: A shows last-known + age. Revoke on B: A shows credential-rejected, loud. Point an entry at A's own URL: refused as self-connected at the authenticated fetch.
2. A human with `instance-directory` on A but no account on B sees B's listing on A and **nothing else** — the workspace popup lands on B's login and goes nowhere without B-side credentials.
3. B allowlists A's origin; a human with accounts on both opens B's project in A's shell, reveals under B's ceremony (popup on B's origin), edits, publishes; B's audit shows the human as actor throughout, on a workspace session artifact. Remove the allowlist entry: every workspace session bound to A's origin dies atomically, and new handoffs refuse at the transaction.
4. A grant attempt of any capability other than `instance-directory` on an instance-connection principal refuses structurally; the instance-connection credential presented to any endpoint other than directory-serve refuses by artifact eligibility (CI-asserted).
5. B's active-session list shows the workspace session as its own artifact type; revoking it there kills the workspace mid-flight.
6. No endpoint on either instance returns another instance's secret values to a server. (Vacuously testable: the surface does not exist.)

Everything here is additive under #25's freeze rules (new endpoints, one exception-class member set, new atoms, new verb families) — nothing constrains later widening (per-viewer listing scoping, non-interactive `remote add`, workspace presence indicators are all named non-preclusions, undesigned).
