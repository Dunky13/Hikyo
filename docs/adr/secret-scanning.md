# Envweave secret scanning (ADR, locked 2026-08-06)

Context: the MVP boundary ([mvp-boundary.md](./mvp-boundary.md) §2.4, [#26](https://github.com/Dunky13/envweave/issues/26)) promotes secret scanning into 1.0 as a new subsystem and fixes its minimum bar: at least scan-on-value-entry, backed by a normative ruleset with a true-positive/false-positive fixture corpus in CI. Three constraints arrive fixed and are honored structurally here, not re-argued: the `ew_` credential grammar's scannability-by-third-parties ([machine-identities.md](./machine-identities.md)) must not weaken — this ADR touches no token format; scanning must not create a new plaintext disclosure path — it runs only where plaintext already legitimately exists under the locked formulas, never as a background decrypt-and-scan job with new authority (§6 carries the full disclosure analysis); the performance envelope fits the calibration floor ([ops-spec.md](./ops-spec.md) §1). The product ground this ADR stands on is the source-of-truth ADR's honest residual ([source-of-truth.md](./source-of-truth.md)): a definitions bundle "is documentation-class material and must be treated as public from the moment it is exported," the exposure of a token typed into a description is "the same exposure as a token pasted into a source comment, and it is managed the same way" — and the false-safety rejection there ends with the observation that a false claim "is the one that stops people scanning." This ADR is the scanning that sentence anticipates, moved to the earliest point the system can act: the write.

Granularity note: wayfinding-level. The vendored ruleset snapshot commit and the full allowlisted rule-ID list are pinned at implementation against §3's stated criteria and **at or above §3's minimum coverage manifest** — the criteria and the manifest are normative, the full ID list is not enumerated here. Finding-presentation microcopy and dialog layout ride the locked editing surfaces ([#21](https://github.com/Dunky13/envweave/issues/21), [#29](https://github.com/Dunky13/envweave/issues/29)) and are carried by synthesis ([#27](https://github.com/Dunky13/envweave/issues/27)). Concrete bound values join the operations spec's bound registry as a declared post-lock addition (§7).

## 1. Shape: scan-on-value-entry, and only that, in 1.0

**Decision: 1.0 ships exactly the promotion floor — scan-on-value-entry at the server's write paths. The two candidate additional shapes are deferred with named triggers.**

- **Leaked-`ew_`-token intake** (an endpoint or CLI path where a scanner or human reports a found `ew_` token for verification and revocation) is deferred on a structural ground, not a scheduling one: the `ew_` grammar (`ew_<version>_<type>_<body><checksum>`, [machine-identities.md](./machine-identities.md)) deliberately carries **no issuer or instance binding**. A third-party scanner that finds an `ew_` token in a public repository cannot determine which self-hosted instance to report it to; a GitHub-partner-program-style universal intake is undeliverable for self-hosted software, and a per-instance "paste the token you found" verb adds little over the existing credential surface — a human who knows their instance and finds their own leaked token already holds the revocation path ([#17](https://github.com/Dunky13/envweave/issues/17)); the checksum already lets any offline scanner reject truncated matches with zero server calls. **Trigger to revisit: demand, together with an issuer-binding story for the `ew_` grammar** — which would itself be a declared machine-identities amendment, weighed against the grammar's locked one-family-one-scanner-rule property.
- **Push-protection-style API** (third parties submit candidate content, the instance answers whether it contains live Envweave credentials or ruleset matches) is deferred as speculative surface: no consumer exists at v1, and the endpoint is a **liveness oracle** — it confirms to the caller that a token is real and current — so it cannot ship as a casually-added convenience; it needs its own authorization design. **Trigger to revisit: a concrete third-party consumer** (a forge, a CI system, a scanner project) asking for the integration, named in the request.

Both deferrals are post-v1 register rows in the terms of [mvp-boundary.md](./mvp-boundary.md) §4: explicit disposition, explicit trigger, return by trigger and never by silent scope creep.

*Rejected: shipping the intake verb anyway as a cheap self-serve win.* It passes the self-hoster test, but it duplicates the revocation surface behind a second door, and its one marginal capability — look up a credential by its token text — is a reverse index from secret material to identity that nothing else in the system needs to exist.

## 2. Scan surface: where a credential-shaped string is wrong

The promotion's phrase "pasted foreign credentials detected at save" hides the product question this section answers. Pasting an AWS key into a **secret-classified** value is the product working as intended — there is nothing to detect. The scan earns its keep exactly where a credential-shaped string lands somewhere it should not:

**Surface 1 — non-secret (`config`) classified values.** A credential stored under `config` classification escapes the reveal ceremony, masking, write-presence-only diffing, and every secret-handling rule the classification exists to trigger ([permission-model.md](./permission-model.md), [#21](https://github.com/Dunky13/envweave/issues/21)). This is the misclassification catch, and it is the core case: the scanner's primary verdict is not "this is a secret" but "this is classified as not-a-secret and looks like one." Surface 1 has **two ingress routes, both scanned**: a config-classified value **write** (any client — UI, CLI, API, server-side `values import`), and **declassification** — the `secret → config` reclassification ceremony ([schema-model.md](./schema-model.md)) re-materializes existing occurrences as config under its reveal-gated ceremony, which is plaintext legitimately in process under a locked formula; the scan runs there too, so a foreign credential correctly stored as secret cannot become config without meeting the scanner. This adds no decryption authority — the ceremony already holds the plaintext.

**Surface 2 — every author-controlled string leaf in the canonical definitions model.** Defined **structurally, not by enumeration**: any string in the definitions model whose content an author supplies is Surface 2 — key names, descriptions, deprecation notes, `pattern` (which "can encode an exact literal as easily as a shape"), JSON Schema documents on `json` keys, `enum` members, `any_of` alternatives, **folder path segments, environment names, key-group names**, and any author-supplied string field added later. A **closed exclusion list** names what is not scanned: fixed schema keywords and server-generated immutable identifiers — content no author composes. The structural definition is CI-enforced: a **generated field-coverage matrix** walks the canonical definitions model, and an author-controlled string field without a scan-coverage fixture fails CI — adding a public field silently unscanned is structurally impossible (SS3). All of Surface 2 is exported in the definitions bundle and is **public from the moment of export** ([source-of-truth.md](./source-of-truth.md)), regardless of any key's classification (a `pattern` on a secret key is still bundle text).

**Surface 3 — secret-classified values: unscanned, as a decision.** The only conceivable signal on a secret value is a live own-instance `ew_` token stored as a value — and storing an automation token for CI to fetch is a plausible legitimate pattern, so even that is warn-at-most, and checking token liveness at save adds a lookup per write for a marginal verdict. Everything else a ruleset could match on a secret value is the value doing its job. *Rejected with reasoning recorded: a scanner that warns on correct usage trains its users to dismiss it; the erosion of the signal costs more than the surface could ever catch.*

Scanned content is exclusively content the system already treats as non-secret (by the author's classification, reaffirmed or corrected at the scan), as public (by the source-of-truth doctrine), or plaintext already legitimately in process under a locked ceremony (declassification). This is load-bearing for §6.

## 3. Ruleset: vendored, pinned, allowlisted, fixtured

**Decision: the ruleset is a pinned vendored snapshot of the gitleaks rule set (MIT, license-compatible with MPL 2.0), filtered through a fail-closed allowlist of rule IDs committed in this repository, plus one Envweave-owned rule for the `ew_` family.**

- **Provenance, pinned executably.** The vendoring record names: upstream repository (`github.com/gitleaks/gitleaks`), the pinned upstream commit, the source path of the rule definitions within it, the license file's hash, and the retained MIT notice; the snapshot enters the **SBOM** the release manifest already signs ([oss-mechanics.md](./oss-mechanics.md)). No network fetch at build or runtime — the snapshot is repository content. Updates happen only by a deliberate PR that bumps the pin, on which the full fixture corpus is the gate.
- **The import contract is defined, fail-closed.** Gitleaks rules are TOML with semantics beyond a regex — keywords, entropy conditions, capture-group selection, per-rule allowlists, path filters. Envweave's build-time generator consumes **exactly: rule ID, regex, keywords** (keywords as a prefilter optimization only — never verdict-changing). A rule using any other field, or whose regex does not compile under RE2, is **rejected at generation — it cannot be allowlisted**; unsupported semantics are never silently discarded. The generator emits a **compiled-rule manifest**, and CI asserts manifest ≡ allowlist — every allowlisted rule compiled, nothing else.
- **The allowlist is fail-closed and criteria-bound.** A rule ships only if its ID is on the committed allowlist; a new upstream rule arriving in a pin bump is not compiled in until explicitly allowlisted with fixtures. Inclusion criteria, normative: a rule must be **anchored on issuer-identifiable structure** (a vendor prefix like `AKIA`/`ghp_`/`xox`/`sk_live`, a framed format like a PEM header, a structurally distinctive grammar); **bare-entropy rules are excluded** (`generic-api-key`-class detectors alarm on exactly the random-looking identifiers that legitimately live in config values — our primary surface). A rule that cannot be given a false-positive fixture demonstrating what it correctly ignores does not meet the bar.
- **Minimum coverage manifest, normative — the floor an allowlist cannot shrink below.** So the promotion cannot be satisfied vacuously (an empty allowlist plus the `ew_` rule would pass a per-rule corpus check while detecting nothing foreign — exactly the no-op mvp-boundary §2.4 forbids), the following credential families MUST each be represented by ≥1 allowlisted, fixtured rule: **AWS access key IDs (`AKIA`/`ASIA`), GitHub tokens (`ghp_`/`gho_`/`ghs_`/`ghu_`/`github_pat_`), GitLab PATs (`glpat-`), Slack tokens (`xox…`), Stripe live keys (`sk_live`/`rk_live`), private-key PEM blocks (`-----BEGIN … PRIVATE KEY-----`), and the `ew_` family.** SS1 asserts every family is represented. The implementation snapshot may expand this manifest; shrinking it is an amendment to this ADR.
- **Every allowlisted rule carries fixtures**: at least one true-positive (a planted, syntactically valid, non-live credential of that rule's class) and at least one false-positive (a near-miss the rule must not match). The corpus runs in CI on every change.
- **The `ew_` rule is two-stage by construction**: RE2 candidate extraction over the grammar, then **procedural CRC validation** of the checksum ([machine-identities.md](./machine-identities.md)) — a checksum is not expressible in RE2 and is not pretended to be. A checksum-invalid candidate is a non-match; the fixtures include truncated and checksum-corrupted non-matches. Our scanner consumes the grammar's exported scannability exactly as third-party scanners do.
- **Engine: RE2 semantics only** (Go `regexp`) — the same engine class the schema model already mandates for `pattern` ([schema-model.md](./schema-model.md)). What RE2 buys is stated precisely: **no exponential backtracking class** — it does not bound aggregate `rules × bytes` work, which §7's explicit budgets do.

*Rejected: own patterns only* — full control, but it silently falls behind vendor-format churn and re-derives gitleaks' curation as a private fork. *Rejected: vendored full set, unfiltered* — the entropy rules alarm on the config surface daily, and 180 unread fixture sets is corpus theatre. The allowlist makes curation a stated rule rather than taste.

## 4. Findings: warn on values, block on public text, override = the write authority

**The finding is a redacted DTO, normatively closed.** A finding, everywhere it travels — wire response, CLI output in every format, UI, audit, import output — carries exactly: **rule ID, surface, immutable locator** (key identity for Surface 1; declaration-field locator for Surface 2, schema-location-class per [schema-model.md](./schema-model.md)'s discipline — never instance-derived), **and an opaque acknowledgement token** (below) where an acknowledgement is possible. **Banned from every representation: the matched text, match offsets, match length, excerpts, and any instance-derived path.** A scanner-internal error (a rule failing at match time) is reported as the rule ID and a structural error class, never library output that could embed content. This is the same trap the schema ADR closed for validation-error paths, closed the same way (SS4 sweeps for it).

The two surfaces have different failure costs, so they get different verdicts:

**Surface 1 (config values): non-blocking warn.** The save **succeeds**; findings ride the response. Two named resolutions, both first-class in the UI and the API shape:

- **Reclassify as secret** — the primary action, one click in the UI, completing under normal edit authority via the existing reclassification ceremony ([#12](https://github.com/Dunky13/envweave/issues/12)'s rules apply; the scanner adds a door to that ceremony, not a bypass).
- **Keep as config** — an explicit dismissal, sticky so the same accepted value does not re-warn on every save while any distinct offending value re-fires. **Dismissal identity, fully specified:** a dismissal row is keyed by **(org, project, environment, key identity, rule semantic digest, value fingerprint)** where the **rule semantic digest** is a digest of the compiled rule definition (regex + consumed fields) — an upstream pin bump that changes a rule's detector invalidates that rule's dismissals by construction (they re-fire; rule-ID reuse cannot silently carry old dismissals forward) — and the **value fingerprint** covers the canonical stored bytes (post-trim, exactly what the value write persists). Lifecycle: reclassification to secret drops the key's dismissals (moot); key deletion deletes them; fingerprint-key rotation (§ below) invalidates them — every invalidation direction is re-fire, the safe direction; dismissal rows travel in backup/restore with the database like other tenant rows.

A true positive here is bad but bounded — the credential is inside the instance, fixable by reclassification; a false positive is a nag on someone's legitimately random-looking ID. Warn matches that cost profile.

**Surface 2 (public free-text): blocking, at every declaration ingress (§7).** A declaration write carrying a finding **fails**, naming each finding by locator + rule ID. A true positive here is plaintext exported to Git as public — practically irreversible once pulled; a false positive is a description *quoting* a token format. The override exists but is deliberate and **content-bound**:

- The refusal carries, per finding, an **opaque acknowledgement token** minted by the server, bound to: the immutable locator, the rule semantic digest, a canonical digest of the offending field's content, and the ruleset snapshot version. The token embeds no plaintext (it is a server-side reference or a sealed binding — opaque either way) and is short-lived.
- The resubmission presents one token per finding. The server **re-scans the current content**: a token whose bound content digest no longer matches (the field changed since the dialog), whose rule or ruleset version changed, or that arrives surplus (no corresponding current finding) is **rejected by name**. A standing acknowledgement list that pre-authorizes future credentials matching the same rule on the same field is therefore structurally impossible — that would be a reusable per-field bypass, and it is the exact shape the binding exists to kill.
- The UI presents this as an explicit dialog stating the consequence in the source-of-truth ADR's own words — this field is exported to Git and treated as public. **No blanket ignore-all-findings input exists on any surface.**

**Override authority is the write authority — no new capability atom.** Whoever may perform the edit may dismiss its warning or acknowledge its block. The scanner is a guardrail on a write the principal already owns, not a new permission domain; minting a `dismiss-findings` atom would amend the locked capability set ([permission-model.md](./permission-model.md), [#15](https://github.com/Dunky13/envweave/issues/15)) to introduce a second decision-maker for a single write, and a reviewer-approval shape is exactly the approval-workflow machinery the MVP boundary keeps post-v1 (mvp-boundary §4.2). If key-scoped restriction ("only the DBA may accept findings on `DB_PASSWORD`") is ever wanted, it arrives with the key-scoped permission extension already registered there — same trigger, same row.

**The fingerprint is a keyed digest under a dedicated key, computed inside the crypto chokepoint — a declared encryption-model amendment.** Dismissal rows must recognize a re-saved value without storing it, and a bare content hash in a stolen database is an **offline-verifiable oracle** for guessable values — contradicting the headline guarantee (gate row K3, [threat-model.md](./threat-model.md)). The encryption ADR ([encryption-model.md](./encryption-model.md)) forbids exactly the shortcut the naive design takes: key material is never overloaded onto a key that already has a job, and `crypto/hmac` outside the envelope package is an architecture-test failure. So, **declared amendment, banner in the encryption ADR**: the hierarchy gains one **tier-3 scanning-fingerprint key** (root→master→scanning-fingerprint, sibling of the project DEKs and token key), used for nothing else; the envelope package exports one function — fingerprint over **domain-separation label ‖ scope binding (org, project, environment, key) ‖ canonical value bytes** — and scanning code never touches a hash or HMAC primitive itself. The key wraps under the existing `wrapped_dek` envelope kind as an instance-scoped tier-3 key (no new AAD schema), joins `rotate-master-key`'s re-wrap set, and gets its own rotation operation — **`rotate-scanning-key`**, the rotation inventory's sixth member: outright replacement, no version keyring, no `reencrypt` walk (fingerprints are keyed digests, not ciphertexts to preserve — old fingerprints must die, that is the operation's purpose), dropping every dismissal row (re-fire — safe), operator-initiated like the other five. Restore carries the key inside the hierarchy as usual; project deletion removes the project's dismissal rows. The fingerprint appears **only in dismissal rows — never in audit payloads** (§5).

*Considered and accepted: a residual probe.* A principal holding write on a key can submit candidate values and observe whether the warn fires fresh or arrives pre-dismissed, learning that some colleague previously dismissed exactly that `(rule, value)`. The prober must already possess the value text, the scopes are tenant-bounded, and the learned bit is "someone accepted this before" — negligible against the cost of making dismissals non-sticky. Recorded, not mitigated.

## 5. Audit: the `scanning.*` category — a declared audit-model amendment

**Decision: the closed `category.action` registry ([audit-model.md](./audit-model.md), [#24](https://github.com/Dunky13/envweave/issues/24)) gains `scanning.*`, four actions, closed** — declared per the [oss-mechanics.md](./oss-mechanics.md) amendment procedure, banner in the audit ADR — **with the per-action v1 schema declared at this lock**, satisfying the registry's closure requirements (payload schema, schema version, retention class, permitted outcomes) rather than gesturing at them:

| Action | Emitted when | `scope_class` / chain / `object` | Payload (v1, `schema_version: 1`) | Outcomes | Retention |
|---|---|---|---|---|---|
| `scanning.finding_warned` | a Surface-1 write or declassification returns ≥1 finding — one event per finding | `env`; org→project→env; object = key identity | rule ID, surface (`value_write` \| `declassification` \| `import_value`) | `success` only — the warn cannot fail separately from the write it rides | `security` |
| `scanning.finding_dismissed` | an explicit keep-as-config acknowledgement is recorded | `env`; org→project→env; object = key identity | rule ID, **dismissal row ID** (opaque reference; the fingerprint itself never appears) | `success` only | `security` |
| `scanning.finding_blocked` | a declaration ingress is refused for ≥1 finding — one event per finding | `project`; org→project (no env — declarations are project-scoped); object = immutable declaration-field locator | rule ID, ingress (`edit` \| `plan` \| `apply`) | `success` only — the refusal is the event | `security` |
| `scanning.finding_overridden` | an acknowledged resubmission commits — one event per acknowledged finding | `project`; org→project; object = immutable declaration-field locator | rule ID, ingress, acknowledgement token reference | `success` only | `security` |

Scope classes are drawn from the audit envelope's closed `instance|org|project|env` set — value events sit at `env` (the value's owning environment), declaration events at `project` (declarations are project-scoped); both land in the org-owned tenant trail.

- **Payload rule, normative: matched plaintext never enters an event — and neither does the fingerprint.** Events carry rule ID, the chain and object above, and opaque row references. Not the matched text, not offsets or length, not excerpts, not a redacted form — the trail is readable under `audit-read`, and carrying match content would mint the new disclosure path §2.4 forbids *through the audit system itself*. The fingerprint is excluded on a second ground: it is a **stable equality token** — publishing it to every `audit-read` holder would let events be correlated by value-equality across keys and time, an oracle the dismissal row (server-side, non-exported) does not create. The event references the dismissal row by ID; forensics that genuinely need the fingerprint read the row under the server's own authority, not the trail.
- **These are ordinary domain events from the write paths, not authorization denials.** A `scanning.finding_blocked` refusal is validation, not a failed `authorize()` — the authorization package's single declared denial-writer ([audit-model.md](./audit-model.md) amendment part 4) is not involved and gains no second writer. No envelope change, no aggregation-licence change (a bulk import warns per finding, per event).
- **Durability composes with the transaction shapes in §7**: warn/dismiss/override events commit **in the same transaction as the write they describe**; block events commit **in their own transaction before the refusal is returned, with nothing else persisted** — the same durable-before-response discipline the audit ADR demands, in the only shape a refusal permits.
- **No configuration event exists because no configuration exists** (§8): the ruleset version is a property of the running binary, surfaced read-only (doctor/version surface, [ops-spec.md](./ops-spec.md)), and changes only by deployment — which the instance's ordinary upgrade story already covers.

## 6. No new disclosure path: the analysis, not the assertion

The §2.4 constraint is discharged structurally, clause by clause:

1. **The scan reads only plaintext already legitimately in process.** It executes inside write requests (on request content) and inside the declassification ceremony (on plaintext the reveal-gated ceremony already holds). There is no background job, no scan-the-corpus pass, no standing decryption authority. A scheduled retro-scan over existing values would require exactly the decrypt-and-scan authority §2.4 forbids — **rejected by name**; the consequence is stated honestly: values that predate a ruleset addition are not retroactively flagged; they are re-scanned when next edited or declassified, and that is the whole story in v1.
2. **Findings surface only to principals who already have the content.** Surface-1 findings return to the writer, in the write response. Surface-2 findings return to whoever submitted the refused ingress — for a plan authored by one principal and applied by another, apply-time findings reach the applier, who **already holds read authority over the declaration text being applied** (declarations are readable to any principal who can plan/apply them, and Surface-2 text is bundle-public by doctrine); no finding crosses a read boundary. There is no cross-principal notification surface in v1.
3. **The finding DTO is redacted by construction** (§4): rule ID + locator + opaque token, never content, offsets, length, or excerpts — on the wire, in logs, in every CLI format, in import output, in the DOM. SS4's canary sweep covers all of these, not just audit rows.
4. **The trail carries locators and opaque references, never matches and never fingerprints** (§5).
5. **Secret values are never scanned** (§2, Surface 3) — the scanner cannot leak what it structurally never reads. The one place secret plaintext meets the scanner is declassification, where the locked ceremony already discloses it to the acting principal.
6. **The fingerprint is keyed under a dedicated tier-3 key inside the envelope package** (§4) — the one derived artifact the scanner persists is useless outside the live instance, and it never leaves server-side rows.

## 7. Execution: the chokepoints, the transactions, the budgets

**Decision: one shared scanner runs below every ingress where scanned content is written — not at one verb, at every door.**

- **Surface 1 chokepoints**: the config-value write path (one server path serving UI, CLI, raw API, and server-side `values import` — [import-paths.md](./import-paths.md) phase 2's `values import` is a value write like any other and meets the same scanner; its findings ride the **`values import` response** and its CLI output contract, per finding, warn-not-block. Import phase 1 is client-side artifact authoring the server never sees — nothing to scan there, stated so the two-phase grammar is untouched); and the **declassification ceremony** (§2).
- **Surface 2 chokepoints — every declaration ingress**: **(a)** direct declaration edits (UI/CLI/API key add/edit, folder and environment and group naming — the DB-mode "ordinary pending change" path per [schema-model.md](./schema-model.md)) are scanned **before the pending change or draft persists** — a credential-shaped string is refused before it ever becomes stored declaration metadata, pending state included; **(b)** `definitions plan` scans **before the immutable plan persists** — a plan artifact is stored declaration text and must not be born carrying a credential; **(c)** `definitions apply` **re-scans iff the running ruleset snapshot differs from the one recorded in the plan** (the plan pins the snapshot version it was scanned under; same-version apply adds no second scan of identical bytes). Acknowledgement tokens (§4) are honored at each ingress under the same content-binding rules. The earlier draft's single-chokepoint claim ("scanned at `definitions apply`") was wrong twice — normal edits never pass through `apply`, and a plan persists before `apply` runs — and is corrected by construction here.
- **Transaction shapes, fixed** (composing with audit durability, §5): Surface-1 warn — authorize → scan → **one transaction**: value write + `finding_warned` events (+ dismissal-match lookup) → commit → compose response. Dismissal — **one transaction**: dismissal row + `finding_dismissed` event. Surface-2 refusal — **nothing persists except** the `finding_blocked` events, committed before the error returns. Surface-2 acknowledged commit — **one transaction**: declaration write + `finding_overridden` events. There is no post-commit event write and no crash window in which a write exists without its events or events without their write.
- **Synchronous is load-bearing, not incidental.** An asynchronous scan cannot block a declaration ingress (the block is the feature), and it turns the Surface-1 warn into an after-the-fact notification requiring exactly the cross-principal notification surface §6.2 declines to build. *Rejected by name.* **A client-side pre-check in the CLI is likewise rejected**: two rulesets in lockstep, and version skew produces contradictory verdicts on the same content.
- **Budgets — explicit, because RE2 alone bounds nothing aggregate.** New bound categories with concrete v1 defaults, normative here, recorded in the ops-spec decision inventory as a **declared post-lock addition** (row 15, added at this lock — not merely claimed): **per-item scanned bytes** = the existing value/declaration size caps (64 KiB value, 64 KiB declaration — nothing scanned is unbounded upstream); **ruleset size ceiling: ≤ 64 compiled rules** (the seven-family manifest plus headroom; raising it is an ops-spec default change, not silent growth); **per-request aggregate scan work** = the enclosing operation's item caps × the per-item budget, under the scan **sharing the enclosing operation's existing deadline** (a publish or apply that would exceed its locked deadline budget because of scan work fails loudly under that same deadline — scanning composes with the cap, it does not get its own second clock; there is no scan-specific item count because every scanned path already carries one); **per-request finding count cap: ≤ 100 findings** (matching the schema error-cap precedent; a request exceeding it fails closed naming the cap — never a silent truncation of findings); **response-byte cap** = the existing error/response-byte cap family covers the finding list. Boot: the ruleset compiles **once at boot; compile failure refuses to start** (fail fast — a binary that silently ships a half-compiled ruleset is a scanner that silently isn't one); **boot compile ≤ 2 s and ≤ 32 MiB on the calibration floor *(measured)*** — a build-known property of the pinned snapshot asserted by the `bench-scan` harness, not an open-ended runtime variable.
- **Performance envelope: the scan adds ≤ 5 ms p99 per scanned item at the size cap on the calibration floor** (Pi 4 / 4 GB sqlite and 2 vCPU / 4 GB VPS, [ops-spec.md](./ops-spec.md) §1), marked ***(measured)*** per the ops-spec convention. The instrument is a **named executable benchmark harness** (`bench-scan`: corpus × compiled ruleset, reporting per-item latency distribution) committed with the corpus: CI runs it as a **relative regression guard** (order-of-magnitude, deliberately not absolute-ms — CI runners are not Pis); the Pi-class run of the same harness, with its stored result artifact, is the pre-implementation-freeze verification the *(measured)* convention requires. The absolute number is the ops-spec registry's to hold; the gate (SS1) asserts the harness and the guard.

Findings and acknowledgements are fields on the **existing** verbs and endpoints — **no new CLI verbs, no new endpoints**; the closed #25 verb taxonomy is untouched and needs no amendment. The UI renders warn/block dialogs on the locked editing surfaces ([#21](https://github.com/Dunky13/envweave/issues/21)) through the same slot validation errors use.

## 8. Configurability: none, and the escape hatch is the dismissal

**Decision: v1 ships no runtime configurability — no instance toggle, no org toggle, no operator-supplied custom rules. The ruleset is a property of the binary.**

The per-finding sticky dismissal (§4) **is** the escape hatch: it absorbs false positives at exactly the granularity they occur, leaving an audit record, instead of an org-wide kill switch that someone flips after one annoyance and never flips back — the audit ADR's off-switch-in-the-restrained-hand shape, and the same reasoning that kept the audit trail's completeness untoggleable. The decision also keeps the ops surface clean by construction: zero new tunables in the ops-spec registry beyond §7's bounds, zero new rows on the locked settings chrome ([#29](https://github.com/Dunky13/envweave/issues/29)).

*Rejected: org-level toggle* — a real freedom argument (their org, their risk), but it needs a capability answer (an amendment to locked #15 or an overload of an existing atom), a settings row on locked chrome, and it silently disarms the guardrail for every member at once while the dismissal mechanism already handles the legitimate cases individually. *Rejected: instance-config toggle* — the operator disarming every tenant's guardrail at once is precisely the operator≡org-admin hardening direction the SCIM ADR refused.

**Post-v1 register rows** (mvp-boundary §4 terms): **org-level disable** — trigger: sustained false-positive noise that the dismissal mechanism demonstrably cannot absorb, evidenced from the field, not hypothesized; **operator custom rules** — trigger: demand naming a pattern class the vendored allowlist misses (the first response remains an upstream/allowlist addition; custom rules only if the class is genuinely private).

## 9. Acceptance criteria — SS1–SS4 join the 1.0 gate
