# Envweave revisions, drafts, publishing & rollback (ADR, locked 2026-07-29)

Context: the domain model ([#7](https://github.com/Dunky13/envweave/issues/7)) fixed the **Resolved snapshot** as an immutable, per-`(project, environment)` materialization carrying the full key→value map, per-key provenance, and a validation verdict. The inheritance ADR ([inheritance-model.md](./inheritance-model.md)) fixed *what* a publish must do — carry an impact preview, bind that preview to the exact schema/layer/base-graph/authorization revisions it was computed against, require per-environment publish authorization evaluated immediately before commit, and materialize every affected environment **atomically** — and delegated to this ticket *when* a snapshot is created and how the draft→publish lifecycle works. This ADR fixes the revision lifecycle: workload-facing revision identity, the draft model, rollback semantics, secret-safe diffs, the matrix "changed" signals, retention, concurrency, and the live-update constraint.

> **Amended twice by the schema ADR ([schema-model.md](./schema-model.md), 2026-07-30, [#12](https://github.com/Dunky13/envweave/issues/12)):**
> 1. **§ Revision identity — canonical encoding.** The change token is computed over a **delivery manifest** of ordered `(key, classification, value)` triples, not a bare key→value map. This changes the stated `iff`: two snapshots with identical key/value bytes but differing classification now produce **different** tokens. Required because an adapter routing `secret` → K8s `Secret` and `config` → `ConfigMap` would otherwise see an unchanged token across a reclassification and never fire the rollout that relocates the value. The `v1:` prefix is retained — nothing has shipped. See [schema-model.md § The change token covers a delivery manifest](./schema-model.md).
> 2. **§ Draft model / § Retention — bounds.** "Editing an entry creates a new version rather than mutating the old one" is unbounded as written; a client saving one field in a loop mints unbounded immutable versions and multiplies every later schema change's revalidation work. Now bounded: per-user and per-project live-draft quotas, GC of superseded pending versions, only the latest version per `(owner, key, layer)` publishable and revalidated, a schema-revision rate limit, and canonical dedup. Concrete values → operations spec. See [schema-model.md § Bounds](./schema-model.md).

Granularity note: this is the wayfinding-level revision ADR. Required-ness and per-key validation rules remain owned by the schema model ([#12](https://github.com/Dunky13/envweave/issues/12)) — this ADR adds one item to its vocabulary (*key groups*, below); the per-capability permission ladder by RBAC ([#15](https://github.com/Dunky13/envweave/issues/15)); the audit event shapes by the audit ticket ([#24](https://github.com/Dunky13/envweave/issues/24)); the live-update transport by the architecture ticket ([#22](https://github.com/Dunky13/envweave/issues/22)); concrete retention, quota, and bound values by the operations spec. Each MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

## Revision identity — monotonic number + opaque change token

A published snapshot is addressed two ways, both recorded at materialization:

- **Revision number** — monotonic per `(project, environment)`. Human-facing ordering ("rev 42"), the unit rollback and history reference.
- **Change token** — an opaque, fixed-length token for machine change detection. This is what the Kubernetes operator's hash-annotation restart mechanism ([k8s-delivery.md](../research/k8s-delivery.md)) consumes: the operator compares tokens to decide whether a rollout is needed.

**The change token is keyed, not a bare content hash.** It is `HMAC(scoped token key, versioned canonical encoding of the resolved key→value map)`. A bare digest over content is a function of secret plaintexts, so a low-entropy secret is brute-forceable offline by anyone holding the digest — and the Kubernetes operator writes that value into a pod-template annotation, where it is readable by every principal who can read Deployments but not Secrets. A keyed token is unforgeable and un-invertible without the key, so it can flow into annotations, logs, and change-detection caches as ordinary non-secret metadata.

**The token key is derived per `(org, project, environment)`**, not shared installation-wide, via a KDF from a server root token key with the scope as context. A single global key would make tokens comparable *across* scopes: an attacker who can write values in their own project constructs a candidate payload, reads its token, and compares it against a target environment's pod annotation — a cross-tenant equality oracle that survives the keying. Scoped derivation makes a token meaningful only within the environment that produced it, which is the only comparison the Kubernetes operator ever needs. The root token key is an Envweave server key managed under the encryption model ([#14](https://github.com/Dunky13/envweave/issues/14)); rotating it changes every token (forcing one benign rollout wave), which the operations spec must call out.

**The token covers delivered content only** — not the pinned schema/layer/base-graph revisions. Two snapshots have equal tokens **iff** they deliver identical content, so re-publishing the same values under a newer schema revision produces the same token and triggers no rollout. Snapshot *identity* (which inputs produced it) is the revision number plus the pinned input revisions recorded on the snapshot; those are separate fields, not folded into the token.

**The encoding and token scheme are versioned from v1** (`v1:<token>`). This is a public machine contract embedded in pod annotations and client caches; changing it later without a version prefix silently invalidates every consumer's comparison.

**Workload addressing.** A workload fetch defaults to **latest published snapshot** for its `(project, environment)` — this is what "changes apply on restart" means: a restart pulls latest. A workload may instead be **pinned to an explicit revision** (see *Pins* under *Retention* — a pin is a durable authorized resource, not a fetch parameter). Delivery reads only committed, valid snapshots (inheritance ADR) or fails closed.

*Rejected:* token-only addressing — immutable but supplies no ordering and no "latest" without a separate pointer, and gives humans nothing to say out loud. Number-only — leaves the operator diffing full payloads to detect change. Bare content digest — the brute-force and annotation-exposure problems above.

## Draft model — per-user working state, selective publish

Each user has their **own working state** within a project: an edit to a `(key, layer)` entry is saved immediately as a **pending change** owned by that user, recorded against the published revision it was staged from. Every pending change has an **immutable version id**; editing an entry creates a new version rather than mutating the old one. Saving is free — per the inheritance ADR, work-in-progress may hold unresolved or masked required keys; only publishing is gated.

Per-user working state exists because a shared one is both lossy and unsafe. Lossy: two contributors cannot hold alternative edits to the same entry — the second overwrites the first. Unsafe: with a shared state, Alice can preview a change, Bob can overwrite that entry, and Alice's publish then commits Bob's value under Alice's production authorization, without the published baseline ever moving to trip a conflict check. Ownership removes the class rather than patching it.

**A publish carries only the publisher's own pending changes**, selected by immutable version id. No principal can publish another principal's staged edit; there is no cross-user hand-off of pending work in v1 (that is approval-workflow territory, held outside MVP). The impact preview, authorization check, and validation are computed for exactly that selection of version ids, and the atomic multi-environment materialize covers exactly the environments it affects. Unselected pending changes remain pending.

**Selection isolation (binding).** The publish computes the resolved snapshot of each affected environment **from the last published state plus the selected pending-change versions only**. Every other pending change — the publisher's unselected ones and every other user's — is invisible to that computation, so the materialized snapshot always corresponds to a state the publisher previewed.

**Key groups — dependency closure (binding on [#12](https://github.com/Dunky13/envweave/issues/12)).** Schema validity is not operational validity: publishing a rotated `DB_PASSWORD` without its matching `DB_USER` passes every per-key check and breaks production. Selection isolation proves the preview is faithful; it does not prove the selection is *complete*. So the schema model gains one vocabulary item: a project may declare a **key group** — a named set of keys that must change together. Selection is then **automatically closed over key groups**: selecting a pending change to any group member pulls the publisher's pending changes to the other members into the same publish. If a group member has a pending change owned by **another** user, or the group's members would end up spanning two publishes, the publish is **rejected loud** naming the group — never silently split. Keys not in a declared group carry no coupling guarantee, and the ADR says so plainly rather than implying one.

*Rejected:* a single shared project-wide working state (lossy and enables the preview-laundering path above). *Rejected:* all-or-nothing publish of a whole working state — one contributor's staged-but-unresolved required key would abort every publish in the project until its author returned, and unrelated edits would ride into production on someone else's authority. *Rejected:* named changesets / PR-style multiple concurrent named batches — per-user ownership already supplies the immutable identity and isolation that make selective publish safe; named batches add naming, listing, and hand-off surface whose real payoff is approval workflow, explicitly outside MVP. Deferred, not precluded — and now genuinely additive, since the identity and ownership machinery exists.

## Rollback — a new revision, never a rewrite

**History is never rewritten.** Restoring an earlier state creates a **new** revision through the normal publish pipeline: it stages pending changes owned by the restoring user, and publishing them runs the full impact preview, per-environment publish authorization, protected-environment confirmation, validation, and atomic materialize. There is no privileged rollback path that bypasses any of these.

Two granularities, both landing in the user's working state as ordinary pending changes:

- **Environment-level** — "restore `(project, env)` to rev N".
- **Per-key** — "restore this key's earlier value".

**Restore is least-blast and deterministic: it writes only to the target environment's own layer.** Reproducing rev N's resolved state has multiple valid inverses with wildly different blast radii — if `prod` rev 10 inherited `DB_URL=X` from `staging` and `staging` now supplies `Y`, prod's old state can be reproduced by a prod-local override *or* by rewinding `staging` (which also drags `qa` back). The ADR fixes the first: restore stages **local** entries in the target environment reproducing rev N's outcome, and never mutates a shared layer or the base graph.

**The comparison is over resolved presence state *and* value, never value alone.** Rev N's outcome for a key is one of `set(v)`, `masked` (deliberately unresolved), or `unset` (never resolved); a restore that compared only values would treat a historical `masked` and a current `absent` as equally "unresolved" and leave the entry alone — silently dropping the mask and re-enabling inheritance on a key an operator had deliberately blocked, which is exactly the silent secret re-exposure the inheritance ADR's delete-vs-mask rule exists to prevent. So, per key:

- rev N `set(v)`, current resolves to anything but `v` → stage local `set(v)`.
- rev N `masked`, current not masked at the target → stage local `masked`.
- rev N `unset`, current resolves to a value → stage local `masked`, because a local mask is the only way to reproduce "unresolved here" without touching a shared layer. This is a deliberate semantic upgrade — never-set becomes deliberately-unresolved — and it is surfaced as such in the impact preview rather than applied quietly.
- rev N `unset`, current `masked` → **left untouched**. Both deliver "unresolved", and the current state is the *more* protective of the two: dropping the mask to match a historical never-set would re-enable inheritance as a side effect of a rollback. **Restore never weakens a mask.** The retained mask is noted in the preview so the operator sees that the restored state is protected where rev N merely happened to be empty.
- Outcome already matches in both presence state and value → left untouched, no churn.

The mask asymmetry is deliberate: a mask is restored when rev N had one and the target does not, and is never removed to reproduce its absence.

The cost is explicit: restoring an inherited value **flattens** it into a local override, changing provenance from inherited to local. That provenance change is a resolution-affecting mutation, so it appears in the impact preview like any other (inheritance ADR requires provenance-only changes to surface), and the operator sees exactly which cells stop inheriting. An operator who genuinely wants the shared layer rewound does that as an ordinary shared-layer edit, with its full blast radius and authorization — not disguised as a rollback.

**Restores re-validate against the current schema revision, not the schema revision pinned in the old snapshot.** A snapshot's stored verdict is immutable with respect to its pinned inputs (inheritance ADR) — that is why a pinned workload keeps receiving it. But re-publishing old content forward is a new delivery, and validation-before-delivery is a property of what workloads receive from the current published state. If the schema has since tightened, some historical states are **not restorable as-is**: the publish aborts loud, naming the failing keys, and the operator resolves them explicitly.

**A revision whose payload has been garbage-collected is not restorable** (see *Retention*). The attempt fails loud, naming the revision and the policy that collected it; nothing is reconstructed or substituted.

## Diffs and secret safety

Revision diffs follow the same disclosure model as the inheritance ADR's impact preview — one rule everywhere, no second code path to get wrong.

**Classification is sticky to the historical value, not to the key's current setting.** Every stored value records the classification in force when it was written. Reclassifying `PAYMENT_PIN` from `secret` to `config` must not retroactively declassify the plaintexts written while it was secret. A comparison or display is gated at the **stricter** of the two sides: if either side of a diff — or either side's historical classification — was `secret`, the whole comparison is treated as secret. The same holds for deleted keys: their retained historical values keep the classification they were written under.

- **`config`-classified (on both sides)** — plaintext old→new diff under normal environment read authorization.
- **`secret`-classified (on either side)** — **status only**, and the status a principal sees depends on whether they hold reveal:
  - **Without reveal** — the status is **write-presence**, not comparison: `edited` / `not edited` / `added` / `removed` / `masked`. It reports that someone wrote to this entry, never whether the plaintext differs.
  - **With reveal** — the comparison statuses `changed` / `unchanged` are additionally available.
  
  This split exists because *comparison status is itself an oracle*: a principal who can edit but not reveal could stage a guessed value and read `unchanged` to confirm it, recovering a low-entropy secret without ever holding reveal — exactly the guessing oracle the keyed change token was introduced to close. Write-presence carries no information about the plaintext. Neither plaintext, digest, nor change token of a secret-bearing snapshot is exposed in a status-only diff.
- **Plaintext reveal of a secret in a diff** is a **separate explicit per-key action**, gated on **current reveal authorization**, re-checked with any required reauthentication **immediately before rendering**, and **audited** as a disclosure event — per the threat model's authorize-before-each-disclosure and separate-capability rules ([threat-model.md](./threat-model.md)). Publish authorization never confers reveal.

**Historical reveal is a capability distinct from current reveal** (binds [#15](https://github.com/Dunky13/envweave/issues/15)). Reading the current value of a secret and reading its predecessors are different powers over different systems: a rotated credential may still be live in an external service, or may unlock decommissioned infrastructure the current one cannot reach. Granting someone operational access today should not silently hand them every credential the installation has ever held. So RBAC expresses `reveal` and `reveal-history` separately; a role may of course hold both, and the default administrator role does. Both are audited identically as disclosure events, with the historical one recording the revision read. *(This reverses an earlier lean to bundle them — Codex cross-review round 1 showed the "they can already do the damage" argument is false across rotation boundaries.)*

## Matrix UI — two "changed" signals, computed on resolved values

The matrix carries two visually distinct signals ([#20](https://github.com/Dunky13/envweave/issues/20), [#21](https://github.com/Dunky13/envweave/issues/21) own the visual design):

1. **Pending** — this cell's resolved value differs from the last published snapshot because of **the viewer's own** unpublished pending changes. This is the primary signal; it answers "what will my publish do". A secondary, visually quieter marker indicates that **another user has a pending change** to this entry, so collisions are visible before publish time.
2. **Recently changed** — this cell's resolved value changed in the last published revision (with "changed in rev N" available on inspection). Secondary, and it fades with age.

**Both are computed on the resolved value, not on the layer entry.** A cell that inherits from `staging` shows changed when `staging`'s value changes, even though nothing was edited in that column. Computing on layer entries would hide exactly the blast radius the inheritance ADR requires the product to surface. The signal distinguishes **directly edited here** from **changed by inheritance**, since per-value provenance is already required rendering.

**For `secret`-classified keys both signals degrade to write-presence for principals without reveal**, under the oracle rule above: the matrix may show that an entry was written, never that its plaintext differs from the published one. Without this, the matrix reproduces the guessing oracle the diff rules close.

## Retention

**Two distinct histories with different retention rules.** Conflating them either grows the database without bound or throws away the lineage:

- **Revision lineage — retained indefinitely.** The small, bounded record of what happened: revision numbers, timestamps, publisher identity, which keys changed in each revision, and the pinned input revisions. One row per revision per environment plus one per changed key. This is what makes history explainable, and it never contains values.
- **Audit event log — policy-managed retention.** The high-volume stream: every fetch, every disclosure, every authorization decision. The threat model requires audit growth to be retention-managed, and workload fetches alone make this unbounded on a single-node install. Retention policy, archival, and export are owned by the audit ticket ([#24](https://github.com/Dunky13/envweave/issues/24)) and the operations spec.

**Snapshot payloads** (the encrypted resolved values, and every other value-bearing representation of a historical revision) are garbage-collected by policy. The default keeps the last N revisions per environment plus everything within X days; concrete values are fixed in the operations spec. **Retention may be configured to unlimited** where an operator's compliance posture requires it — a single explicit setting, not an emergent behavior.

**GC scope is every value-bearing record, not just the snapshot row.** If change records, diff caches, or audit entries retained enough ciphertext to reconstruct a collected revision, they would be payloads in substance and would preserve exactly the secrets GC claims to retire. They do not: the lineage records *which* keys changed, never their values. The consequence is stated plainly rather than papered over — **a collected revision cannot be restored, diffed by value, or revealed.** There is no replay-from-metadata path. Requests against a collected revision fail loud naming the revision.

**Pins are durable, authorized, bounded resources.** A pin is created explicitly (an operator or an authorized human pinning a workload to a revision), not implied by a fetch parameter — a fetch parameter is not a reference GC can observe, and would let any read-only workload token pin every revision and defeat retention entirely. Each pin is a stored record with an owner, an authorization check at creation, a per-project quota, and an expiry; creating a pin and marking its payload retained is **one atomic operation**, so GC can never delete a revision that a concurrent pin request is acquiring. A payload is never collected while it is the current snapshot of an environment or while any live pin references it; where a pin holds a payload past its policy window, that pin is surfaced to operators as the reason, with a release action.

**Pinned delivery is an explicit, documented exception to current-schema validation.** A pinned revision was validated against the schema revision it was built for and is delivered verbatim thereafter, even after the schema tightens. This is the point of pinning — reproducibility — and it means "everything delivered now satisfies the current schema" is true of *latest* delivery, not of pinned delivery. Creating a **new** pin to a revision that fails current-schema validation requires an explicit override and is recorded as such; an existing pin is grandfathered and surfaced to operators as drift.

**GC bounds live-database exposure, not backup exposure.** Removing a revision's payload from the database does not remove it from retained backups, and the threat model already notes an old root key still decrypts copies protected under that key version. So bounded payload retention is a real reduction in what a stolen *live* database yields, and it is a precondition for rotation meaning something — but effective retirement of a historical secret also requires a bound on backup retention (or per-revision cryptographic erasure). That bound belongs to the operations spec and the encryption model ([#14](https://github.com/Dunky13/envweave/issues/14)); this ADR does not claim GC alone achieves it.

*Rejected:* keep every payload forever as the only mode (unbounded growth; rotation never retires old ciphertext). *Rejected:* store only per-key change events and materialize snapshots on demand — cheapest storage, but it breaks the inheritance ADR's "delivery reads only committed snapshots" and puts re-derivation cost on every fetch.

## Concurrency — owned drafts, serialized publish

Per-user working state removes stage-time conflict entirely: two principals staging a change to the same `(key, layer)` each hold their own pending change, and neither destroys the other's. The matrix surfaces the collision (above) so it is visible before publish rather than discovered after.

Two rules govern commit:

- **Publish is a single serializable operation per project.** Conflict checking, snapshot construction, revision-number allocation, and the latest-pointer advance happen inside one serializable transaction (or under a per-project advisory lock) covering the project's published state — the same invariant the inheritance ADR already imposes on base-graph mutation. Without it, two publishes computed from the same baseline can both commit — X publishing `A=2` and Y publishing `B=2` — and the later latest-pointer advance silently reverts the other's key, because per-entry freshness checks each pass and unique revision numbers alone do not linearize the outcome.
- **Optimistic freshness check, by immutable version id.** A publish names specific pending-change **version ids**, and is **rejected loud** if the published state of any selected entry has advanced since that version was staged, or if any named version has been superseded by a newer edit from its owner. Binding to version ids rather than to entry identity is what prevents a publisher from committing a value they never previewed. This composes with the inheritance ADR's preview-freshness rule, which invalidates and recomputes a preview whose pinned schema/layer/base-graph/authorization revisions have advanced.

*Rejected:* per-key locks held from stage to publish — abandoned edits become deadlocks and demand a lock-administration surface. *Rejected:* silent last-write-wins anywhere in the path — violates fail-fast, fail-loud.

## Live updates — advisory, metadata only, per-event authorized

The matrix view receives **server-pushed change notifications** so another user's staged change and another publisher's advance are visible without a manual refresh. Binding constraints:

- **Metadata only.** The channel carries facts *about* changes — "user X staged a pending change to `(env, key)`", "`(env)` advanced to rev N", "your pending change to `(env, key)` is now stale". It **never** carries values, and never carries change tokens. Clients refetch under their own authorization, so every disclosure still passes the authorize-immediately-before-each-disclosure check rather than riding a channel authorized once at connect time.
- **Authorization is per event and per referenced object, with recipient-specific projection.** Checking only that the subscriber may view the project is insufficient: a user with `dev` access but not `prod` would otherwise receive `user X changed (prod, PAYMENT_KEY)` — which environments exist, which keys they hold, and when production changed are all disclosure. Every event is authorized against **each environment and key it references**, and is projected per recipient: unauthorized references are dropped, and an event reduced to nothing is not sent. Revocation mid-session takes effect on the next event, not at the next reconnect.
- **Advisory only.** Correctness never depends on delivery. The serialized publish and the version-id freshness check are the authority; a client that missed every event still cannot publish a stale change. This keeps the feature droppable under any transport failure.
- **Transport is delegated to the architecture ticket** ([#22](https://github.com/Dunky13/envweave/issues/22)), with server-sent events as the standing recommendation: the traffic is one-directional server→client fanout of state the server already owns, which is exactly SSE's shape, and it needs a documented polling fallback for proxies that break long-lived streams.

*Rejected: WebRTC.* Peer-to-peer transport (signaling server, STUN/TURN, DTLS) for what is server→client fanout — large machinery for the wrong topology, and routing configuration data through a client mesh moves data off the server boundary the threat model draws. *Rejected for v1: collaborative editing (CRDT/OT) and presence cursors* — the edit unit is a whole value, not a shared document; deferred, not precluded.

## Propagations (binding on downstream tickets)

- **Schema model ([#12](https://github.com/Dunky13/envweave/issues/12))** — owns required-ness and per-key rules; publish-time and restore-time validation consume them, restore against the **current** schema revision. **Must add key groups** (declared co-change sets) to the v1 vocabulary, per *Draft model*.
- **RBAC ([#15](https://github.com/Dunky13/envweave/issues/15))** — must express `reveal` and `reveal-history` as **distinct** capabilities, both separate from read and from publish; must supply the per-environment publish authorization and protected-environment confirmation that rollback publishes are subject to; must support per-event, per-object authorization for live-update projection.
- **Encryption model ([#14](https://github.com/Dunky13/envweave/issues/14))** — owns the server-held **change-token key** (storage, rotation, and the benign rollout wave rotation causes); owns per-revision cryptographic erasure if that is how backup exposure is bounded.
- **Matrix-UI prototypes ([#20](https://github.com/Dunky13/envweave/issues/20), [#21](https://github.com/Dunky13/envweave/issues/21))** — must render the pending and recently-changed signals distinctly, compute both on resolved values, distinguish directly-edited from changed-by-inheritance, show other users' pending changes, and degrade both signals to **write-presence** for `secret` keys without reveal.
- **Audit ([#24](https://github.com/Dunky13/envweave/issues/24))** — must define events for publish, rollback-publish, secret reveal (current and historical, as distinct disclosure events recording the revision), pin creation/override/release, retention-policy change, and payload garbage collection; and must own the **audit log's own retention policy**, distinct from the permanently-retained revision lineage.
- **Architecture ([#22](https://github.com/Dunky13/envweave/issues/22))** — owns the live-update transport (SSE recommended) and its polling fallback, under the metadata-only, per-event-authorized, advisory-only constraints above.
- **Kubernetes integration ([#19](https://github.com/Dunky13/envweave/issues/19))** — consumes the **keyed change token** for hash-annotation restarts; must use the token, never a content digest, and must handle the token-scheme version prefix.
- **Operations spec (fog)** — fixes default retention values (N revisions, X days), pin quotas and expiry defaults, the unlimited-retention option and its backup-exposure consequence, and the **backup-retention bound** without which GC does not retire historical secrets.
