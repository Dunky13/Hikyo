# Wenv GitHub Actions adapter — deltas over the deployment-module seam (ADR, locked 2026-08-06)

Context: the MVP boundary ([mvp-boundary.md](./mvp-boundary.md) §2.1, [#26](https://github.com/Dunky13/wenv/issues/26)) promotes a GitHub Actions deployment adapter into 1.0 as the second in-tree adapter over the seam fixed in [deployment-adapter.md](./deployment-adapter.md). That ADR's **constraints transfer wholesale**; its **mechanisms do not transfer by assumption** — each was re-derived here against GitHub's actual REST API, verified in [docs/research/github-actions-api.md](../research/github-actions-api.md) (facts cited below without repeating URLs; every endpoint/status claim traces to that file, ambiguities included). This is a sibling ADR: it composes with the seam, amends nothing. Where this ADR is silent, the Forgejo ADR's rule applies verbatim.

Granularity note: wayfinding-level, like its sibling. Concrete pacing curves, attempt bounds, queue depths → operations spec ([ops-spec.md](./ops-spec.md), a declared post-lock addition per its bound registry). Adapter-configuration UI already locked at [#31](https://github.com/Dunky13/wenv/issues/31) extends with the GitHub-only knobs (destination kind, visibility, environment-create consent) → synthesis carries the delta ([#27](https://github.com/Dunky13/wenv/issues/27)). Exact fine-grained-PAT permission spellings and the CI contract-test fixtures are pinned at implementation against this ADR's rules.

## What transfers unchanged (cited, not restated)

From [deployment-adapter.md](./deployment-adapter.md), adopted as written: the four-operation seam and its value-blind `Plan`; full-state converge with writes-before-prunes; the stale-write fence (target generation + exclusive per-target provider-write lease); supersede semantics; per-sensitive-step re-authorization; the two triggers (on-publish + manual) and the rejection of scheduled reconcile; the ledger (reserve → dispatch → confirm, global uniqueness constraint, `owned ∪ dispatched` prune set, strict ledger-bounded pruning); adoption's artifact binding and revalidation; the sentinel pair and its reserved name; id-bound explicit key subsets with widen/narrow asymmetry; the pinned-key rule (rename/reclassify refused while targeted); the destination collision rule on effective names; the per-target `name_prefix` and canonical-name invariant; teardown scrub/orphan semantics and the dead-credential rule; the one-way value-blind posture and its **no-variable-read rule** (GitHub's variable get/list responses carry stored plaintext values at every scope — the read path must not exist, structurally); the egress posture; the authorization table; the audit spellings (category `adapter`, closed action set — no new actions here); the CLI verb family. The `GITHUB_` reserved prefix the Forgejo grammar already banned is, on this provider, the provider's own rule.

**One transferred rule gets a sharpening this provider forces: secret name lists are paginated, and conflict refusal is only as good as list completeness.** Every secret name list the adapter consumes (plan, dispatch re-check, org-truncation warning) MUST be exhaustively paginated; a converge or plan whose list traversal fails or terminates early **fails closed by name — a partial list is never treated as the list**. A truncated list would convert an unowned existing secret into a silent PUT overwrite, which is the capture the conflict refusal exists to prevent. Page-size bounds → ops spec.

## Destinations — repository, organization, environment

**Three destination kinds in v1: repository, organization, and repository environment.** The API shapes are parallel (`/repos/{owner}/{repo}/actions/…`, `/orgs/{org}/actions/…`, `/repos/{owner}/{repo}/environments/{environment_name}/…`). A target remains one Wenv environment → one destination; the ledger identity gains the kind: **`(provider origin, destination, surface, normalized effective name)` where destination is `(repo id)`, `(org id)`, or `(repo id, environment id)` — immutable numeric ids in every kind, the environment included.** The environment *name* appears in API paths and displays, but it is a locator, not identity: paths address by name, the ledger and every binding (adoption acknowledgements, uniqueness constraint) key on the pinned numeric ids. Path segments are URL-encoded exactly once (environment names may contain `/`, encoded `%2F`); encoding fixtures (slash, percent, exotic-but-legal names) are contract-tested.

**Environment destinations are the recommended multi-environment shape on this provider** — GitHub has what Forgejo lacks, so the docs lead with it: one repo building dev/stage/prod maps to three environment targets with no prefix and no workflow-side name stripping (workflows select the environment; canonical names arrive as-is). **The prefix mechanism transfers anyway** and is the documented fallback for where environments don't exist: **Free-plan private repositories have no environments at all** (public repos: all plans). GitHub's own resolution precedence is environment > repository > organization. **Falling back is always the user's reconfiguration, never the adapter's**: an environment-target failure is refused by name with the fallback *named in the message* — the adapter never silently redirects a write to repo scope.

**Identity pinning extends to the environment.** The repo/org resolves to its immutable numeric id at configure time, verified per operation, mismatch = hard named refusal — the Forgejo rule verbatim. The environment's numeric id is pinned at configure time (environments are GET-readable under Actions read) and verified per converge. An id mismatch — or a 404 where the environment stood — means the environment was deleted (its provider-side secrets and variables died with it) and possibly recreated as a fresh namespace wearing the old name: hard named refusal, no silent re-pin, no converge-time resurrection. **The repair is re-configure**: pointing the target at the successor environment is a routing mutation (full formula — the destination id changed), the old destination's ledger rows are **released** (retained for audit, claiming nothing — the namespace they described no longer exists), and conflicts in the successor namespace surface through the ordinary adoption path. Stale claims never transfer to a new id.

**Environment auto-create is a configure-time provider mutation, specified — not a converge-time repair, and not a hole in the seam.** Per the resolved grilling, `target add` against a missing environment creates it. The mechanism:

- Creation happens **inside the `target add` flow**, which already carries the full formula + reauthentication; the acting principal's authorization covers the create. It precedes the target's first converge, and the target's provider-write lease and generation exist from `target add` — the create is the target's first fenced provider write, single-flighted trivially (no converge can exist yet).
- **INTENT/OUTCOME wrap it like any external effect** (threat model rule): the create PUT rides the existing `adapter.push_intent` / `adapter.push_outcome` spellings — they are defined per provider write request, and this is one; `correlation_id` binds to the `adapter.configure` event instead of an outbox job. Declared interpretation, no new audit action.
- **Order: GET (absence check) → PUT (create).** The PUT is issued only after a GET returns not-found, and the PUT body carries **no protection-rule fields whatsoever**. The TOCTOU residual is stated, not hidden: GitHub offers create-or-update with no conditional-create, so a third party creating the environment between GET and PUT means our PUT lands as an *update*. Two containments, one pinned: (1) the empty-of-settings body — **a CI contract test pins that a settings-free PUT against an existing environment leaves reviewers/branch-policy untouched; if that pin ever breaks, auto-create is disabled by the failing gate**, not left to damage settings; (2) immediately after the PUT, the adapter GETs the environment to pin its id — a creation-race environment is thereby *adopted as the destination knowingly at configure time* by the same reauthenticated principal, which is what configure means. Scope note: creation needs fine-grained **Administration (write)** — deliberately broader than the delivery floor — so a scope-refused create fails **by name, stating both remediations**: pre-create the environment in GitHub's UI (keeps the token minimal), or widen the token.

**Organization destinations carry visibility as target routing — and visibility modes are not a total order.** Org secrets and variables carry `visibility` (`all` | `private` | `selected`, the last with selected repositories). The recipient-set algebra is: `private ⊂ all` and `selected ⊂ all` (selected repositories are org repositories by construction), but **`private` and `selected` are incomparable** — `private → selected` can add public repositories, `selected → private` can add every unselected private repository. So the widening/narrowing split is decided on **recipient sets, not mode names**:

- **Plain narrowing** is exactly: `all → private`, `all → selected`, and removing ids from a `selected` set — the only transitions where the new recipient set is provably ⊆ the old.
- **Everything else is a routing mutation** — `→ all` from anywhere, `private ↔ selected` in either direction, adding ids to a `selected` set: full formula + reauthentication + authority reassignment.
- **Selected repositories are pinned by immutable numeric id at configure time** and verified before every routing write; a vanished or recreated id is a named refusal (the recreated-repo disclosure hole is closed the same way destination pinning closes it). Both surfaces' selected sets are maintained by **full-set replacement** via their `/repositories` sub-endpoints — atomic per call, so no partial update leaves a stale or broader intermediate recipient set; exact call ordering is pinned at implementation under the invariant that **no intermediate provider state is ever broader than both the old and new configurations**.

The converge continuously re-asserts the configured visibility (the org secret PUT carries it; the variable surface's visibility rides its own write/replace calls) — declarative, like every owned attribute. The Forgejo ADR's wide-destination caveat transfers with sharper teeth: GitHub's precedence means an org-target's `converged@revN` is a storage-level claim shadowable by both repo- and environment-level same-name entries, and a repo-target's by environment-level ones; the docs state this beside the target-kind instructions, and the sentinel breadcrumb remains the human-facing pointer. Same-name entries at other scopes are invisible to the adapter by design (no read exists that would see them safely); no shadow detection is attempted, per the sibling's rejected-alternative reasoning, which transfers.

## The secret surface — sealed box, and honest about what it is not

**Writes are client-side sealed-box encrypted.** Per converge, per scope, the adapter fetches the destination's public key (`GET …/secrets/public-key` at repo, org, or environment scope), then each secret PUT carries `encrypted_value` (libsodium sealed box — `crypto_box_seal`; in Go, `nacl/box` anonymous sealing) plus the returned `key_id`. The public key is fetched **fresh at converge start** inside the job's authorized operation scope; plaintext exists only within each push attempt's scope per the architecture's crypto boundary.

**Stated honestly: sealed box narrows Wenv's outbound exposure, nothing more.** What it guarantees is exactly this: **plaintext is absent from Wenv's outbound HTTP bodies and from any request log under Wenv's or intermediaries' control** — an improvement over Forgejo's plaintext-inside-TLS body. It is not end-to-end encryption and no doc claims it: GitHub holds the private key, decrypts at workflow time, and under the transferred provider-as-attacker model can do anything with the plaintext thereafter, its own logs included.

**Stale `key_id` has no documented error contract** (research ambiguity #2). The rule, in order: a 4xx from a secret PUT is **first classified against the rate-limit decision tree** (§ Rate envelope — 403/429 rate responses are waits, not errors); only a non-rate 4xx takes the stale-key path: re-fetch the public key, **re-seal the plaintext under the new key** (a new `key_id` is a new sealed box — retrying the old ciphertext is invalid by construction), and retry that write **once**, under the same step-boundary re-authorization gate as any sensitive step. A second failure is a terminal named failure for that name; its ledger disposition follows the seam: a refusal that provably did not land releases a `reserved`-lineage row, an indeterminate outcome leaves `dispatched`.

**The PUT's 201/204 split (created/updated) is a documented oracle — and on a first write, an unexpected 204 is possible capture, not routine drift.** The converge records which status each name got. Two cases, sharply distinct:

- **First dispatch of a reservation** (fresh absence check this converge): the expected status is 201. **A 204 means the name appeared between the list check and the PUT and Wenv just overwrote a value it never wrote** — the seam's accepted dispatch window, *hit*. The write is not silently confirmed: the name is recorded as a **`possible_capture` conflict finding** (a payload disposition on the push outcome and the target's sync status — no new audit action), the row does **not** transition to `owned`, and continued management of that name requires the explicit adoption acknowledgement path, same binding and revalidation as any adoption. The overwrite itself cannot be undone (re-pushing a prior value is a disclosure decision, per the seam) — what the rule buys is that capture is *surfaced and dispositioned by a human*, never absorbed.
- **Retry from `dispatched`** (indeterminate prior attempt): 204 is expected — the plausible writer is Wenv's own landed request — and the seam's presumed-written rule applies: confirm `owned`. The residual (a third party creating the name inside an indeterminate window is indistinguishable) is the seam's stated dispatch-window residual, unchanged here.

A 201 where the ledger held `owned` (our name vanished provider-side) is the inverse drift signal: logged by name in the OUTCOME payload, ownership retained, nothing silent.

Secret list/get return names and timestamps only at all scopes — the plannable surface, same as Forgejo — subject to the exhaustive-pagination rule (§ Transfers).

## The variable surface — the POST-409 oracle, pinned

GitHub's variable API is create-with-POST / update-with-PATCH — unlike Forgejo's POST/PUT — and the conflict oracle the seam requires exists in the same place: **POST-create fails on an existing name.** The observed status is **409, contractually undocumented** (the REST reference lists only 201; GitHub's own `gh` CLI hard-depends on the 409 — research ambiguity #1). Per the resolved grilling, the adapter uses it, **pinned, not assumed**:

- **A CI contract test against the real API** asserts POST-on-existing fails with 409 (and that get/list still carry values, keeping the no-read rule's premise pinned too). **The pin is scoped**: it holds for the provider/version/destination-kind combinations the harness exercises (github.com, all three kinds); GHES inherits it best-effort only (§ GHES). The gate catches contract drift **before a release ships** — it does not and cannot protect already-deployed releases from a provider-side change, which is why the runtime branch below fails safe on its own.
- **At runtime the branch is exact**: POST → 201 = created (dispatch semantics as the seam fixes); POST → 409 = the conflict signal, recorded as the variable surface's adoption artifact exactly like Forgejo's failed-create; **POST → anything else = an ambiguous named failure for that name — no PATCH, no transition, no inference**. Never a blind PATCH on an unexpected status — `gh`'s fallback-to-PATCH-on-409 shape is precisely what the ownership model forbids without a ledger claim.
- **PATCH is issued only for ledger-owned names, and its failure handling is a specified state machine, not a hope.** PATCH-on-missing has no documented status (ambiguity #3); the contract test pins the observed status (expected 404). Then: **a pinned missing-name response** on an owned-name PATCH marks that row `owned, missing` — ownership retained, absence recorded — and the same converge (or the next) recreates it via POST from that state: **201 → re-confirmed `owned`**, the recreate's INTENT/OUTCOME riding the ordinary push spellings; **409 → the name reappeared under someone else's hand mid-window — a conflict finding: ownership suspended, adoption acknowledgement required to resume management** (never a blind PATCH-over). **Any other PATCH failure — auth, rate (classified first), unknown 4xx/5xx — transitions nothing**: the row stays plain `owned`, the name fails by name in the outcome, and the failure class is named. Absence is the only signal that moves the state machine, and only its pinned spelling counts.
- Delete-then-recreate was considered and rejected for both oracle and update duty: as an oracle it probes existence by destroying (deleting an unowned name is the silent capture the conflict refusal exists to prevent, and strictly ledger-bounded pruning forbids the DELETE); as an update path it doubles mutation cost under the content-creation budget and opens a read hole mid-converge that writes-before-prunes exists to close.

Adoption semantics per surface therefore transfer with the artifact kinds unchanged: **secrets adopt from a `Plan` artifact** (the names-only list shows conflicts pre-write) **or from a recorded `possible_capture` sync finding** (§ Secret surface — the write outcome that must not self-confirm); **variables adopt from recorded sync conflicts** (the 409 — and the recreate-race 409 above — durably recorded with destination, generation, job id). Every artifact kind carries the same binding and revalidation; zero value read-back. Plan artifacts bind adoption to what the plan *saw* — sync-time findings are their own artifacts, never retroactively folded into a plan.

## Naming, limits, byte-exactness

- **Grammar (both surfaces, provider-enforced):** alphanumeric + underscore, no leading digit, no `GITHUB_` prefix. Names are case-insensitive and stored uppercase — the sibling's rule transfers verbatim: **a non-uppercase effective name is refused by name**, never silently uppercased, and case-insensitive collisions between effective names are one named configure/`Plan` error. No `FORGEJO_`/`GITEA_` ban here (each adapter encodes its provider's real rules), and no variable-`CI` ban — GitHub documents none.
- **Size: 48 KB per secret and per variable.** An oversize value is **refused by name at `Sync`** (where values first exist; `Plan` is value-blind and cannot see size) — the sibling's unrepresentable-value posture: named key, stated reason, no chunking or encoding costume. GitHub's own documented workaround (encrypt a file into the repo) is a consumption-semantics change Wenv does not smuggle in.
- **Count caps: named provider errors, pre-warned where honestly computable.** Caps: 100 secrets / 500 variables per repo, 1,000 / 1,000 per org, 100 / 100 per environment. On the **secret** surface `Plan` sees the provider's full name list and warns exactly. On the **variable** surface no safe read exists, so the warning is **explicitly a lower bound** computed from manifest + ledger — unowned provider variables consume the cap invisibly, the docs say so, and a cap hit at `Sync` remains a per-name named failure either way.
- **Workflow-visibility truncation caveats — both stated, both warned:** (1) workflows see only the first 100 org secrets alphabetically; when an org target's owned set plus the provider's listed names exceeds 100, `Plan`/`Sync` warn by name. (2) **A workflow run's combined org+repo variables are capped at 256 KB** — storage writes succeed while workflow delivery silently truncates, the same failure class. The adapter warns when manifest + ledger variable bytes cross the threshold, **as a lower bound** (unreadable unrelated variables make an exact prediction impossible, stated). Both are storage-vs-consumption gaps; the acceptance criteria exercise consumption, not just storage.
- **Byte-exactness is pinned by consumption, not assumed for either surface.** The sealed box forecloses transformation of Wenv's *outbound bytes*, but proves nothing about what GitHub stores after decryption or hands a workflow. So the CI contract tests pin **round-trip byte-exactness through real workflow consumption for both surfaces** — representative classes: CRLF and lone `\r`, trailing whitespace, non-ASCII/Unicode, size boundaries, and the binary edge (variables additionally harness-read in the fixture; the adapter still has no read path). **NUL-containing values are refused by name at `Sync`, both surfaces, from day one** — the consumption path is process environment variables, where NUL is structurally unrepresentable; this is the Compose ADR's unrepresentable-class rule, not a provider question. Non-UTF-8 byte sequences short of NUL are pinned by the fixture: preserved → supported; transformed or rejected by the provider → a named refusal class. A discovered transform becomes a named refusal class like Forgejo's `\r` rule, decided at implementation against evidence, not guessed here.

## Credential — fine-grained PAT floor, classic refused

**The outbound credential is a fine-grained personal access token; classic PATs are refused by name.** Token kinds are contractually prefix-distinguishable (`github_pat_` vs `ghp_`), so configure and `TestConnection` refuse a classic PAT client-side before any provider call, stating why: a classic PAT is a coarse account-wide grant that cannot express least privilege over these endpoints, and standing outbound custody of one contradicts the minimal-scope posture. An org whose policy blocks fine-grained PATs changes its policy, not Wenv's floor. (Per the resolved grilling — the version-floor refuse-by-name pattern applied to credential kind.)

**Scope floor by destination kind** (fine-grained permission names, exact spellings pinned at implementation): repo targets — repository **Secrets: write** + **Variables: write**; environment targets — repository **Environments: write** (which gates both env secrets and env variables; Secrets/Variables permissions do not cover them) **+ Actions: read** (the environment GET that the identity pin performs at configure, TestConnection, and every converge reads under it); org targets — organization **Secrets: write** + **Variables: write**. Environment auto-create alone additionally needs repository **Administration: write** — opt-in, never the floor (§ Destinations). Fine-grained PATs are single-resource-owner: an adapter's targets all live under one owner by construction (one adapter = one credential), and org-approval-pending tokens surface as `TestConnection` auth failures, named. Docs prescribe the minimal recipe per destination kind; the ops spec carries it (propagation), and the E2E harness mints the exact minimum token per kind to prove the recipe is really the floor.

**Expiry posture: accept what the provider mints, surface what it communicates.** Fine-grained lifetimes run 1–366 days or `none`; org policy may cap them. The adapter treats expiry as an operational fact, not a floor: `TestConnection` and `adapter show` surface expiry metadata when the provider communicates it on responses (header presence pinned at implementation), and an expired token fails exactly like a revoked one — named auth failure, dead-credential teardown rule in force (remove targets while it still authenticates). Custody rules transfer: write-only, envelope-encrypted at rest, replace-don't-read.

## Rate envelope — serial, header-driven, in-job waits

GitHub's documented limits: primary 5,000 req/h per PAT; secondary — 100 concurrent, 900 points/min per endpoint group (mutations cost 5 → ≈180 mutations/min), **80 content-creating requests/min and 500/h**. GitHub's stated best practice for mutation bursts: serial requests, ≥1 s between mutations. The adapter's rules:

- **All provider mutations under one adapter credential serialize through one pacer** honoring the documented spacing — the per-target write lease already single-flights each target; the pacer extends that to the credential, since the budget is per-token. Concrete pacing curve and attempt bounds → ops spec, under this invariant.
- **Rate-limit classification follows GitHub's full documented decision tree, fallbacks included**: a 403/429 with `retry-after` waits that long; else with `x-ratelimit-remaining: 0`, waits until `x-ratelimit-reset`; **else — headerless 403/429 with no auth-failure signature — waits at least one minute and backs off exponentially under a bounded retry cap** (secondary limits can answer headerless; a headerless response is never immediately terminal). Only a response that classifies as none of these is an error with its own name (auth, not-found, contract drift).
- **A rate-limit wait is an in-job pause, never alone a terminal failure — and plaintext does not sleep.** The converge records its position (a cursor of completed names — no values), **discards the manifest and every derived ciphertext before any wait that leaves the step boundary**, then on resume re-authorizes and reassembles the *remaining* manifest inside a fresh authorized transaction — confirmed writes are not replayed, progress is monotonic, and the crypto boundary's plaintext-lifetime rule holds across waits of any length. The generation fence and re-authorization checks apply at every step boundary, resumes included. **If the single-converge wall-clock bound (ops spec) expires mid-wait, the job fails named-non-terminal and returns to the outbox's ordinary backoff** — a later attempt is a fresh converge; nothing is silently dropped.
- **No hardcoded quotas.** GHES rate limits are admin-configured and may differ arbitrarily; the adapter keys off response headers everywhere, github.com included. The numbers above size the ops-spec defaults; they are not baked into refusal logic.

## TestConnection — honest about what it can probe

`TestConnection` probes: credential kind (prefix) and validity; destination identity (repo/org id match, environment id match where applicable — under the env-target floor's Actions: read); secret-surface permission and reachability (the names-only secret list is a safe read, exhaustively paginated); the sealed-box public-key endpoint for the target's scope. **Environment-endpoint failures are reported as what they verifiably are — a named capability/authorization failure for that destination** — because GitHub documents no status distinguishing Free-plan-private unavailability from permission loss or deletion (research ambiguity #6); the message names the possible causes and the prefix fallback *as a reconfiguration the user may choose*, and the adapter never probes its way into a silent repo-scope fallback. **It cannot probe variable-surface permission or presence**: every variable read returns values, the no-read rule is structural, and TestConnection must not mutate — so no safe probe exists, on github.com or GHES alike. Stated plainly: **Variables/Environments write permission is first proven by the sentinel variable write on first sync** — a scope-refused sentinel write is a named first-sync failure pointing at the token recipe, not a mystery. One probe short, said out loud, beats a value-bearing GET that breaks the adapter's central structural guarantee.

## GHES — configurable base URL, best-effort, said out loud

Per the resolved grilling: **the adapter accepts a GitHub Enterprise Server base URL** (`https://HOST/api/v3`; github.com default `https://api.github.com`), same endpoint paths after the prefix. `TestConnection` probes what it can probe safely — credential acceptance (fine-grained PAT), destination resolution, the secret list, the public-key endpoint — and refuses a missing capability by name, the sibling's version-floor pattern; the variable surface stays sentinel-proven (§ TestConnection), on GHES as everywhere. **The support claim is honest: v1 CI exercises github.com only.** GHES conformance is best-effort — probe-guarded, header-driven (no github.com quota assumptions), but not harness-proven, **and the contract-test pins (the 409 oracle, PATCH-on-missing, settings-preserving PUT, byte-exactness) are asserted against github.com — on GHES they are assumptions, and the docs say exactly that**; a pinned GHES floor with a real E2E harness is the recorded upgrade path (§ Deferred). The egress posture already covers the self-hosted case: a GHES on RFC1918 is the instance-operator exception, deliberately.

## Audit & CLI — no new spellings

The `adapter` audit category's closed action set covers every operation here; no new actions. GitHub-specific facts ride in existing payloads: destination kind and environment id in configure/adopt/plan payloads; the 201/204 signals, `possible_capture` and `owned, missing` dispositions, and per-name outcomes in push payloads; the configure-time environment create's INTENT/OUTCOME on the push spellings with configure-event correlation (§ Destinations — declared interpretation, no new action); rate-limit waits are job-progress facts (ops-level observability), not audit events. CLI verbs are the seam's family unchanged; `adapter create` takes provider type `github`, `target add` gains the destination-kind grammar (repo / org / repo+environment) and, for org targets, visibility with pinned selected-repo ids. `target show --format workflow` emits the env-selection or prefix-strip mapping per the target's shape, names only.

## Acceptance criteria (mvp-boundary §1.1 format)

Extends the M4 row ([mvp-boundary.md](./mvp-boundary.md) §1.1); owning doc: this ADR.

[E2E] against real github.com (dedicated test org), per destination kind (repo, org, environment): converge → `converged@revN` with workflow-side consumption asserting exact values on both surfaces (sealed-box encrypt→decrypt and variable delivery proven end to end); adoption per artifact kind — secret Plan conflict, variable 409 conflict, `possible_capture` finding — each incl. stale-acknowledgement refusal on generation bump; identity pins at every kind: environment delete-and-recreate → converge refuses by name, re-configure releases old-id rows; **repo and org delete-and-recreate (or transfer) → id-mismatch named refusal, no write to the successor**; auto-create: minimal-token refusal names both remediations, Administration-scoped token creates with pinned id, post-PUT id pin holds; classic PAT (`ghp_`) refused at configure and TestConnection; **minimum-token proof per destination kind** (the documented recipe authenticates; one permission less fails named); visibility matrix: each plain-narrowing transition (`all→private`, `all→selected`, id removal) succeeds plain, each other transition demands the full formula (fixture per direction, `private↔selected` both ways); teardown scrub empties all three kinds, sentinels last; dead-credential teardown orphans loudly. [CI, deterministic stubs] the transferred state machine on GitHub's verbs: reserve-state crash replay, dispatch-window duplicate, indeterminate-retry 204 confirmation vs first-attempt 204 → `possible_capture` (no silent `owned`), PATCH-missing → `owned, missing` → POST 201 reconfirm and → POST 409 suspend-to-adoption, stale-key path (rate-classified first, re-seal asserted — old ciphertext never re-sent), generation supersede mid-flight, **teardown racing an in-flight provider write (the scrub waits for the in-flight request's terminal or indeterminate outcome — never fires alongside it)**, credential replace/revoke mid-queue, selected-set full-replacement never broader mid-state, pagination fail-closed (conflict beyond page one refused, truncated traversal fails converge). [CI, contract pins vs real API] variable POST-on-existing = 409; PATCH-on-missing status; non-201/non-409 create → ambiguous named failure, no PATCH (stub); variable get/list value-bearing premise; settings-free environment PUT preserves protection rules; byte-exactness through workflow consumption, both surfaces (CRLF, lone `\r`, trailing whitespace, Unicode, non-UTF-8 bytes, 48 KB boundary; oversize refused by name; NUL-containing value refused by name at Sync, both surfaces); >100 org-secrets warning and 256 KB variable lower-bound warning fixtures; env-name URL-encoding (slash `%2F`, percent) exactly once; rate tree: `retry-after`, reset-only, and headerless 403/429 each → in-job wait and resume at cursor (manifest discarded during wait, asserted), wall-clock expiry → named non-terminal; no-variable-read asserted structurally (no GET/list variable code path linked — the sibling's import-boundary test, same mechanism).
