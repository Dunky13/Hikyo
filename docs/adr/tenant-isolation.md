# Wenv tenant isolation — enforcement, layer by layer (ADR, locked 2026-08-02)

> **Declared amendment (2026-08-06, [scim-provisioning.md](./scim-provisioning.md), [#38](https://github.com/Dunky13/wenv/issues/38), per the [oss-mechanics.md](./oss-mechanics.md) amendment procedure):** the authz package's import-bounded **identity-resolution interface gains the SCIM provisioning create/attach lookup as a named member** — instance-wide `(kind, issuer, subject)` resolution for an org binding's user create, never through tenant-scoped stores, one query path whether the identity exists or not, response byte-shape identical between fresh-create and attach (the cross-org account-existence oracle is closed by equality, with engine microtiming remaining this ADR's stated residual). SCIM wire operations join the probe-classification and authorization registries with formula `scim-provision(org)` and proof-carrying authorization like every other operation — no structural bypass. Details in [scim-provisioning.md](./scim-provisioning.md).

> **Amended narrowly by the flat-model ADR ([flat-model.md](./flat-model.md), 2026-08-06, [#40](https://github.com/Dunky13/wenv/issues/40)):** the restated transplant-resistance invariant reads cross-*environment*, not cross-*layer*. Nothing else changes.

Context: the threat model ([#8](https://github.com/Dunky13/wenv/issues/8)) fixed the *stance* — cross-org isolation is **deny-by-default authorization with org context propagated through every execution path via a single mandatory chokepoint**, explicitly **not** cryptographic per-org keys in v1, with the residual stated: an authorization bug is not backstopped by crypto. The architecture ADR ([#22](https://github.com/Dunky13/wenv/issues/22)) fixed the *siting*: authorization happens inside the service-layer transaction at `authorize()`, handlers structurally cannot reach the store, and there is no authenticated principal outside a transaction. The permission ADR ([#15](https://github.com/Dunky13/wenv/issues/15)) fixed the *semantics*: `authorize(principal, capability, scope)` in-transaction, no authorization cache, unauthorized ≡ nonexistent on every route, and per-operation **authorization formulas** — conjunctions over dynamically resolved scopes, not one capability per endpoint. What none of them fixed — and each explicitly delegated here — is the **pattern**: how a query, a job step, a cache entry or a probe suite actually carries the tenant boundary, such that isolation is enforced once instead of re-implemented per endpoint. This ADR fixes that pattern.

Granularity note: this ADR fixes the enforcement mechanism — the proof type, the row shape, the query discipline, the cache keying rule, and the CI/lint machinery that keeps them honest. It does not add capabilities, scopes or event shapes: the capability lattice stays [#15](https://github.com/Dunky13/wenv/issues/15)'s, audit event shapes go to [#24](https://github.com/Dunky13/wenv/issues/24), endpoint enumeration to [#25](https://github.com/Dunky13/wenv/issues/25), concrete quota/limit values to the ops spec ([#32](https://github.com/Dunky13/wenv/issues/32)). Each delegated ticket MUST satisfy the constraints stated here; a delegation satisfied in letter but violating an intent stated here reopens this ADR.

**What kind of guarantee this ADR makes, stated up front.** The pattern below layers three kinds of enforcement, and the ADR names which is which rather than selling one as another: **structural** (the code cannot express the bug — compile failure), **fail-closed runtime** (the bug is expressible but every instance dies at a single checked boundary, before any data moves), and **CI/lint guardrail** (the bug is caught at build time by analysis or probes, with its honest evasion limits stated). "Unforgeable" and "unexpressible" below always mean one of these three, never folklore.

## No DB-level tenancy — application-layer scoping only

Isolation is enforced in the application layer, through the repository pattern this ADR defines. There is **no row-level security, no per-tenant database role, no engine-level tenancy mechanism** on either engine.

*Rejected: Postgres RLS as primary enforcement.* Dead on arrival against the locked sqlite parity commitment ([#3](https://github.com/Dunky13/wenv/issues/3), [#22](https://github.com/Dunky13/wenv/issues/22)): sqlite has no RLS, so the primary isolation mechanism would exist on one engine only — the architecture ADR already rejects postgres-only infrastructure on exactly this ground.

*Rejected: RLS as defence-in-depth on postgres only.* Tempting and still wrong, on three grounds. First, it **splits enforcement semantics across engines**: the cross-engine conformance suite would pass sqlite paths that RLS silently covers on postgres, so scoping bugs hide preferentially on the engine without the net — the deployment profile ([#3](https://github.com/Dunky13/wenv/issues/3)) says small installs, which is where sqlite runs. Second, it demands per-transaction `SET LOCAL` plumbing through the one package that owns the transaction boundary, for a backstop the threat model already **declines to claim**: a datastore writer is operator-equivalent, and the accepted residual is precisely "an authorization bug is not backstopped". Third, a second mechanism is a second thing to audit, and the half-trusted one rots. One mechanism, tested hard, beats two half-trusted ones. Revisit alongside the threat model's own revisit trigger (SaaS multi-tenancy).

## The chokepoint pattern — proof-carrying authorization

The re-implemented-per-endpoint trap has a specific shape: each endpoint separately looks up the object, separately checks its org, separately checks the capability, and one of them eventually forgets a step. The pattern that closes it is **proof-carrying authorization**: `authorize()` returns a value — a **proof** — and the store accepts calls only with one. The proof's properties, each with its enforcement kind:

- **A proof exists only as `authorize()`'s return value** *(structural + fail-closed)*. `authz.Proof` is an exported **interface with an unexported method**, implemented by exactly one unexported type inside the authorization package. Outside code cannot implement it and cannot construct a non-nil value of it; the **only forgeable value is `nil`**, and the store boundary rejects a nil or non-canonical proof fail-closed before touching any query. The zero-value composite-literal forgery (`authz.Proof{}` from another package) is therefore not closed by "unexported fields" — Go permits zero values across packages — it is closed by the interface shape plus the boundary check, and the forgery-guard analyzer additionally flags any declaration of the concrete type or `nil`-proof literal outside the authorization package.
- **A proof is operation-bound** *(fail-closed runtime + CI)*. [#15](https://github.com/Dunky13/wenv/issues/15) requires per-operation authorization *formulas* — conjunctions across dynamically resolved scopes — so a proof minted for one formula must not satisfy another: `authorize()` evaluates a named formula from the **operation registry** (the single table mapping each operation to its formula, the registry [#25](https://github.com/Dunky13/wenv/issues/25) enumerates endpoints against), and the proof records **which operation it was minted for**. Every store method is registered with the operation(s) it serves; the store boundary rejects a proof minted for a different operation. A `read`-formula proof handed to the reveal path dies at the boundary, not in review. CI asserts registry completeness: a store method with no registered operation, or an operation with no formula, fails the build.
- **A proof is transaction-bound and single-use per step** *(fail-closed runtime)*. The proof carries the identity of the transaction it was minted in and is invalidated at commit or rollback; the store boundary rejects a proof presented outside its live transaction. A proof is therefore not a capability token, not storable, not reusable across retries — copying the Go value copies a reference to a dead or foreign transaction and fails closed. This is what makes "no authorization cache" ([#15](https://github.com/Dunky13/wenv/issues/15)) and "re-authorize before every sensitive step" *mechanical*: yesterday's proof cannot be replayed after a revocation because yesterday's transaction is gone.
- **The proof carries the resolved tenant identifiers, and only generated code binds them** *(structural + codegen)*. Every store method takes the proof as its first argument, and the **chain parameters of every statement are bound by the store's generated binding layer directly from the proof** — the caller-facing signature exposes no chain parameters at all, so caller arguments *cannot reach* the chain predicate or the chain columns of an insert: the binding map from proof fields to chain parameters is generated, part of the trusted query registry, and conformance-tested (chain parameters map from proof fields and from nothing else). The proof-signature analyzer additionally bans tenant-identifier-typed parameters (`domain.OrgID`/`ProjectID`/`EnvID`) in store signatures **and transitively in argument struct fields**. Honest limit, stated: a caller can still smuggle a tenant id as a raw string into a *non-chain* parameter (a name filter, a search term) — the analyzer cannot see intent in a string — but a non-chain parameter never reaches the chain predicate, so the smuggled id selects within the proof's tenant or selects nothing. "Authorized against project X, queried project Y" therefore requires editing generated code inside the trusted set, not writing ordinary service code.

**What "the missing check is a compile error" now precisely means:** *absent* authorization is structural — a service function that never called `authorize()` has no proof value to pass, and the call does not compile. *Wrong* authorization (stale proof, foreign transaction, mismatched operation, nil forgery) is expressible and is killed at the store boundary, fail-closed, before any query runs — one check, in one package, not per endpoint.

**Scope-chain resolution is one query, one round trip.** `authorize()` resolves the addressed chain (org → project → environment, as addressed by the request) in a **single query** joining the chain tables with all tenant predicates — not a top-down sequence of per-level lookups. Zero rows means the uniform nonexistent response, before any capability evaluation. What the single-query shape delivers, stated precisely: it eliminates every **application-visible** timing signal — no per-level branch divergence, no differing query *count* (a per-level walk does one query for a missing org and three for a missing environment, a probe-visible oracle), one round trip and one code path regardless of which level failed. What it does **not** deliver: equal engine-internal work — a join can stop early at a missing org row, and planner choice and data distribution vary. That microtiming residual is **accepted and stated**, the same class of honesty as the threat model's accepted residuals; see the harness section for how this squares with the locked "including timing" wording.

**The bootstrap reads are carved out explicitly, not smuggled.** `authorize()` cannot itself run under a proof — it must read sessions, credential verifiers, grants, chain ownership and recovery-mode state *in order to mint one*. Those reads go through a narrow, enumerated resolution interface (`internal/store/authn`) importable **only by the authorization package** — the same import-boundary machinery as handlers-never-import-store. The universal rule below is therefore stated exactly: **every store call outside the authorization package's own resolution interface requires a proof.** The resolution interface is part of the trusted set (with the transaction package and the authorization package itself), enumerated, and its surface is the highest-scrutiny diff target in the repo.

*Rejected: convention — repositories take `orgID, projectID` parameters and services pass them.* That is the trap itself with better marketing; the negative tests catch omissions only where someone wrote a test. *Rejected: tenant ids resolved into `context.Context`.* Invisible, untyped, and a missing value is a runtime nil at 3am rather than a build failure; `context` smuggling is also exactly how a background job inherits a request's tenant by accident.

## Instance and system operations — two escape hatches, not one

The tenantless paths split on whether a **grant** is evaluated, and conflating them would turn route selection into authorization:

- **`authz.InstanceProof` — grant-evaluated, tenantless.** Instance-scoped operations (`backup-export`, `restore`, the rotation set `rotate-root-key`/`rotate-master-key`/`rotate-dek`/`reencrypt`, instance configuration, instance-scope member management) are **still authorized**: the encryption and permission ADRs fix them as operator- or instance-level **capabilities, separate grants**. `authorize()` evaluates the instance-scope formula exactly as for tenant operations and mints an `InstanceProof` — same interface shape, same operation binding, same transaction binding, no tenant chain. An `InstanceProof` is *proof of an instance grant*, never proof of having entered a route.
- **`authz.SystemProof` — the closed no-principal set, operation-bound like every other proof.** A handful of paths run where no principal can exist or where [#15](https://github.com/Dunky13/wenv/issues/15) explicitly places authority outside the grant table: **boot, migration (`migrate` mode), recovery-mode reconciliation, and break-glass local host authority** — the last being, per the permission ADR, "the only authorization path in the system not evaluated against a grant", which this ADR keeps true: `SystemProof` adds no second one, it *names* the existing set. A `SystemProof` is **not generic store authority**: it is operation-bound and transaction-bound exactly like the other proof kinds, against a closed **system-operation registry** that maps each mint site to the store operations it may invoke — boot to its pragma/keyring checks, migration to the migration tables, recovery reconciliation to the quarantined-grant set, break-glass to grant writes ([#15](https://github.com/Dunky13/wenv/issues/15)'s enumerated break-glass surface). The store boundary rejects a `SystemProof` presented for an operation outside its mint site's registry entry, fail-closed, same check as an operation-mismatched ordinary proof. Both the mint-site set and the per-site operation sets are closed and enumerated in this ADR's CI invariant; growth of either fails the build until this ADR is amended.

## Row shape and lookup discipline

**Every tenant-owned row carries the denormalized, immutable id chain down to its owning scope.** Rows come in **scope classes**, matching the encryption ADR's per-kind AAD schemas rather than one universal tuple: **org-owned** rows (org settings, org-scope grants, org membership) carry `org_id`; **project-owned** rows carry `org_id, project_id`; **environment-scoped** rows carry `org_id, project_id, env_id`. There is no mandatory `project_id` on a row whose owning scope is the org — the earlier universal phrasing was wrong the same way a universal AAD tuple would be. The columns are not a new cost: [#14](https://github.com/Dunky13/wenv/issues/14) already binds the same chain into every envelope's AAD (`value`: org+project+…, `project_field`: org+project, `instance_field`: none) and declares bound identifiers immutable.

**Chain consistency is constraint-enforced, not FK-adjacent.** Independent single-column FKs would accept `(org_id = A, project_id = B-of-org-C)` — three valid parents, inconsistent chain. Instead: **composite ancestry FKs** — parent tables expose composite unique keys (`(org_id, id)` on projects, `(org_id, project_id, id)` on environments) and children reference the composite, so a row's chain is consistent by constraint on both engines. **Immutability is enforced twice**: the SQL analyzer rejects any `UPDATE ... SET` naming a tenant-chain column (re-parenting is a new row, per [#14](https://github.com/Dunky13/wenv/issues/14)'s "a ciphertext is never copied between rows — any operation that produces a new row re-encrypts"), and the cross-engine conformance suite asserts the store exposes no operation that mutates a chain column.

**Filter-in-query, never fetch-then-check.** A store method appends the tenant predicate derived from the proof — the full chain to the row's owning scope — to every statement it issues. A cross-tenant identifier therefore matches **zero rows**: the foreign object is never loaded into memory, no post-fetch ownership branch exists to forget, and *missing* versus *foreign* are the same query outcome, which is what makes the permission ADR's same-status-same-body rule structural rather than per-endpoint. **Writes follow the same provenance rule in their own shape**: `INSERT` has no `WHERE`, so for inserts and upserts the tenant-chain columns are bound to **reserved parameters populated by the repository layer from the proof** — never from caller arguments (the signature analyzer already bans tenant-typed caller arguments); `ON CONFLICT DO UPDATE` branches are constrained like updates (conflict target includes the chain columns; the update branch may not set them).

*Rejected: fetch by bare id, compare ownership after.* The foreign row transits memory; the comparison is a branch someone forgets; found-then-rejected and not-found take observably different paths.

## Universal proof — every execution path, not just HTTP

The threat model's list — API handlers, background workers, exports, search, audit queries, K8s reconciliation, adapter jobs — becomes one rule:

**Every store call outside the authorization package's enumerated resolution interface carries a proof.**

- **Jobs and the adapter outbox** mint a **fresh proof per sensitive step**: each step is its own transaction, `authorize()` runs against the **recorded authority principal** ([#15](https://github.com/Dunky13/wenv/issues/15), [#22](https://github.com/Dunky13/wenv/issues/22)), and transaction-binding makes reuse of a prior step's proof mechanically impossible rather than merely forbidden. A job that outlives its principal's grants fails closed at the next step's mint. **Job-kind completeness is registry-based, not convention**: the outbox's job-type registry ([#22](https://github.com/Dunky13/wenv/issues/22)) is the closed enumeration the probe harness checks against — a new job kind without a probe fails the build regardless of whether anyone exported a method for it.
- **SSE emit-time authorization** ([#11](https://github.com/Dunky13/wenv/issues/11), [#22](https://github.com/Dunky13/wenv/issues/22)): the per-event, per-object check at emit time mints and consumes a proof like any other read.
- **Search is decrypt-and-scan under proof.** The encryption ADR already forbids SQL predicates over values; the scan's candidate set is tenant-filtered by the proof's predicate before any decryption, and each decrypt is authorization-checked per value as [#14](https://github.com/Dunky13/wenv/issues/14) requires.
- **Audit queries** are tenant-scoped reads like any other: audit events carry the id chain of the acted-on scope (to its owning scope class), and an org-scoped audit view resolves through the same proof discipline. Event shapes and the read capability's exact placement stay with [#24](https://github.com/Dunky13/wenv/issues/24), bound by this rule.
- **Workload and operator fetches** ([#18](https://github.com/Dunky13/wenv/issues/18), [#19](https://github.com/Dunky13/wenv/issues/19)): the K8s ADR assigns this ticket the proof that the server never lets one project's credential resolve another project's material. Under this pattern that is the ordinary proof: the credential resolves to a principal whose grants are confined to its owning project's subtree ([#17](https://github.com/Dunky13/wenv/issues/17)), `authorize()` resolves the addressed chain, and a cross-project fetch dies at the chain resolution with the uniform response — indistinguishable, per [#17](https://github.com/Dunky13/wenv/issues/17), from a revoked or unknown credential.
- **Backups and exports** split on the grant boundary above: `values export` is an env-scoped authorized disclosure ([#15](https://github.com/Dunky13/wenv/issues/15), [#18](https://github.com/Dunky13/wenv/issues/18)) under an ordinary proof; the **instance backup** runs under an `InstanceProof` minted against the `backup-export` grant — instance-scoped, cross-tenant by definition, trusted per the threat model's operator stance, and still grant-evaluated. There is **no per-org backup** in v1; the per-tenant export surface is `values export` and the definitions bundle, both proof-gated.

## Caches — proof-gated access, full-chain keys

Two rules, because keying alone is not authorization:

**Access rule.** A cache holding tenant-owned data is store-adjacent: its read and write methods **take a proof**, like any store method, and sit downstream of `authorize()`. A cache *hit* therefore passes the same boundary a query does — the earlier framing ("the refill path re-runs under a proof") was wrong exactly where it mattered, since a hit bypasses refill; under this rule there is no proof-free path to a hit either.

**Keying rule.** Entries are keyed by the **full id chain to the owning scope** — `(org_id, project_id, [env_id], leaf…)` — via **exactly one exported key constructor per cache, whose input is the proof** (the chain comes out of the proof, so a caller cannot assemble a key from request ids at all). Structured, injective encoding (length-prefixed — the same argument [#14](https://github.com/Dunky13/wenv/issues/14) makes for AAD and HKDF info strings: bare concatenation is how `(org "a", project "bc")` and `(org "ab", project "c")` collide). Ad-hoc `fmt.Sprintf` keys are lint-banned. Applied to the existing caches, not excepted from them: the **DEK LRU** is keyed `(org_id, project_id)` (the chain to a project-owned object — not bare project id), the **change-token cache** `(org_id, project_id, env_id)` (already the HKDF info tuple in [#14](https://github.com/Dunky13/wenv/issues/14)), the **JWKS cache** is instance-scoped with no tenant axis. Eviction rules stay with the owning ADRs. There is still **no authorization cache** ([#15](https://github.com/Dunky13/wenv/issues/15)); nothing here weakens that — these caches hold derived material, never authorization results.

## What cryptography contributes — and what it must never be sold as

Per-project DEKs participate in isolation to exactly three ends, and this ADR names them so nobody upgrades them by folklore:

1. **Transplant resistance.** AAD row-anchoring means a ciphertext moved across rows, layers, keys, projects, organizations or envelope kinds fails to decrypt — even for a datastore writer ([#14](https://github.com/Dunky13/wenv/issues/14)).
2. **Crypto-shred.** Destroying a deleted project's DEK protects future copies of the datastore ([#14](https://github.com/Dunky13/wenv/issues/14), with its honest limits: not retroactive against existing backups).
3. **Blast-radius bounding.** A compromised project DEK exposes one project's key domain.

What per-project keys do **not** do, verbatim from the locked ADRs: stop an attacker holding API-level authority ("that is authorization, not cryptography" — [#14](https://github.com/Dunky13/wenv/issues/14)); backstop an authorization bug (the threat model's accepted residual, revisit-if-SaaS); make "AAD-bound" mean "tamper-proof" ([#14](https://github.com/Dunky13/wenv/issues/14)'s own documentation rule).

**Documentation rule, normative:** no Wenv documentation, marketing text, or UI copy may present per-project encryption keys as a tenant access-control mechanism. Isolation is authorization; the keys bound blast radius.

*Rejected: promoting DEKs into the authorization path* (per-request key release, per-org KMS routing as an isolation claim). Re-opens the locked encryption ADR, which explicitly scopes the KMS seam to the root-key boundary; expresses access policy in a second language beside the grant table, which [#15](https://github.com/Dunky13/wenv/issues/15) forbids; and buys nothing against the attacker classes the threat model actually defends.

## Enforcement machinery — the probe harness and the static layer

Guarantees above are structural or fail-closed; these keep them true as the code grows. Both layers are **guardrails with named evasion limits**, not proofs.

**The cross-tenant probe harness (CI, build-failing).** Every operation is **classified, and unclassified fails the build** — classification is the completeness mechanism, replacing the incoherent "every operation gets a cross-tenant probe" (login has no foreign-tenant twin; the instance backup is cross-tenant by design; `migrate` has no principal at all). Four classes, each with its own probe contract:

- **Tenant-scoped operations** (the bulk): cross-tenant probes on a fixed fixture set — two organizations; a human principal in org B probing org A's objects; and **machine-principal fixtures probing cross-project within one org** (a workload credential from project P₁ addressing project P₂'s material — [#19](https://github.com/Dunky13/wenv/issues/19) assigns this ticket exactly that proof, and org-level probes alone never exercise it). Asserted: the **uniform nonexistent response** (status and body byte-shape identical to a genuinely missing object, via the shared assertion helper the contract tests already use); **no bulk leak** (mixed-tenant id sets show no trace of foreign objects in counts, partial results or ordering); **no side effect** — asserted by **row diff plus instrumented effect ports**: the harness runs with the adapter transport, SSE sink and outbox enqueue behind test instruments and asserts zero emissions, because a row diff alone cannot see an external effect that escaped and rolled back ([#22](https://github.com/Dunky13/wenv/issues/22)'s no-external-effect-before-commit is the invariant being probed, so the probe must watch the effect ports, not the rows).
- **Instance-scoped operations**: probed for **grant refusal, not tenancy** — a principal *without* the instance capability (an org admin, the strongest non-instance fixture) receives the uniform denial; asserts the `InstanceProof` path is grant-evaluated, closing the route-selection-as-authorization failure.
- **Unauthenticated operations** (login, health, bootstrap): probed under the pre-auth contracts fixed elsewhere — enumeration-uniformity and admission limits per [#16](https://github.com/Dunky13/wenv/issues/16) — enumerated here only so the classification is total.
- **System operations** (`migrate`, boot-time checks, recovery-mode reconciliation, break-glass local authority): the probe contract is **network unreachability plus local-authority preconditions** — no HTTP route exists for any of them (asserted against the OpenAPI spec and the router's route table), and each asserts its local precondition (host-process identity, root-owned socket/file per [#15](https://github.com/Dunky13/wenv/issues/15)'s break-glass mechanics, recovery-mode server state). A system operation reachable over the network is the probe failure.

Non-HTTP entry points enumerate from **registries, not conventions**: the outbox job-type registry, the SSE emit sites, the operator fetch and CLI-only verbs from the OpenAPI spec ([#22](https://github.com/Dunky13/wenv/issues/22), spec-first), and the system-operation registry for the fourth class. **What the harness does not assert: wall-clock timing equality.** The timing half of unauthorized ≡ nonexistent is delivered at the **application layer** — single-query chain resolution (one query, one round trip, one code path regardless of failing level) and filter-in-query (no found-then-rejected branch) remove every timing signal the application code itself generates — while **engine-internal microtiming** (join short-circuit on a missing row, planner variance, cache warmth) is an accepted, stated residual, because a CI wall-clock assertion is a flake generator, not a control, and no locked mechanism measures wall clock either (the locked contract tests assert status and body). This is the strongest deliverable reading of [#22](https://github.com/Dunky13/wenv/issues/22)'s "including timing": structural at the layer the application controls, honest about the layer it does not.

**The static layer (lint, build-failing).** Three custom analyzers (go/analysis, run under the repo's linter), each with its limit stated:

1. **Proof-signature analyzer**: every exported method in `internal/store` operating on a tenant-owned aggregate takes a proof as its first parameter **and takes no tenant-identifier-typed parameter** (`domain.OrgID`/`ProjectID`/`EnvID`) beside it. Limit: cannot prove what the method body does with the proof — that is the boundary check's job.
2. **SQL predicate analyzer**: sqlc queries are static SQL. The analyzer is **conservative by design**: for every statement touching a tenant-owned table it requires the full owning-scope chain predicate as a **top-level conjunct** — in *each* `UNION` branch, *each* CTE that reads a tenant table, and the `ON`/`WHERE` of each tenant-table join alias — and **rejects any query shape it cannot prove**, forcing a rewrite into a provable shape. An `OR` beside the tenant conjunct, a predicate stranded in an unused CTE, or a constrained alias beside an unconstrained one all fail. For inserts/upserts it requires the chain columns bound to the reserved proof-populated parameters, and no `SET` on chain columns anywhere. **The tenant-table registry is derived, not curated**: every table declares its scope class in migration metadata; a table with no declaration fails the build, so a new table cannot be invisible to the analyzer.
3. **Proof-forgery guard**: no `reflect`/`unsafe` on proof types, no declaration of the concrete proof type, and no nil-proof literal outside the authorization package.

**The `instance-scoped` escape annotation is content-pinned, not counted.** Each `-- wenv:instance-scoped` query is recorded in a reviewed fixture as `(query name, SQL hash)`: broadening an annotated query changes its hash and shows as a fixture diff; moving the annotation to a different query is an add-plus-remove, not an invisible swap. A bare count was bypassable without count growth; the hash pin is what makes the allowlist reviewable in diffs.

**Honest limits, stated:** the analyzers are guardrails — a wrapper that assembles SQL outside sqlc's static queries, or logic bugs *inside* the trusted set, are beyond lint. The trusted set is explicit and enumerated: the authorization package (including the formula evaluation and the store boundary check), the `internal/store/authn` resolution interface, the transaction package, and the store's query registry. Those get the adversarial review depth; changes to them are the highest-scrutiny diffs in the repo. The import-boundary test ([#22](https://github.com/Dunky13/wenv/issues/22)) completes the set: handlers cannot reach the store, store methods cannot be called without a proof, a proof cannot be minted without `authorize()`, a minted proof dies with its transaction and operation, queries cannot omit the chain predicate, and every operation class must demonstrate its refusal contract in CI.

## CI invariants

1. **Classification totality**: every OpenAPI operation, outbox job type, SSE emit site, CLI verb and system entry point carries exactly one probe class (tenant-scoped / instance-scoped / unauthenticated / system); unclassified fails the build. System-class probes assert network unreachability.
2. **Probe fixtures**: the harness includes cross-org human probes **and** cross-project machine probes; removing either fixture axis fails the harness's own self-check.
3. **Uniformity**: cross-tenant probe responses are byte-identical in status and body shape to genuine-missing responses (shared assertion helper with the contract tests). Timing is delivered structurally (single-query chain resolution), not wall-clock-asserted.
4. **No side effect**: mutation probes assert zero rows written (row diff) **and zero emissions on instrumented effect ports** (adapter transport, SSE sink, outbox enqueue).
5. **Proof lifecycle**: boundary tests assert a nil proof, a foreign-transaction proof, a committed-transaction proof, and an operation-mismatched proof are each rejected fail-closed at the store boundary.
6. **Operation registry completeness**: every store method is registered to operation(s), every operation to a formula; unregistered fails the build.
7. **Proof signatures**: analyzer 1 passes — proof-first parameter, no tenant-typed parameters beside it, transitively including argument struct fields.
8. **Predicate confinement and chain-binding provenance**: analyzer 2 passes — conservative per-branch chain conjuncts, no `SET` on chain columns, derived scope-class registry total over all tables — and the conformance suite asserts the generated binding layer maps every chain parameter from proof fields and from nothing else, with no chain parameter exposed in any caller-facing signature.
9. **Forgery guard**: analyzer 3 passes — no `reflect`/`unsafe`/concrete-type/nil-literal on proof types outside the authorization package.
10. **Tenant columns**: every tenant-owned table carries the immutable id chain to its owning scope class with **composite ancestry FKs**; a migration dropping, loosening or de-compositing one fails; the conformance suite asserts chain columns are unmodifiable through the store on both engines.
11. **System-proof enumeration and binding**: the set of `SystemProof` mint sites is exactly {boot, migration, recovery-mode reconciliation, break-glass local authority}, each bound to its closed per-site operation set in the system-operation registry; a new mint site or a widened operation set fails until this ADR is amended. Boundary tests assert a `SystemProof` is rejected for operations outside its site's set. `InstanceProof` mint sites all route through `authorize()` with an instance-scope formula.
12. **Cache keys**: every cache holding tenant-owned data exposes proof-taking accessors and a single exported proof-consuming key constructor with full-chain structured encoding; ad-hoc key construction is lint-banned.
13. **Allowlist pinning**: the `instance-scoped` annotation fixture pins `(query name, SQL hash)`; any drift fails until the fixture is re-reviewed.

This ADR binds **[#24](https://github.com/Dunky13/wenv/issues/24)** (audit events carry the acted-on scope's id chain; audit reads are proof-scoped), **[#25](https://github.com/Dunky13/wenv/issues/25)** (every endpoint and CLI verb names its operation in the registry `authorize()` evaluates; the spec is the probe harness's enumeration source), **[#28](https://github.com/Dunky13/wenv/issues/28)** (adapter job steps mint per-step transaction-bound proofs against the recorded authority principal), **[#32](https://github.com/Dunky13/wenv/issues/32)** (per-org/per-principal quota and rate-limit values; probe-harness runtime budget), and the synthesis ([#27](https://github.com/Dunky13/wenv/issues/27)). It amends nothing: every upstream constraint it touches is restated, not changed.
